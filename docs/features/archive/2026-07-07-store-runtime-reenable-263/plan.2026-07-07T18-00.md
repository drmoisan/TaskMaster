## Binding Design Decisions (resolve the spec's "confirmed during atomic planning" open items)

1. **Bounded retry window (spec STA-Safety, AC6).** The coordinator's per-call readiness/retry loop is bounded by a **maximum readiness-attempt count of 20 attempts** (mapping to roughly 60 s under the production `HookReadinessCoordinator` cadence of 1 s initial / 5 s after 10 ticks). The bound is expressed as an attempt count, not wall-clock time, so the pure decision logic is deterministic and COM-free-testable (tests drive `SetupSequence(...).Returns(false)` 20 times and assert `TransientTimeout` on the 21st decision, mirroring `HookReadinessCoordinatorTests`). Exceeding the bound returns `TransientTimeout`; no `Thread.Sleep`/`Task.Delay`/real timer is used in production or tests.
2. **Result type location (reconciled).** `StoreRehookOutcome` (enum) and `StoreRehookResult` (record) live in `UtilitiesCS/OutlookObjects/Store/StoreRehookResult.cs`. F1's shipped `IStoreRehookService.RehookAsync(StoreIdentity)` returns a bare `Task` (no outcome value), so `StoreRehookResult` is **not** the interface return type. It is the coordinator's internal result type, returned by the internal core method `RehookStoreCoreAsync(string)`; it remains resident in `UtilitiesCS` and visible where the coordinator (in the `TaskMaster` assembly) needs it. Its five outcomes and the coordinator tests are unchanged in intent.
3. **Interface ownership and visibility (reconciled).** F1 owns and ships `public interface IStoreRehookService` in namespace `UtilitiesCS` (verified in merged code). F3 **implements** it in `StoreRehookCoordinator`; F3 does not create or recreate the interface file. `StoreRehookResult`/`StoreRehookOutcome` remain public types in `UtilitiesCS`. `TaskMaster` already declares `[assembly: InternalsVisibleTo("TaskMaster.Test")]`, so the coordinator's internal core method is directly testable without widening its public surface.
4. **Identity parameter and adapter (reconciled).** The coordinator's public method is F1's exact signature `public async Task RehookAsync(StoreIdentity identity)`. It adapts to the rich decision logic: it extracts `identity.Value` (the DisplayName-primary resolved key — `StoreIdentity` has no `DisplayName` property), invokes the internal core `internal async Task<StoreRehookResult> RehookStoreCoreAsync(string storeIdentity)`, logs the resulting outcome (log4net) with identity/subsystem/HRESULT where COM-derived, and returns `Task`. No outcome is propagated to F1 (its seam is void-returning `Task` by design). F3 therefore has an **unavoidable and intended** compile-time dependency on `StoreIdentity` (F1's collaborator seam), but takes **no** compile-time dependency on `IStoreDisableService` (AC9).
5. **DI accessor (reconciled).** An `IStoreRehookService StoreRehook { get; }` accessor on `IApplicationGlobals` is **optional, not required**. F1 obtains the collaborator via constructor injection at the DI construction site in `ApplicationGlobals.cs` (`new StoreDisableService(this, <coordinator>)`), not via the aggregate. A public `StoreRehook` accessor on `ApplicationGlobals` may be retained for symmetry with `StoreDisable`, but `IApplicationGlobals` is not modified unless a consumer genuinely needs the coordinator reachable through the aggregate.

## Highest-Risk Tasks (live COM event rewiring) — isolation and verification

The primary risk is a leaked or duplicated event subscription during live rehook (spec Risks; issue "must not leak subscriptions or double-hook"). The following tasks touch live `+=`/`-=` wiring and carry StoreID-keyed idempotency obligations. Each is isolated behind a mockable seam and verified without live Outlook:

- **P3-T3 (AppEvents per-store inbox-item-subscribe primitive + StoreID-keyed dictionary).** Risk: unconditional `OlInboxes.AddLast` double-subscribes on repeat. Verification: `AppEventsStoreRehookTests` asserts a second call for the same StoreID performs zero additional `ItemAdd` subscribes via Moq `Times.Never()`, using the existing `Mock<Items>` pattern from `AppEventsTests`.
- **P3-T5 (OutlookFolderNotificationSink `AddStore`/`RemoveStore`, frozen list → mutable StoreID-keyed structure).** Risk: re-subscribing an already-present StoreID, or leaking a subscription on remove. Verification: `OutlookFolderNotificationSinkTests` extended with add/remove and already-present-no-op cases using the existing `FakeSubscription` fixture; assert subscription count invariants and `Times.Never()` on repeat add.
- **P4-T2 (coordinator sequencing of the four live primitives behind the readiness gate).** Risk: eager expensive COM read before the gate is ready, or an uncaught COM exception escaping. Verification: `StoreRehookCoordinatorTests` drives every branch through injected seams (no COM), asserting ordering, no primitive invocation before the gate reports ready, `AlreadyHooked` performs zero primitive calls, and all five outcomes are returned without a thrown exception.

Mitigation is structural: the coordinator depends only on narrow injected interfaces (store-lookup seam, StoresWrapper gateway, inbox-hookup seam, `IOutlookFolderNotificationSink`, `IOutlookFolderTreeService`, extended `IOutlookReadinessGate`), so every risk path is exercised deterministically with Moq.
