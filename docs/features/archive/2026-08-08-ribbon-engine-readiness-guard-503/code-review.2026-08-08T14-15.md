## Executive Summary

The design is the right one for this defect and for this codebase. The central insight — that readiness must be evaluated per engine key rather than as a global "initialization complete" flag — is correct and well argued: `AppItemEngines.InitAsync()` filters engines on `config.Value.Engine` and drops null factory results, so a coarse flag would report ready for a command that will never work, converting a timing bug into a permanent one. The second key decision, deferring the engine dereference into a `Func<Task>` lambda rather than scattering null-conditional operators through eight handlers, is what makes the guard a single auditable chokepoint instead of eight independent partial fixes.

The separation between decision and presentation is disciplined. All four new types are host-neutral, carry zero `Microsoft.Office.*` reference, take their collaborators as plain delegates, and are deliberately left out of the coverage exemption. Everything that touches COM stays inside types that were already exempt at the merge-base. This is the distinction the repository's own #227 precedent asks for, and it is applied here without the usual slippage of pushing one more decision into the exempt shim.

Error handling is correct in the way that matters most for a guard: the runner contains no `catch` clause of any kind, so it can never degenerate into a swallow-all. `RunAsync` validates its action argument before touching the gate, so a programming error surfaces immediately rather than being masked by a closed gate. The ready path returns `action()` directly, which preserves the caller's await semantics and keeps behaviour byte-identical to the pre-fix handlers.

Test quality is high. Each of the 45 added tests names a behaviour, follows Arrange–Act–Assert explicitly, and supplies a `because` reason on every assertion. The regression tests deliberately reproduce both reported exception shapes, and the S1-to-S2 transition is modelled by mutating a dictionary between two probes rather than by any timing construct.

Seven findings are recorded. None is blocking. The most substantive is a null-conditional operator in the ribbon-XML test that makes the assertion named by AC5 silently vacuous when the attribute is absent; the acceptance criterion is nevertheless genuinely enforced, because a sibling test asserts set equality over the declaring ids. The remainder are a narrow residual dereference window the readiness contract does not cover, a non-thread-safe lazy initialiser, and four documentation or process observations.

## Design and Implementation Notes

**What is done well, and worth preserving as a pattern.**

The lambda-deferral technique is the load-bearing idea. Because the caller passes `() => Controller.SB.TrainAsync(Controller.OlSelection, true)` rather than a pre-evaluated task, the engine is dereferenced only inside the lambda body, and the lambda body runs only when the gate is open. This converts eight distinct dereference sites into one guarded call site without editing any of the eight expressions. The relocated handler bodies are byte-identical to their merge-base text apart from the wrapping, which was verified by reading the removed and added regions of `RibbonViewer.cs` side by side.

The refusal to add a member to `IAppItemEngines` is correct and correctly justified. .NET Framework 4.8.1 has no default interface members, so any new member could only be bodied inside `AppItemEngines`, which is `[ExcludeFromCodeCoverage]` at type level; the new logic would have been entirely uncoverable. Reading the already-published `InboxEngines` member instead yields a zero-line diff on both fenced files, zero test-double churn, and full coverage of the decision. This is a better outcome than the acceptance criterion literally demanded.

The choice not to route readiness through `RibbonController.SB` or `Triage` is a real correctness decision, not stylistic caution: those getters install a `WindowsFormsSynchronizationContext` on the calling thread as a side effect. The code comments record this, and the tests avoid those getters entirely. Likewise, `() => Globals?.Engines` is used rather than the existing `RibbonController.Engines` property because the latter is not null-safe on `Globals` — a distinction the author noticed and recorded rather than tripping over.

`EngineCommandRefreshPlanner` deriving its invalidation set from `EngineCommandCatalog.ControlIds` rather than duplicating a literal list is what allows a single test to prove the XML, the callback, the guard, and the refresh all agree on the same eight ids. Asserting that set as set equality rather than sequence equality is correct, because Office documents callback ordering as unspecified.

**Documentation quality.** The XML doc comments explain *why* consistently — why the type is not coverage-exempt, why the probe is per-key, why the marshalling is explicit rather than ambient, why each null-forgiving operator is present. The three null-forgiving operators each carry an adjacent comment recording that null is a supported value with a defined contract, which is the right way to use that operator.

**Notification presentation.** The `Action<string>` sink is the correct seam: the decision to notify and the message content are host-neutral and unit-tested, while the presentation sits in the exempt shim. The delivered presentation is `logger.Warn` plus `MessageBox.Show`, which is a modal dialog rather than the "non-modal indication" the spec's prose suggested. The deviation is explicitly recorded in `spec.md` Deviation 1 with the rationale that the repository has no non-modal notice surface and introducing one would be scope creep for a bug fix. That reasoning is sound; the binding acceptance criterion (AC12) constrains only the sink contract, which is satisfied. Worth noting for follow-up: a modal dialog on every blocked click during a startup race could be intrusive if a user clicks repeatedly, since the runner emits one notification per blocked invocation rather than one per session.

**Test-runner caveat for future reviewers.** Running `TaskMaster.Test.dll` under `Common7\IDE\CommonExtensions\Microsoft\TestWindow\vstest.console.exe` without `/Settings:TaskMaster.runsettings` produces 26 failures, all a `System.Threading.Tasks.Extensions, Version=4.2.0.1` load failure inside `Moq.Async.AwaitableFactory` caused by the app.config binding redirect not being applied. Three unrelated pre-existing tests fail identically under the same invocation, which is what identifies it as an environment artifact. The same 69 tests pass under `Common7\IDE\Extensions\TestPlatform\vstest.console.exe` with the runsettings file, which is the binary `scripts/vscode/Invoke-MSTestWithCoverage.ps1` resolves. CLAUDE.md CUT3 does not pin either choice.

## Verdict

**Approve, with the recorded findings as non-blocking follow-ups.** The Medium finding on the vacuous test assertion should be fixed, either in this change or in an immediate follow-up, because the acceptance criterion it is named against depends on it; the criterion itself remains genuinely enforced in the meantime by the sibling set-equality assertion. Nothing in this review requires a remediation plan or blocks PR creation.
