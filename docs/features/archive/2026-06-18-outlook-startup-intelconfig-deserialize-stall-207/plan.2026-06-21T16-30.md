**Guardrail: net48 type constraints.** Target framework is net48. Do NOT introduce positional `record struct` (its compiler-generated `init` accessors require `System.Runtime.CompilerServices.IsExternalInit`, unavailable on net48 → CS0518). **Guardrail: banned APIs (BannedApiAnalyzers RS0030) — REMEDIATION NOW IN SCOPE (AC10).** No `DateTime.Now`, `DateTime.UtcNow`, `Random.Shared`, `Thread.Sleep`, or `Task.Delay` may remain in ANY production file this fix touches — including pre-existing call sites within those files. The pre-existing `Task.Delay(100)` in `AppEvents.ProcessNewInboxItemsAsync` (current line ~456, the unprocessed-queue error-retry path) is remediated, not deferred: it is replaced by `await NonBlockingDelay.WaitAsync(TimeSpan.FromMilliseconds(100))`, a non-blocking, pump-independent awaitable that completes when a `System.Threading.Timer` fires its callback and sets a `TaskCompletionSource` (never blocks the STA, and does not require a running Dispatcher). `System.Threading.Timer` is NOT in the banned-API list (`DateTime.Now`/`DateTime.UtcNow`, `Random.Shared`, `Thread.Sleep`, `Task.Delay`), so the helper satisfies AC10. Any `DateTime.Now`/`DateTime.UtcNow` discovered in a touched file is remediated via an injected `System.TimeProvider` (`GetUtcNow()`/`GetLocalNow()`), per `.claude/rules/csharp.md` time seam; any `Thread.Sleep`/`Task.Delay` is replaced with `NonBlockingDelay.WaitAsync`. The sweep is scoped to touched files ONLY (`AppEvents.cs`, `AppOlObjects.cs`, `AppOlObjects.JunkFolders.cs`, the four new production files); it does NOT expand to untouched files. Any new timing uses `System.Diagnostics.Stopwatch`; polling uses `System.Windows.Threading.DispatcherTimer` only.

**Guardrail: COM apartment reality.** Outlook COM objects are apartment-bound to the STA on which they were created. COM property reads, event subscriptions, `Restrict` calls, and `SetUdf` writes MUST execute on the STA — moving them to a worker thread marshals back to the STA and does not free it. Only pure compute on already-extracted .NET primitives (strings/ints) may run on a worker.

**Guardrail: NonBlockingDelay design (pump-independent).** `NonBlockingDelay.WaitAsync(TimeSpan)` is a `static` helper returning a `Task` that completes when a one-shot `System.Threading.Timer` (created with the supplied due time and an infinite period) fires its callback and sets a `TaskCompletionSource<bool>`; the timer is disposed inside the completion callback. Design rationale:
- **Pump-independent.** It completes whether or not a `Dispatcher` is running on the current thread. This is the corrective change from the prior `DispatcherTimer`-backed design, which completed only on a Dispatcher tick and therefore hung the pump-less MSTest host (regression captured in `evidence/regression-testing/gated-mstest-hang-regression-2026-06-22T14-55.md`). The `System.Threading.Timer` approach restores the pump-independent completion behavior the prior `Task.Delay(100)` had.
- **Non-blocking and STA-safe.** It returns a `Task` immediately; the awaiting code suspends and yields control to the message loop, so an STA continues pumping window messages during the wait. The timer callback fires on a threadpool thread and sets the TCS; the `await` continuation then resumes on the captured STA `SynchronizationContext`, so subsequent COM work still runs on the STA.
- **No banned API.** `System.Threading.Timer` is NOT in the banned list (`DateTime.Now`/`DateTime.UtcNow`, `Random.Shared`, `Thread.Sleep`, `Task.Delay`); the helper satisfies AC10 and contains no banned call.
Because the helper no longer depends on a Dispatcher, it is pump-free and deterministically unit-testable; it carries the new-code coverage obligation (≥ 90%) and is NOT in the COM/VSTO coverage-exempt set.
