## Verified context (do not re-litigate)

- The Phase 3.1/3.2 heartbeat was scoped to `ApplicationGlobals.LoadSequentialAsync`, which runs in ~3 s. The maintainer confirms the UI locks for ~2 minutes on EVERY cold start. The freeze window is therefore NOT bounded by `LoadSequentialAsync`.
- In `evidence/other/runtime-capture-allphase-uiheartbeat-gc-2026-06-24T10-24.md`: `Application_Startup() complete` at 10:24:41; first heartbeat/IntelConfig at 10:24:49 (an ~8.6 s gap with no heartbeat coverage); `Finished loading globals` 10:24:52; TaskMaster's last log line 10:24:58; external Outlook provider churn (`GLookSyncer`, `GmailSyncImpl::Init`, `WrappedMSProvider::Logon` 0x80040401) continues to ~10:26:28 (~108 s after `Application_Startup`). The existing heartbeat only covered ~3 s of a ~108 s freeze.
- Goal: measure the ENTIRE add-in startup lifetime so the next capture shows exactly when the STA (UI thread) is frozen — before `LoadSequentialAsync`, during it, and after globals finish — and for how long.

## Acceptance criterion introduced by this plan

- **AC15 — Full add-in-startup-lifetime UI heartbeat with stage labels and bounded self-stop.** A 250 ms `DispatcherTimer` UI heartbeat starts as the FIRST action in `TaskMaster/ThisAddIn.cs` `Application_Startup` (before `SetUpBrightIdeasSettings()`, `SetUpDeedle()`, `new ApplicationGlobals(...)`, and the `IdleAsyncQueue.AddEntry` calls), using `UiThread.Dispatcher`. It runs CONTINUOUSLY across the whole add-in startup, independent of `LoadSequentialAsync`. Each tick emits one `[startup-lifetime-heartbeat] stageLabel=<...> nominalMs=250.0 actualMs=<F1> gapMs=<F1>` line via the existing `log4net` logger, where `gapMs` far larger than nominal proves the STA was blocked for that interval. A coarse `stageLabel` is maintained and updated at lifecycle points (`PreGlobalsCtor`, `GlobalsCtor`, `AwaitingIdleQueue`, `Loading`, `PostLoad`); the `Finished loading globals` log point flips the stage to `PostLoad`. The heartbeat is bounded: it self-stops and disposes the timer when EITHER (a) a max cap is reached (~180 s after start) OR (b) the UI has been continuously responsive (gapMs below a small threshold) for a sustained run of consecutive ticks after `PostLoad`. The pure gap/stage/stop-condition logic lives in `StartupDiagnosticsProbe` (coverable, not `[ExcludeFromCodeCoverage]`) and is covered by deterministic MSTest (synthetic tick timestamps; asserted stop decisions and formatted lines) with no live timer/Dispatcher/COM/filesystem/network and no temporary files. The `DispatcherTimer` construction/start/stop stays in `ThisAddIn` (lifecycle-exempt) as a thin seam. Startup order/semantics are unchanged; the existing `[ui-heartbeat]`, `[gc-delta]`, `[continuation-resume]`, and `[engine-init]` lines are unchanged. `PreserveReferencesHandling.All` is untouched. New code reaches `>= 90%` coverage with no repository-wide regression; the full C# toolchain passes in order.
