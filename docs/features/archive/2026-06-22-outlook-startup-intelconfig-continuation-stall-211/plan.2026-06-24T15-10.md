## CONSTRAINT-A — SpamBayes.cs 500-line ceiling (binding)

`SpamBayes.cs` is already 705 lines. The hard constraint forbids silently exceeding 500. The instrumentation strategy is therefore:

1. All pure line-formatting logic goes into a NEW coverable helper `SpamInitTimingProbe` (NOT in `SpamBayes.cs`).
2. The `Stopwatch` wrapping + per-sub-step + per-folder COM reads added to `SpamBayes.cs` must be minimal.
3. Because `SpamBayes.cs` is already 705 lines, adding any net lines worsens an existing violation. The plan REQUIRES a net-neutral-or-better outcome for `SpamBayes.cs`: the instrumentation additions MUST be offset by extracting three self-contained regions of `SpamBayes.cs` into sibling partial-class files (`SpamBayes.Conditions.cs`, `SpamBayes.Actions.cs`, `SpamBayes.Classify.cs`) so that, after edits, `SpamBayes.cs` is `<= 500` lines (verified to reach ~402 lines) AND no new file exceeds 500 lines. A single-file extraction (removing only ~89 lines) is mathematically insufficient: it would leave `SpamBayes.cs` at ~616 lines, still over 500, before Phase 3 instrumentation adds more. P0-T2 measures the exact baseline; if the three extractions cannot bring `SpamBayes.cs` to `<= 500`, P1 STOPS and surfaces the residual as a blocking constraint decision for the maintainer (do not exceed 500 silently).

This constraint is auditable in Phase 0 (baseline line count) and Final QA (post-change line count for every touched/new file).
