## Executive Summary

This is a minimal, well-targeted bug fix. `QfcDatamodel.InitEmailQueue` previously had no guard for `batchSize <= 0`, so High-Confidence mode's intentional zero-batch call fell through to an unconditional Deedle slice-and-project (`_frame.GetRowsAt(Enumerable.Range(0, 0))` → `GetRowsAs<IEmailSortInfo>()`), which throws on an empty column index. The fix adds a 4-line early-return guard before the existing clamp/slice logic, leaving the `batchSize > 0` path byte-for-byte unchanged (confirmed by diff inspection). A companion `RemainingEmailLoader` injectable-delegate seam was added so the new tests (which necessarily start a real `BackgroundWorker`) do not trigger the production `MessageBox.Show`/live-Outlook-COM path in `LoadRemainingEmailsToQueueAsync`. The v1.1 revision of the test file correctly replaced an earlier, flaky `worker.IsBusy` assertion with a deterministic `WorkerSupportsCancellation` + bounded `TaskCompletionSource` wait, and correctly removed a test defect that previously triggered a live modal dialog during test runs — both self-identified and fixed by the executor before this review, per `.claude/agent-memory/atomic-executor/project_qfc_backgroundworker_async_void_race.md`.

Independent verification performed for this review: read the full production diff; re-ran `dotnet tool run csharpier check` on both touched `.cs` files (clean, exit 0); read the new test file end-to-end; confirmed the `batchSize > 0` branch is textually unchanged below the new guard; confirmed both file sizes are under the 500-line limit (471 and 212 lines respectively); confirmed no banned APIs (`Thread.Sleep`, `Task.Delay`, `DateTime.Now`) appear in the new/changed lines.

No functional defects were found in the shipped fix. Two non-blocking quality observations and one blocking, process-level coverage-artifact gap are recorded below (the coverage-artifact gap is detailed fully in `policy-audit.2026-07-06T12-48.md` §5 and is not duplicated as a code defect here).
