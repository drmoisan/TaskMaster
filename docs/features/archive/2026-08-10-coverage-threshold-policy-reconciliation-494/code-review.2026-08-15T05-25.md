## Executive Summary

The code in this fan-in is of good quality and is unusually well documented for shell code. Every
new PowerShell function is an advanced function with typed, validated parameters and
comment-based help that states purity, ordering constraints, and — in the case of
`Remove-CoberturaExemptClosureCoverage` — an explicit fail-safe invariant with the reason it must
hold. The new closure filter reaches 100% line coverage. The four mechanical lanes each do what
they claim.

Five Major findings and twelve Minor findings are recorded. None is Blocking.

Three findings are worth separating from the rest because they concern the epic's own subject —
gate fidelity — rather than ordinary code quality:

1. **CR-1** — The new `Assert-CoberturaLineCoverageThreshold` hard-codes an 80% line floor and no
   branch floor, in a repository whose always-loaded rule files mandate 85% line and 75% branch.
   The epic set out to remove a contradiction between gates and what they measure; on this lane
   it added a fourth numeric authority instead.
2. **CR-3** — The Pester suite that certifies this work executes `vswhere.exe` and a script that
   rewrites tracked `.csproj` files. The same suite over the same source produced two different
   coverage figures (`Sync-PackageReferences.ps1` 71/84 in committed evidence, 53/84 in the
   reviewer's head run). The evidence that certifies the gates is itself non-deterministic.
3. **CR-5** — When the new threshold gate fails, it throws before the processed coverage document
   is written, so the artifact left on disk is the raw one. The diagnostic a developer would open
   after a failure is the wrong document.

The merge resolution at `fb8eff9b` is clean: all three conflicted files resolved to supersets of
both parents with no dropped hunk. The one merge defect is in a file that did *not* conflict —
`CLAUDE.md` still names `.github/workflows/ci.yml` for three commands that `main`'s workflow split
moved into reusable workflows (CR-2).

## What the branch does well

Recorded because it is load-bearing for the Minor-not-Major severities above.

- `Remove-CoberturaExemptClosureCoverage` states its fail-safe invariant explicitly — "a method
  whose declaring member could not be derived is RETAINED" — and the code honors it at
  `ClosureFilter.ps1:296-300`. Every failure mode of the key is in the under-exclusion direction,
  so a file can only measure worse than it truly is, never better. This is the correct direction
  for a filter that shrinks a coverage denominator, and it is the reason the denominator change
  is a Major policy tension rather than a Blocking correctness risk.
- The ordering constraint between the closure filter and the merge is documented at
  `ClosureFilter.ps1:245-249` with the reason it cannot be reversed ("Running it after the merge
  does not degrade the result, it makes the result unobtainable"), and the call site at
  `Helpers.ps1:427-428` honors it.
- `Test-CoberturaClosureClassName` deliberately excludes `Type.<Member>d__<N>` state machines,
  with the consequence of getting it wrong spelled out ("Classifying it as a closure would delete
  the coverage of every async member").
- `ConvertTo-KoverageCoberturaXml` recomputes the root `line-rate`, `lines-covered` and
  `lines-valid` from `Get-CoberturaCoverageSummary` *after* both the closure filter and the merge,
  so the threshold gate judges post-processed arithmetic rather than the collector's raw figures.
  This was verified specifically because asserting on a stale root attribute would have
  reintroduced the #441 defect inside the #494 gate.
- `-EnableNullable` is retained as a warning-emitting no-op rather than deleted, so an unknown
  external caller still binds while being told the switch is inert.
- No changed test file creates a temporary file, uses `TestDrive`, `Start-Sleep`, or `Get-Random`.
