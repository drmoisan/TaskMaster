## Design and Consistency Assessment

- **Seam pattern consistency:** The new `_openByModeAndAccess` field, its public-constructor default binding (`_fileInfo.Open`), and its internal-constructor null-guarded parameter are structurally identical to the three pre-existing seams (`_appendText`, `_openByMode`, `_openWrite`) in the same class. This is the correct application of "match existing style" (General Code Change Policy §7.1) over introducing a new abstraction (e.g., a full `IFileOpener` interface) for a single member.
- **Production behavior preserved:** The public constructor binds `_openByModeAndAccess = _fileInfo.Open;`, an exact method-group reference to the real `FileInfo.Open(FileMode, FileAccess)` overload, so production call sites are unaffected. This was independently confirmed via the CSharpier/analyzer/nullable re-runs in this review's policy audit, all of which found zero diagnostics on the touched files.
- **Test change precision:** The test change removes exactly the one real-file 2-arg `Open` call that was the documented root cause (previously at `PhysicalFileSystemAdapters_Tests.cs:207`, per `evidence/baseline/line-anchors-baseline.2026-07-08T00-05.md`) and replaces it with an assertion against the seam-provided sentinel stream. No unrelated assertions were weakened or removed; the pre-existing `openModeReadSharedCanRead`/`openReadCanRead`/`openTextLine` assertions are untouched.
- **Comment quality:** Both files' updated comments explain the underlying "why" (the `FileShare.None` default is the contention mechanism, not the read/write direction of the call) rather than restating "what" the code does, consistent with General Code Change Policy §5.3.
