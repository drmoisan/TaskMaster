## Executive Summary

Verdict: **PASS**. 0 Blocking findings, 11 Non-blocking findings.

This is a careful delivery. Three design choices are worth naming because they are the ones that make the change trustworthy rather than merely working.

First, the counting rule is not re-derived. `ConvertTo-JacocoPackageProjection` calls `Get-CoberturaPackageLineSummary` once per package and performs exactly one new arithmetic step — JaCoCo `missed` equals valid minus covered, computed independently for lines and for branches. An abstract-syntax-tree test proves the delegation mechanically: it asserts the shared summariser is invoked, that no string anywhere in the file names the `condition-coverage` attribute, that the file declares no hashtable literal, and that it performs no index assignment. Those are the shapes a second implementation of the de-duplicating rule would take, so their absence is evidence rather than assertion.

Second, the reconciliation assertion is exact and is covered on both of its equalities. The projection is committed as evidence in place of the document it summarises, so a silent arithmetic divergence would become undetectable the moment the raw document is discarded. `Assert-JacocoProjectionReconciliation` enforces two independent equalities — summed covered against the root `lines-covered`, and summed missed plus covered against the root `lines-valid` — and each has its own negative test that asserts both the throw and the presence of the expected and observed figures in the message. The second of those two tests exists only because the coverage gate caught line 143 as unexercised on its first measurement; the residual was diagnosed and closed rather than explained away.

Third, the conditional discard is split into a pure predicate and the discard itself. `Test-RawCoverageDocumentRetained` takes the output path and the repository root, performs path arithmetic only, and returns a boolean. The `Remove-Item` stays at the entry point. That split is what makes the discard decision unit-testable with no file existing anywhere, which matters because the repository prohibits temporary files in tests with no approved exception. The predicate uses equality rather than containment, deliberately, and a third test supplies a subdirectory of the coverage tree specifically so that a containment implementation cannot pass by coincidence.

The eleven Non-blocking findings cluster around one theme. The coverage entry point's post-run sequence — projection write, reconciliation, summary write, conditional discard — is correct in its ordering but couples two concerns that are independent. Findings 1, 2 and 3 are all consequences of that coupling, and all three are cheap to address. Nothing in this review blocks merge.

## Detailed Observations

### Design and separation of concerns

The two new part files are correctly scoped. Both are pure, both declare `Set-StrictMode -Version Latest` at the top, and neither performs filesystem or process I/O. The decision to create a new part file rather than extend `Invoke-MSTestWithCoverage.Helpers.ps1` is justified by measurement rather than preference: the helpers file stood at 470 lines against the 500-line ceiling, so the three projection functions would have breached it on their own. The header comment records that reasoning, which is the right place for it.

The summary part file is a separate file rather than an addition to either entry point because both entry points dot-source it. That is the correct call. Duplicating the reader in two entry points would give one behaviour two implementations, and the reader is the piece whose namespace handling is most easily got wrong.

One dot-source arrangement is worth noting as correct but fragile. `Invoke-MSTestWithCoverage.Helpers.ps1` dot-sources the projection part file, so a caller that dot-sources the helpers alone resolves all three projection functions transitively. The summary part file is not in that chain, so `Invoke-MSTestWithCoverageMain` dot-sources it explicitly at line 295. The comment at lines 291-294 states exactly why — without that line `Get-TrxRunSummary` would be unresolvable and every summary attempt would silently take the non-fatal warning branch, so no summary would ever be written. That is the right comment to have left: the failure mode is silent, and a future reader removing the line as apparently redundant would not see a test fail.

### Strict-mode handling

Both new files handle a repository-specific hazard correctly and document it. Under `Set-StrictMode -Version Latest`, bare property access on a missing XML attribute throws rather than returning `$null`. The projection writer uses `GetAttribute` with a comment recording the reason, and the summary reader guards each `GetAttribute` with `HasAttribute` so that a counter the test platform omitted reads as zero rather than throwing. The distinction matters: an omitted counter is a legitimate document rather than an error, and the comment at lines 59-61 of the summary part file says so.

### Error handling

Error handling is specific and fails fast. Four throw sites exist across the two new files, and each names the condition. The missing-packages wording is reused rather than duplicated: a case-sensitive search across `scripts/vscode` for the phrase `does not contain a` returns four occurrences of exactly one distinct string, `Cobertura XML does not contain a <packages> node.`, and the projection part file's occurrence is byte-identical to the three that preceded it. The test that proves this obtains the expected message by invoking the first-party helper on the same fixture and capturing what it throws, rather than restating the literal. That is the right construction: restating it would make the test pass even if the two wordings had drifted apart.

The one non-fatal path is justified and covered. A missing, unreadable, unparseable or result-summary-less test-result document produces a `Write-Warning` rather than a throw, because a genuine test failure is already surfaced by the exit-code check upstream and a caller that mocks no content reader must not be forced to write a real document. `tests/scripts/vscode/Invoke-MSTest.ResultsDirectory.Tests.ps1` asserts that branch directly, including that neither the summary write nor the discard occurs. Four such warnings were observed in the final full-folder run and are accounted for in the test artifact, so they are not mistaken for a defect.

### The call-order test

The discard-ordering assertion is the strongest test in the delivery and deserves specific credit. It captures call order into a script-scoped list through the wrapper seams, filters the two `Set-Content` mocks by parameter so that the projection write is distinguishable from the other writes, and then asserts three separate index inequalities: the discard index exceeds the threshold index, the projection-write index and the reconciliation index. A test that asserted only that the discard occurred would pass for an implementation that discarded first.

The choice of `coverage\tm873-external-output\coverage.cobertura.xml` as the output path in that test is deliberate and necessary — the predicate reports a subdirectory of the coverage tree as not retained, so the discard branch is the one reached. Without that choice the test would exercise the retention branch and the ordering assertion would never fire.

### Namespace handling

The summary reader resolves every node through a `local-name()` predicate rather than an unprefixed path, which is mandatory because the test-result document's root declares a default namespace and an unprefixed XPath therefore selects nothing. The paired companion test is what makes this provable rather than assumed: it asserts that an unprefixed `//ResultSummary` path over the identical fixture selects exactly zero nodes. That companion is the difference between a test that happens to pass and a test that would catch a regression, because a namespace regression would otherwise surface as a run reporting zero of everything rather than as a failure.

### Test quality

The empty-collection test at lines 174-185 of the summary test file is written with unusual care. It asserts `($null -eq $failedName) | Should -BeFalse`, `($failedName -is [System.Array]) | Should -BeTrue` and `@($failedName).Count | Should -Be 0` without piping the value into `Should`, and the comment explains why: piping an empty collection sends no input at all, which would make an empty result indistinguishable from a null one. The production code backs this with `[string[]]$failedTestName.ToArray()`, so the contract holds.

The negative reconciliation test includes a guard against passing for the wrong reason. It builds an altered projection by string replacement and then asserts `$alteredProjection | Should -Not -BeExactly $projection` before proceeding, so a substitution that matched nothing cannot leave the rest of the test asserting against an unmodified projection.

The document-order test uses package names that are deliberately not in alphabetical order — `Zeta.First`, `Alpha.Second`, `Mid.Third` — so an implementation that sorted its output would fail rather than pass by coincidence. The empty-package test gives the fixture a deliberately non-zero stale `line-rate` attribute so a zero result cannot come from copying the input.

### The splatting conversion

The conversion of `tests/scripts/vscode/Invoke-MSTest.RunSettings.Tests.ps1` to splatting from hashtables declared in `BeforeAll` is the right response to the constraint. The file stood at 496 lines against a 500-line ceiling and carries fourteen call sites across three functions that each gained two mandatory parameters. Adding two arguments at each site in the existing line-continuation style would have breached the ceiling; splatting made the change net two lines. The four hashtables are derived from one another by `Clone()` with only the differing keys overridden, and the comments at lines 27-29 and 40-45 state which sites read which set and why one set does not serve all of them, including the note that no site supplies a parameter both by splat and explicitly, which PowerShell rejects as a binding error.
