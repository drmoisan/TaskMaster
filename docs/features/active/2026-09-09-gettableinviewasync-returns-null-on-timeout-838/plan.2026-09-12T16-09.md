## Coverage denominators, stated once

Two distinct denominators exist for C# coverage in this repository and a figure computed one way is not comparable to a figure computed the other way. Every figure this plan records is produced the same way and is labelled with its denominator:

- **Denominator R (repository-wide, report-only).** The document-level `line-rate` attribute of the raw Cobertura document produced by the coverage collector, over all instrumented modules minus the seven module exclusions coverage.config carries at its lines 14 through 20 minus the test-assembly exclusion P0-T19 derives. No post-processing is applied. This figure is recorded and reported and gates nothing, because no merge-base coverage baseline exists for this feature and a repository-wide blocking threshold therefore cannot be shown satisfiable.
- **Denominator C (changed and added lines, blocking).** The set of lines that the anchored diff reports as added in the two production Write Set files, intersected with the line elements the raw Cobertura document carries for those files. Lines the Cobertura document does not carry are non-executable (braces, comments, declarations, XML documentation) and are excluded from both numerator and denominator. Coverage is the covered count divided by the total count.

**Per-file aggregation rule, applied by every task that reads a Cobertura document.** A partial class contributes several class elements to a Cobertura document, and the async state machine of `GetTableInViewAsync` splits that member across more than one of them. Every per-file figure in this plan is therefore computed as follows: select every class element whose `filename` attribute ends with the target file name; take the union of the `number` attributes of their line elements; for each line number take the maximum `hits` value across all elements that carry it; a line is covered when that maximum is greater than 0. This is the rule scripts/vscode/Invoke-MSTestWithCoverage.Helpers.ps1 applies from its line 159 and is restated here so every reader of the document applies it identically.

Only line coverage is asserted. No branch figure is asserted anywhere in this plan. Acceptance criterion 15 asks for a line figure only.

## Search-gate conventions, fixed once

Every content search in this plan is executed through pwsh with `Select-String`, not through a git search, for three reasons verified against this environment: a git search cannot see a file the plan has created until it is staged; Git Bash rewrites a leading-slash argument into a Windows path before git sees it, so a pattern beginning with a forward slash silently matches nothing; and a git search exits non-zero when it finds nothing, which makes an absence assertion's pass and fail states easy to confuse.

Accordingly:

- Every search gate is phrased as a **count comparison that exits 0 on pass**. The payload computes the occurrence count with `@(Select-String -LiteralPath <file> -SimpleMatch -CaseSensitive -Pattern "<literal>").Count`, prints it as a self-describing `NAME=value` token, and calls a non-zero exit when the count is not the required value. Every search-gate artifact therefore carries `EXIT_CODE: 0` and no `ExpectedExitCode:` field.
- Every search names an explicit file path. No repository-wide search appears in this plan. This is mandatory for the two phrases acceptance criterion 9 names, because both phrases also occur in spec.md inside criterion 9's own text and in this plan: an unscoped search for either can never reach zero.
- `Select-String` matches case-insensitively by default. Every gate passes `-CaseSensitive`.
- `-SimpleMatch` is used wherever the pattern contains a backslash, a parenthesis, a period or a quotation mark, so no escaping is required. Every search gate in this plan that uses a regular expression rather than a fixed literal states its pattern verbatim inside its own task. The gates that do so are P0-T7's criterion-line count, P0-T21's and P4-T15's timed-constructor searches, and P4-T12's null-forgiving-return search. No count of such gates is asserted, because a later revision that converted a fixed-literal gate to a pattern, or a line classification implemented with a string operation rather than a pattern, would falsify a fixed count without changing the rule.
- Every absence gate has a **recorded positive control**: P0-T21 records the present-day occurrence count of each literal in a named carrying file, and a Phase 0 count of zero for any of them halts the run, because a literal that is already absent makes its later zero-hit gate incapable of failing. Every control names a file in the tree and is read through the same file-reading search form as the gate it controls. No control in this plan is an in-payload string.
