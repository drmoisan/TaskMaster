## Executive Summary

The change is well scoped and correctly implemented. Four null-producing exits converge on one return statement; the delivered remedy rethrows on cancellation, wraps the two retry-ceiling routes with the originating exception preserved, and adds a three-line guard immediately before the return that checks the caller's token before it reports a timeout. The null-forgiving suppression is gone and the nullable build passes with warnings as errors, which is the compiler confirming that the guard narrows the local on every path reaching the return. The method signature is byte-identical, so none of the nine binding sites needed an edit.

Zero Blocking findings. One Low finding on duplicated reflective test scaffolding, and three informational observations recorded for accuracy rather than action. The single production caller was independently verified and needs no adaptation.

Two points deserve emphasis because they are the parts a reviewer could accept too easily.

First, the guard is not dead code and its internal ordering is actually pinned. A guard of this shape can be written in either order and a test that merely asserts a `TimeoutException` on the exhausted path cannot tell the two orders apart. `GetTableInViewAsync_AbsorbedDefaultWithOuterTokenCancelled_ThrowsOperationCanceledNotTimeout` reaches the guard with a null local *and* a cancelled outer token, by having the table-read delegate cancel the test-owned source and then throw a type the shared helper absorbs under its non-strict flag. That construction can only produce an `OperationCanceledException` if `token.ThrowIfCancellationRequested()` precedes the timeout throw, so the ordering property is decided by a test rather than asserted in prose. The spec's own amendment record shows the earlier nominated test could not decide it, and the replacement does.

Second, the failure route whose behaviour at the consumer boundary genuinely changes is the cancellation route, not only the timeout route. Before the change, an outer-token cancellation inside the task-cancelled catch assigned null, the null travelled into the column-adder work item, and the resulting null-reference failure reached `QfcDatamodel.FrameBuilding.cs` where the generic clause logged an error and rethrew. After the change the bare `throw;` rethrows a `TaskCanceledException`, which that boundary's narrower clause handles quietly. A cancelled operation therefore stops producing a logged error and a rethrow, and instead takes the quiet path the spec names as intended. This is an improvement and is the documented design, but it is a real behavioural difference at the consumer and not merely a diagnostic one. Per the feature's research record both catch clauses are unreachable in production, because the production deadline-source factory raises neither caught type, so in the production host the only route whose behaviour changes is the absorbed default.

## Correctness Review of the Delivered Remedy

**The four exits, each checked against the delivered code.**

1. Absorbed default. `table` stays null, no catch clause runs, and control reaches line 153. The guard throws. Previously this returned null through `return table!;`. Confirmed at lines 151-157.
2. Cancellation branch of the task-cancelled catch, line 105-108. `if (token.IsCancellationRequested) { throw; }`. A bare rethrow, so the original stack and the original exception instance survive, and no catch clause for the base cancellation type was introduced. Confirmed.
3. Retry-ceiling branch of the task-cancelled catch, line 124. `throw AcquisitionTimeout(counter, timeoutMs, e);`. The caught instance becomes `InnerException`. Confirmed.
4. Retry-ceiling branch of the timeout catch, line 147. Same shape. The inner-exception identity is asserted by reference in the fourth new test, which is what distinguishes a wrapper from a bare rethrow. Confirmed.

The fifth exit, an `OperationCanceledException` raised by the outer token's check inside the shared helper, still escapes uncaught because it does not match the narrower `TaskCanceledException` clause. The pre-existing test that pins that behaviour passes with its file absent from the diff.

**Why the helper returns instead of throwing.** `AcquisitionTimeout` returns a `TimeoutException` that each site throws. The alternative, a void helper that throws, would leave the compiler unable to see that control does not continue, because the does-not-return attribute is unavailable on net48. The consequence would be a definite-assignment or nullable-flow complaint at each site, most likely resolved with another suppression, which is the very construct this change removes. The delivered shape avoids that, and the reason is recorded in the helper's own documentation rather than left for a reader to reconstruct. This is the correct call.

**Why the unsuppressed return compiles.** The guard narrows `Outlook.Table? table` to non-null on every path that reaches line 159, so the conversion to the non-nullable return type is legal without a suppression. The nullable build with warnings as errors reports zero `CS86` error lines, and the artifact records `CORECOMPILE_SKIPPED=0`, so that gate actually compiled rather than returning a warm up-to-date exit. This is the empirical form of the claim, not an inference from reading.

## Test Quality Review

The five new tests are the strongest part of the change. Each states its scenario in a doc comment that also explains why the construction is the one chosen, which is the difference between a test a maintainer can safely modify and one they cannot. Three specific qualities are worth naming.

The determinism technique is sound rather than merely compliant. Injecting a factory that returns a fresh, already-cancelled source makes the work item cancel before dispatch, so no outcome depends on the scheduler and nothing waits on elapsed time. A fresh instance per invocation is required, not stylistic: the shared helper disposes each source at the end of each attempt, so a reused instance would make the second attempt read a token on a disposed source and raise a different exception entirely. The delivered factories all construct a new source per call.

The regression test asserts more than the exception. `factoryInvocations.Should().Be(2)` and `tableReadInvocations.Should().Be(0)` together establish that both attempts were internal to the shared helper and that neither of the method's own recursive retries ran, which is the property that identifies the defect's actual mechanism. A test asserting only the thrown type would pass against a wrong-mechanism implementation.

The fail-before record is genuine RED-first evidence, not a reconstruction. The recorded failure message is an assertion failure reading `no exception was thrown`, the artifact explicitly checked that the message names no compiler error code, and the same test passes after the production fix with the test file unchanged between the two runs. That pairing rules out the common false positive in which the red state is a compile failure.

One observation on the reflective helper, unrelated to the Low finding above: `method.Invoke(null, args)` returns `object?` and the code calls `.Should().BeAssignableTo<Task>()` before casting, so a signature drift fails on a clear assertion rather than a cast exception. `task.GetType().GetProperty("Result").GetValue(task)` is only reached after `await task` has already surfaced any fault, so the ordering is correct.
