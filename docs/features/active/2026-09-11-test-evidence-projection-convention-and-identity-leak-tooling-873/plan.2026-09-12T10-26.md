## Standing Rules for This Plan

**Fail-closed evidence rule.** Every command-bearing task writes one evidence artifact carrying `Timestamp:`, `Command:`, `EXIT_CODE:` and `Output Summary:`. A baseline artifact additionally carries the numeric values its later comparison consumes. A missing or field-incomplete artifact means the task's checkbox stays unchecked and the verdict is BLOCKED, never PASS.

**Evidence location.** Every artifact resolves under `docs/features/active/2026-09-11-test-evidence-projection-convention-and-identity-leak-tooling-873/evidence/` with the sub-kind `baseline`, `regression-testing`, `qa-gates`, `issue-updates`, `other` or `remediation-baseline`. There is no coverage kind. No artifact is written under the repository orchestration artifacts tree.

**Base anchor.** Phase 0 task T3 records a base commit and publishes it as the local ref `refs/base-anchor-873`. Every diff in this plan uses that ref as an explicit operand. No task may substitute an unanchored diff, and no task may re-derive the base from a shell variable set by a different task.

**PowerShell toolchain order.** Format, then analyze, then test, via `mcp__drm-copilot__run_poshqc_format`, `mcp__drm-copilot__run_poshqc_analyze` and `mcp__drm-copilot__run_poshqc_test`. Editor task wrappers are not substituted. Because those three MCP tools return only an ok flag and a prose summary and carry no counts, each is paired unconditionally with a direct PowerShell run that supplies the numbers. The pairing is unconditional and is never expressed as a fallback.

**Scan scope, named once.** The two script folders are the editor script directory scripts/vscode and its mirror test directory tests/scripts/vscode, named here without backticks because this delivery does not own every file in either folder. Every scan_folders argument in this plan is exactly that pair. The test folder is tests/scripts/vscode, and every direct Pester run this plan describes as covering the test folder runs over exactly that folder, so the Phase 7 analyzer diagnostic-set comparison and the Phase 7 passed-count comparison read the same population as their Phase 0 baselines.

**Formatter restore rule (a rule, not a list).** `mcp__drm-copilot__run_poshqc_format` takes folders, so it rewrites files this delivery does not own, including a part file under the editor script directory that a concurrent item owns. After every format invocation the executor runs a porcelain status limited to the two script folders, and for every reported path that is not named as a backticked repository-relative path somewhere in this plan, runs `git checkout --` on that path and re-runs the porcelain status to confirm the path is no longer reported. Both status outputs go into the task's artifact. A format invocation that rewrites a path this plan does own does not by itself restart the toolchain loop, because the analyze and test steps that follow in the same task run against the formatted tree; a failure of the analyze or the test step does restart the loop from format.

**PowerShell analyzer gate shape.** `mcp__drm-copilot__run_poshqc_analyze` exits 1 on any Warning and `scripts/vscode/Invoke-MSTestWithCoverage.Helpers.ps1` already carries an unsuppressed plural-noun warning, so a baseline exit code of 1 is legitimate and an absolute exit-zero demand is unsatisfiable. Every analyzer gate in this plan is a diagnostic-set comparison against the Phase 0 baseline artifact, never an exit code.

**New PowerShell file conventions.** Every `.ps1` file this plan creates is written with a UTF-8 byte-order mark, begins with `Set-StrictMode -Version Latest`, uses advanced functions with `[CmdletBinding()]`, and uses singular nouns so no new plural-noun analyzer diagnostic is introduced.

**C# toolchain invocation.** MSBuild is not on the path in an agent worktree and the repository build wrapper unconditionally runs a package-reference synchroniser that rewrites the hint paths of every project file in the tree. That synchroniser would edit project files outside this delivery's footprint, so this plan resolves MSBuild through vswhere and passes the argument list from `CLAUDE.md` directly. The C# format step runs in verify mode rather than write mode: this delivery changes no C# source file, the repository formatter ignore file already excludes project files from the formatting check, and verify mode exits non-zero on drift so its exit code is a real discriminating observation.

**Command invocation form.** The repository Bash allow list grants only git, pwsh, poetry run and three library shell scripts, and every chained segment of a command line is matched independently. Every dotnet and msbuild command this plan quotes is therefore issued as a single `pwsh -NoProfile -Command` segment whose body carries the quoted command text, with the worktree root supplied by a `Set-Location` inside that same body rather than by a separate directory-change segment. No command line in this plan uses a shell-level command substitution, a shell-level pipeline whose later segment is neither git nor pwsh, or grep, sed, cat, find or wc. A pipeline written inside a `pwsh -NoProfile -Command` body is not a shell-level pipeline: the whole body is one quoted argument, so the allow list matches a single `pwsh` segment. No command in this plan assumes a Python toolchain; this repository has none.

**Baseline-relative C# gates.** The solution-wide analyzer and nullable passes are rebuilds of the whole solution and may be non-green before this delivery starts. Every C# gate in this plan compares the recorded exit code, error count and warning count against the Phase 0 baseline artifact for the same command. That is the operative reading of AC15's "no NEW diagnostics" and it is applied to AC22's msbuild clause as well; Phase 0 task T17 verifies that the spec already records that reading, and amends the criterion only in the contingency that it does not, which is not the expected outcome, so the two criteria cannot be read as demanding an absolute zero that no task in this plan can produce.

**Footprint declaration correction.** Two test files are forced to change by this delivery rather than chosen, and Phase 0 task T16 verifies that the spec's Write Set already lists both and records why each is forced. `tests/scripts/vscode/Invoke-MSTest.Main.Tests.ps1` pins the complete four-element array that `Invoke-MSTestMain` hands to the vstest wrapper seam, which becomes a six-element array once the plain builder gains the two switches. `tests/scripts/vscode/Invoke-MSTestWithCoverage.AssemblyDiscovery.Tests.ps1` declares an explicit five-parameter mock body for `Invoke-DotnetCoverageCollection`, which stops binding once that function gains two parameters. Leaving either unrepaired makes AC22's zero-failed-tests clause unsatisfiable.

**Batching.** The PowerShell change budget caps a batch at three production files and three test files. It is enforced by the editor batch-budget hook, which accumulates distinct PowerShell paths for the whole session in a state file under the editor state directory and denies the fourth distinct file of either kind until that state file is deleted. Phases 1 through 4 are the batches, so the first task of Phases 2, 3 and 4 opens its batch by deleting every batch-budget state file for this worktree before it makes any edit. Phase 1 opens on a clean state file set and needs no reset. Phase 1 touches two production files and one test file. Phase 2 touches one and one. Phase 3 touches one production file and three test files. Phase 4 touches one production file and three test files. Phase 5 touches no PowerShell file. The first task of Phase 7 performs the same reset for a fifth time, because the hook accumulates for the whole session rather than per phase and Phase 4's accumulated state would otherwise still be in force through Phases 5, 6 and 7, denying any Phase 7 remediation edit that reached a fourth distinct file of either kind. Every one of those four reset tasks excludes the file named `powershell-batch-budget.default.json` from both the deletion clause and the count clause, for the reason each of them states. The shared argument-builder test file is repaired in the same phase as each builder signature change that breaks it, so no phase gate runs a test path the same phase has just broken.

**Out of scope, stated without path tokens.** The branch-coverage threshold part file under the editor script directory and the test file that covers it belong to a concurrent item and are not written or extended here. The repository ignore file is not changed; the results directory is placed beneath an already-ignored tree precisely so that no ignore-file change is needed. The editor-agent settings document, the editor-agent rules, skills, agents, hooks and library trees, the blast-radius configuration and the orchestration-routing configuration are push-down owned and none is written by this delivery. The historical sweep over already-tracked raw evidence documents across every feature folder is issue #602 and runs after this item; no already-tracked raw document is deleted here.

**Phase 6 flakiness attribution.** Each of the two Phase 6 runs invokes the coverage entry point over the whole solution's test assemblies, and that entry point throws on any nonzero test-console exit code before it reaches the projection write, so a single failing test anywhere in the solution prevents both runs from producing the artifacts Phase 6 observes. This repository has documented suites that hang or fail on assembly load under coverage on a local machine while passing in continuous integration. A Phase 6 failure whose cause is a pre-existing flaky or hanging test is not a failure of this delivery. On such a failure the executor records the failing or hanging test's identity, the assembly it belongs to and the observed symptom in the phase's evidence artifact, and reports, rather than modifying any test outside the Write Set to make the run green. Modifying a test outside the Write Set is prohibited here for two reasons: it would change the delivery's declared footprint, which Phase 0 task T16 verifies and the Phase 7 inventory gate enforces, and it would suppress a pre-existing defect that belongs to a separate item rather than fixing anything this delivery introduced.

**Fixed design values, so the executor selects no evidence of its own.**

- Results directory default on both entry points: the parameter default text is the single-quoted literal `coverage\test-results`, resolved against the repository root.
- Log file name on the plain entry point: `mstest-run.trx`. On the coverage entry point: `mstest-coverage-run.trx`.
- Projection output path: the coverage output file's directory joined with the coverage output file name without its extension plus the suffix `.jacoco.xml`.
- Test-result summary output path: the results directory joined with the log file name without its extension plus the suffix `.summary.txt`.
- Retention predicate: `Test-RawCoverageDocumentRetained` returns true when the full parent directory of the output path equals the repository root joined with `coverage`, compared case-insensitively with a trailing separator trimmed, and false otherwise.
- Reused error wording: the literal thrown for a missing packages node is the wording the first-party helper already throws; no second wording is introduced. The single-line phrase used to enumerate the distinct wordings is `does not contain a`.
- New `CLAUDE.md` section heading, authored by this plan: `## Committed Test Evidence Format`.
- New `CLAUDE.md` toolchain switch literals, authored by this plan: `/ResultsDirectory:` and `/Logger:trx;LogFileName=`.
