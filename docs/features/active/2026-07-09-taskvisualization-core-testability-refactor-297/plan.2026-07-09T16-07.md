## Canonical C# Toolchain (run in this exact order)

1. `dotnet tool run csharpier .`
2. `msbuild TaskMaster.sln /t:Build /p:Configuration=Debug /p:Platform="Any CPU" /p:EnableNETAnalyzers=true /p:EnforceCodeStyleInBuild=true`
3. `msbuild TaskMaster.sln /t:Build /p:Configuration=Debug /p:Platform="Any CPU" /p:Nullable=enable /p:TreatWarningsAsErrors=true`
4. `vstest.console.exe TaskVisualization.Test\bin\Debug\TaskVisualization.Test.dll /EnableCodeCoverage`

If any step fails or changes files, restart from step 1. Each implementation task below is complete only when steps 1–4 pass in a single pass (the "full toolchain gate") and the step summaries are appended to `<FEATURE>/evidence/qa-gates/`.

## Behavior-Preservation and Compile-Safety Rules

- This is a structure-only refactor. Method names, event routing, dialog outcomes, keyboard-accelerator behavior, and control state transitions are preserved exactly.
- The decomposition is sequenced in compile-safe increments: every task leaves the full solution building. Semantic retargeting (Phase 3) precedes mechanical partial-class splitting (Phase 4).
- The sole constructing caller `TaskVisualization/FlagTasks.cs` receives zero edits. All new seam parameters (`ITagPromptService`, `Action<string>` notifier, `Func<MailItem, Task<MailItemHelper>>` factory) are optional-with-default with production defaults so `FlagTasks.cs` compiles and behaves unchanged.

## Notes

- `user-story.md` is intentionally absent for this refactor child per the epic's Design-Phase Deliverables; acceptance criteria are carried by `issue.md` and `spec.md`.
- No new production dependencies are introduced. Only already-referenced libraries are used.
- Sibling #298 reuses `ITagPromptService`; it is defined in `TaskVisualization` (P1-T4) so #298 consumes rather than duplicates it.
- Proposed (NOT implemented in this plan; flagged for later maintainer decision): graceful handling of non-integer/empty/whitespace `Duration` input in `CaptureDuration`. Current behavior propagates an uncaught `FormatException` from `int.Parse` for such input, and the `catch (InvalidCastException)` branch is dead (`int.Parse` throws `FormatException`/`OverflowException`, never `InvalidCastException`), so its user-facing "Could not convert to integer" message is never shown. A future change could catch `FormatException` and surface that message via the notifier instead of propagating — the behavior the dead branch appears to have intended. This plan preserves current behavior exactly (throw-on-non-integer) and does not implement this change; it is recorded here as a non-implemented proposal for the maintainer to decide separately.
