## STA Last-Resort Coverage of Control-Identity Regions (maintainer-ratified refinement)

Per the epic Shared Design Pattern item 4 refinement (2026-07-09, last-resort STA controls), the two control-identity partials (`TaskController.ControlMaps.cs` and `TaskController.Accelerator.cs`) are NOT blanket file-level exempt. Their control-identity logic is measured by dedicated STA-bound tests that construct real, never-shown, in-memory WinForms controls; only the residue that genuinely requires a live window handle or the message pump stays exempt at line/method level. The refinement conditions bind this plan:

- **(a) Seam-first, and why no logic-isolating seam is feasible.** A seam (interface > delegate > adapter) remains the first approach and is used wherever it isolates logic (the primitive `ITaskViewer` facade, `ITagPromptService`, the notifier, and the `MailItemHelper` factory). For the control-map/accelerator regions no seam can ISOLATE the logic from real controls: `TipsController` throws without a real parented `TableLayoutPanel`/`Panel`; the lookup dictionaries key on control object-identity; `.Visible`/`.BackColor`/`Button.PerformClick` require real `Control` instances. A mock/stub of those members would either throw or not exercise the identity semantics under test. The control-identity surface is therefore isolated on a dedicated companion interface `ITaskViewerControls` (typed as real `Label`/`Control`, not primitives) whose sole purpose is to let the STA tests supply REAL in-memory controls — it removes the `Form`-type dependency only, not the real-control dependency, so STA remains unavoidable. Each STA test records this rationale (satisfying condition (a)).
- **(b) Dedicated STA files, minimal surface.** All STA-bound tests live in dedicated files with suffix `*.StaTests.cs` (`TaskControllerControlMaps.StaTests.cs`, `TaskControllerAccelerator.StaTests.cs`) using `[STATestClass]`/`[STATestMethod]`. The primitive-facade controller tests (Phase 6, `Mock<ITaskViewer>`) stay in their non-STA files. The STA surface is limited to the control-identity logic that cannot be seamed.
- **(c) No pump, no popups, dispose per test.** STA tests never call `Show()`/`ShowDialog()`; they assert no message-pump round-trips (no `PostMessage` round-trip assertions, no `DoEvents`, no timers). Because an unshown control's `.Visible` getter is parent-dependent, STA assertions target reliable state (`.BackColor`, `.Text`, `.Checked`, the returned state tuples/dictionaries, and `Button.PerformClick` side effects) rather than the `.Visible` getter. Every control constructed in a test is disposed in that test (try/finally or `[TestCleanup]`).
- **(d) No Form-derived types.** No test constructs `TaskViewer` or any `Form`-derived type, even unshown. The STA tests construct only leaf/container controls (`Label`, `Panel`, `TableLayoutPanel`, `Button`, `CheckBox`) and supply them through `ITaskViewerControls` (via `Mock<ITaskViewerControls>` returning the real controls, or a non-`Form` fake).

### MSTest STA mechanics (verified)

The test project uses MSTest 4.2.2 (`MSTest.TestFramework`/`MSTest.TestAdapter` 4.2.2, `MSTest.Analyzers` 4.2.2 per `TaskVisualization.Test/packages.config`). `[STATestClass]`/`[STATestMethod]` (`Microsoft.VisualStudio.TestTools.UnitTesting`) are present in this MSTest version and are already used in-repo (for example `UtilitiesCS.Test/HelperClasses/WindowsForms/WinFormsLayoutTests.cs`), with global STA intentionally disabled via `UtilitiesCS.Test/test.runsettings` so only opt-in classes/methods run STA. This plan uses the per-class/per-method attributes (no assembly-wide apartment change). Fallback (not required here, recorded for completeness): if the attributes were unavailable, an assembly-scoped `.runsettings` with `<RunConfiguration><ExecutionThreadApartmentState>STA</ExecutionThreadApartmentState></RunConfiguration>` would force STA for the whole `TaskVisualization.Test` assembly; the tradeoff is that it removes the non-STA suite from the default (parallelizable) threading model, which is why the attribute-scoped approach is preferred.

## Notes

- `user-story.md` is intentionally absent for this refactor child per the epic's Design-Phase Deliverables; acceptance criteria are carried by `issue.md` and `spec.md`.
- **STA last-resort refinement (v1.1).** This revision applies the maintainer-ratified refinement (epic Shared Design Pattern item 4, 2026-07-09). The two control-identity partials (`TaskController.ControlMaps.cs`, `TaskController.Accelerator.cs`) are no longer file-level exempt: their control-identity logic is measured by dedicated `*.StaTests.cs` files (`[STATestClass]`/`[STATestMethod]`, MSTest 4.2.2) that construct real never-shown in-memory controls, supplied to the controller through the new `ITaskViewerControls` companion surface (P1-T2). A seam is used first everywhere it isolates logic; STA is used only where the control identity IS the logic and no logic-isolating seam exists, and each STA test records that rationale (condition a). Remaining exempt residue is method/branch-level with a named handle/pump/focus dependency (condition c). No test constructs a `Form`-derived type even unshown (condition d).
- No new production dependencies are introduced. Only already-referenced libraries are used. `ITaskViewerControls` is a new first-party interface, not a package dependency.
- Sibling #298 reuses `ITagPromptService`; it is defined in `TaskVisualization` (P1-T5) so #298 consumes rather than duplicates it.
- Proposed (NOT implemented in this plan; flagged for later maintainer decision): graceful handling of non-integer/empty/whitespace `Duration` input in `CaptureDuration`. Current behavior propagates an uncaught `FormatException` from `int.Parse` for such input, and the `catch (InvalidCastException)` branch is dead (`int.Parse` throws `FormatException`/`OverflowException`, never `InvalidCastException`), so its user-facing "Could not convert to integer" message is never shown. A future change could catch `FormatException` and surface that message via the notifier instead of propagating — the behavior the dead branch appears to have intended. This plan preserves current behavior exactly (throw-on-non-integer) and does not implement this change; it is recorded here as a non-implemented proposal for the maintainer to decide separately.
