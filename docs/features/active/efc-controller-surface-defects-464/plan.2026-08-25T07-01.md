## Fail-closed rules

- **Evidence rule.** Every command-bearing task writes an artifact under
  `docs/features/active/efc-controller-surface-defects-464/evidence/<kind>/`, where the canonical
  singular `<kind>` is one of `baseline`, `regression-testing`, `qa-gates`, `other`. Each command-step
  artifact records `Timestamp:`, `Command:`, `EXIT_CODE:`, and `Output Summary:`. A task with a missing
  or field-incomplete artifact stays unchecked. Paths under `artifacts/baseline/`,
  `artifacts/baselines/`, `artifacts/qa/`, `artifacts/qa-gates/`, `artifacts/coverage/`,
  `artifacts/regression-testing/`, and `artifacts/evidence/` are forbidden and must not be used by any
  task in this plan.
- **No-SKIPPED rule.** Every command task in this plan executes its stated command. `EXIT_CODE: SKIPPED`
  is not a passing outcome for any task here.
- **Expect-fail rule.** A task tagged `[expect-fail]` must record a non-zero `EXIT_CODE:` together with
  `ExpectedExitCode: 1` and the named failing test results. A task tagged `[expect-fail]` that records a
  pass is a failure of that task.
- **Non-vacuity rule.** Every task that runs `vstest.console.exe` must record a **non-zero** total
  executed count and enumerate the distinct test result names it observed. A run that discovers zero
  tests is a failure of that task, never a pass.
- **Baseline-comparison rule.** No task in this plan asserts an absolute analyzer-diagnostic count, an
  absolute warning count, or an absolute repository test count. Every such gate compares against the
  Phase 0 baseline figures recorded in `[P0-T10]`, `[P0-T11]`, and `[P0-T12]`.

### C3 — Test policy

MSTest, Moq, and FluentAssertions only. These prohibitions are hard, not advisory, in every test file
this plan writes:

- The token `Thread.Sleep` must not appear.
- The token `Task.Delay` must not appear.
- No temporary file of any kind (CLAUDE.md §UT4; currently approved exceptions: none).
- No live Outlook, no COM interop against a running host.
- No `BackgroundWorker`, no message loop, no started thread whose completion is awaited by polling.
- No test fixture class may derive from `System.Windows.Forms.Form`
  (`QuickFiler.Test/NoLiveFormInTestAssemblyTests.cs:17-36` asserts this over the whole test assembly).
- No test calls `Show()`, `CreateControl()`, or reads `Handle` on any `Form`-derived instance.
- The only timer test arms with `Timeout.Infinite` for both due time and period and observes disposal
  through `ObjectDisposedException` from `Timer.Change`; it never waits.

Two authorised headless construction seams, both already used in `QuickFiler.Test`:

1. `System.Runtime.Serialization.FormatterServices.GetUninitializedObject` — used in 26
   `QuickFiler.Test` files. It runs **no** constructor, so an `EfcViewer` produced this way has no
   window handle, no controls, and no message pump. It is the seam for the `EfcFormController`
   defect tests that must get past a `_formViewer` null guard.
2. A real headless `QuickFiler.ItemViewer` (a `UserControl`, not a `Form`), constructed and never
   shown, with `SynchronizationContext` saved and restored in `finally`. Precedent:
   `QuickFiler.Test/Controllers/QfcItemController.EventWiringTests.cs:229-309`.

### C4 — Two verified runtime facts this plan depends on

1. **`await` on a null `SynchronizationContext` throws `ArgumentNullException`.** The awaiter extension
   is `UtilitiesCS/Threading/UiThread.cs:108-111`, and `SynchronizationContextAwaiter`'s constructor
   (`UiThread.cs:91-98`) throws `ArgumentNullException` when the context is null. This resolves the
   assumption `spec.md` §`Assumptions, Constraints, Dependencies` marks UNVERIFIED and requires the
   plan to verify. `[P0-T17]` records it as evidence before any test relies on it. The consequence is
   that `await _formViewer.UiSyncContext` on an all-fields-null controller faults deterministically,
   which is the fault injection every RC3 boundary test uses. The converse also follows and is relied on
   by `[P7-T4]`: **given any non-null `SynchronizationContext`, the same await completes**, because the
   constructor's only guard is the null check. `EfcViewer.UiSyncContext` (`EfcViewer.cs:37-40`) is an
   ordinary getter over the private field `_context` (`:36`), so injecting `new SynchronizationContext()`
   into that field through the `SetPrivateField` helper at `EfcFormControllerTests.cs:159-166` makes an
   awaited UI-thread marshal runnable headlessly against an uninitialized concrete `EfcViewer`. Nothing
   is shown, no handle is created, and no message pump is required: the default
   `SynchronizationContext.Post` queues the continuation to the thread pool.
2. **`Dispatcher.InvokeAsync` cannot be awaited headlessly.** `ItemViewer.UiDispatcher`
   (`QuickFiler/Viewers/ItemViewer.cs:72`) is a WPF `System.Windows.Threading.Dispatcher`. On the
   dispatcher's own thread `InvokeAsync` queues the delegate rather than running it inline, so an
   `await` of it never completes without a running message loop, which C3 prohibits. Therefore no test
   in this plan awaits `EfcItemController.ToggleExpansionAsync(Enums.ToggleState)`; the dispatched
   bodies `ToggleExpansionOn` and `ToggleExpansionOff` are invoked directly instead, and `[P1-T15]`
   records the dossier for that substitution.

## Decisions Record

- **D1 — Toolchain gate commands are the CLAUDE.md commands verbatim, with `/t:Rebuild`.** Both msbuild
  gate tasks use `/t:Rebuild`. A warm `/t:Build` skips `CoreCompile` on every project, so the analyzer
  and nullable gates could not fail.
- **D2 — `/p:Nullable=enable` is never added.** Nullable enforcement in this repository is per-file
  opt-in through `#nullable enable`. The nullable gate command is character-for-character CI's.
- **D3 — Intermediate builds are not gates.** A task that only needs a fresh `QuickFiler.Test.dll` in
  order to run a scoped test uses `/t:Build` against `QuickFiler.Test\QuickFiler.Test.csproj`. Such a
  task is never cited as an analyzer or nullable gate and its artifact says so.
- **D4 — MSBuild and vstest are invoked from PowerShell with absolute paths** resolved in `[P0-T4]`.
  Neither `msbuild` nor `vstest.console.exe` nor `vswhere.exe` is on `PATH` in this environment, and a
  bash shell mangles the parallel-build switch into a drive-letter path.
- **D5 — CSharpier 1.2.6 requires a subcommand.** `dotnet tool run csharpier format` and
  `dotnet tool run csharpier check`. `dotnet tool restore` runs once, in `[P0-T8]`, before any
  csharpier invocation. The bare-path form and `pipe-files` are not enforcement commands.
- **D6 — The mutating format pass is scope-locked.** `[P10-T1]` runs `csharpier format` against the
  explicit owned file paths, never a repository-wide `.` argument. The repository-wide read-only
  `csharpier check .` remains the gate in `[P10-T3]`, compared against the baseline unformatted set
  recorded in `[P0-T9]`.
- **D7 — Every `vstest` run writes its TRX into its own results directory** named for the task
  (`p#-t#`), so a later run can never make an earlier TRX ambiguous.
- **D8 — Compile-enabling seam introduction precedes the failing-test observation.** A regression test
  cannot compile before the member it names exists. For each such member the plan introduces it first in
  a **defect-preserving** form that changes no behaviour, builds and observes the test failing, and only
  then corrects the defect. Both artifacts are recorded, so the fail-before evidence stays auditable.
  This applies to `IncognitoArgument`, `ClaimsAltChord`, `WithTrashRow`, `ApplyDeleteGesture`,
  `IsBannerRow`, `IsSelectableFolder`, `ThrowInitializationFailure`, and the five RC3-B boundary members.

  **`MatchesForSearchText` is deliberately excluded from that list, and its exclusion is the reason
  `[P7-T14]` exists.** It is a new pure helper with no pre-change counterpart, and the RC8 defect it
  accompanies is a *relocation* of a control read, not a change of value: after `[P7-T1]` the data model
  receives exactly the same string it received before, so a defect-preserving introduction would produce
  a test that passes both before and after and would gate nothing. RC8 is therefore discharged by a
  structural fail-before pair — the sign of the `_formViewer`-to-`Task.Run(` line offset recorded in
  `[P7-T13]` — together with the exception dossier `[P7-T14]` writes. Every other extracted helper with a pre-change
  counterpart is on the defect-preserving list above; `BindSourceFolderRows` is a new routing method
  introduced by the corrective task itself, `[P7-T7]`, whose fail-before evidence is `[P7-T5]`. No task
  in this plan introduces `BindSourceFolderRows` in a defect-preserving form, and none is required to.
- **D9 — `[DataRow]` rows count as individual named tests.** Where `spec.md` says "a named test per
  handler", a `[DataTestMethod]` with one `[DataRow]` per handler satisfies it: MSTest reports each row
  as a distinct result with its own name and outcome in the TRX. The executor enumerates the distinct
  result names in the evidence artifact.
- **D10 — The logged boundary is observed through an injectable sink, not through log4net.**
  `QuickFiler.Test/QuickFiler.Test.csproj` carries **no** `log4net` reference (verified while authoring
  and confirmed independently at preflight: the file's `Reference Include` list contains no log4net
  entry, and the only occurrence of the token under `QuickFiler.Test/` is a binding redirect at
  `QuickFiler.Test/app.config:78`, which is a runtime assembly-resolution hint and not a compile-time
  reference), and C1 forbids adding one, so a test
  in that assembly cannot attach a log4net appender or assert on `log4net.ILog`. This plan therefore
  adds `internal System.Action<string, System.Exception> BoundaryErrorSink { get; set; }` to
  `EfcFormController`, defaulted to a delegate that calls `logger.Error(message, exception)` on the
  pre-existing static logger at `EfcFormController.cs:123`. Every RC3 boundary calls the sink; a test
  injects a counting delegate and asserts exactly one invocation. `[P6-T15]` records, by source
  inspection, that the default sink is `logger.Error(message, exception)` and nothing else. The
  `spec.md` criterion was amended at preflight round 1 to name this instrument explicitly — it now
  requires "exactly one invocation of the controller's boundary error sink, whose default delegate is
  verified by source inspection to be exactly one `logger.Error(message, exception)` call on the
  pre-existing static logger" — so `[P6-T15]` is the source inspection the criterion itself calls for,
  not an undeclared workaround. `[P11-T15]` still records the sink as a recorded deviation from the
  criterion's original wording, so the substitution stays visible rather than concealed.
- **D11 — RC9 separates retention from presentation.** The supporting facts, stated exactly:
  pre-change `_folderRows` is **assigned in two places** — its declaration initializer at
  `EfcFormController.cs:134` (`= Array.Empty<string>()`) and the write-back inside `BindFolderRows` at
  `:879` — and is **read in two places** — `ActionDeleteAsync` at `:745` and `BindFolderRows` itself at
  `:880`, where the value the write-back has just stored is handed to `BindBreadcrumbRowsAsync`. So
  `:879` is not the only assignment and `:745` is not the sole read; the conclusion below nevertheless
  stands, because `:879` is the only assignment **in a method body**, and it is the one that makes the
  field accumulate presentation state.

  After the change `BindFolderRows` neither assigns nor reads `_folderRows`: the `:879` write-back is
  deleted and the `:880` read becomes the method's own `rows` parameter, so the method only guards and
  binds what it was handed. The three source call sites (`:556`, `:803`, `:1035`) route through a new
  `BindSourceFolderRows`, which retains the fresh suggestion rows and then binds; the delete gesture
  routes through a new `ApplyDeleteGesture`, which applies the idempotent `WithTrashRow` and then binds.
  `_folderRows` therefore keeps exactly the meaning it has today and the trash row can no longer
  accumulate. `ApplyDeleteGesture` assigns `_folderRows` before the viewer guard, which is the one
  deliberate micro-difference from today's ordering and is what makes the accumulation observable
  headlessly: with `_router` left null the guard at `:874-877` returns early, yet the assignment has
  already happened.
- **D12 — RC7 adds a second pure helper.** `IsBannerRow` is the single classification owner, and
  `IsSelectableFolder(string)` carries the rest of `IsValidSelection`'s pure logic so that a test can
  put the same input through both classification paths without constructing a `BreadcrumbBridgeRouter`
  and driving a selection through it. `IsValidSelection` becomes
  `IsSelectableFolder(SelectedFolder)` and `ActionOkAsync`'s guard calls `IsBannerRow`, so both sites
  classify through `IsBannerRow` as the criterion requires.
- **D13 — One acceptance criterion per check-off task.** Each check-off task flips exactly one `spec.md`
  checkbox and cites exactly one evidence artifact.
- **D14 — `.claude/agent-memory/**` is excluded from every diff and clean-tree gate.** It is
  agent-session state, not feature output, and it is tracked, so an unscoped gate would be
  unsatisfiable.
