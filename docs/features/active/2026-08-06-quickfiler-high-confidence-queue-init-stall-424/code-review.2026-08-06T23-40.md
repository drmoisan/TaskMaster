## Design Notes (non-findings)

- **Deadline placement.** Checking the deadline at loop top (after the cancellation check, before `_tryTakeNext`) while letting an in-flight score complete gives the pinned include-final-accept semantics with no task abandonment; the returned partial batch reuses the existing exhaustion result shape, so no caller needs new handling. This is the simplest design that satisfies the AC set.
- **Mapper extraction.** Placing the band mapping in `QfcScanProgressBandMapper` rather than inline in `RunAsync` is the correct response to the coverage boundary (`QfcDatamodel` excluded, controller COM/WinForms-dominated): the decision logic gets a 100 percent-coverage home, and the controller change is four statements. The `Action<double, string>` sink type binding directly to `ProgressTracker.Report` by method-group conversion avoids any UI or threading coupling.
- **Liveness flag.** Clearing the flag in a `finally` around the awaited `RemainingEmailLoader` in `Worker_DoWork` (rather than inside `LoadRemainingEmailsToQueueAsync`) is a recorded, reasoned deviation (plan Decisions item 3) that keeps the transition observable through the loader seam; the throwing-path test proves the `finally` guarantee. `volatile` is appropriate for the single-writer/multi-reader bool.
- **Test splits.** The 500-line-driven splits are thematic (deadline vs progress vs liveness), each with in-file documentation of the partial-class/`[TestClass]` constraint, matching the repo's established `.Part2.cs` and helper-duplication conventions.
