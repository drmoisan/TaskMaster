## The Directional Constraint (read before writing any code)

The issue's Expected Behavior reads as though the three-character and four-character banner prefixes should be unified upward to four characters. **That reading is wrong and would be a behavioural regression. This plan prohibits it.**

The mechanism, verified against the current tree in this authoring pass:

- `QuickFiler/Controllers/EfcSelectionGuard.cs:15` declares `private const string BannerPrefix = "===";` — three characters.
- `QuickFiler/Controllers/EfcFormController.cs:1146` classifies banner rows through `UtilitiesCS.OutlookObjects.Folder.BreadcrumbRowBuilder.BannerPrefix`, which is `"===="` (`UtilitiesCS/OutlookObjects/Folder/BreadcrumbRowBuilder.cs:19`). `IsBannerRow("===")` is therefore false.
- `EfcSelectionGuard.IsValidCreationSelection` (`EfcSelectionGuard.cs:66-77`) tests `value.Length >= MinimumCreationLength` where `MinimumCreationLength = 3` (`:22`). For the input `"==="` that comparison is `3 >= 3`, which is true, so the length rule rejects nothing.
- The three-character prefix at `:49` and `:75` is therefore the **only** mechanism rejecting a three-equals row at either EFC classification site.

Widening the guard constant to the producers' four-character value makes `IsValidFilingSelection("===")` and `IsSelectableFolder("===")` both return true and fails `QuickFiler.Test/Controllers/EfcFormControllerTests.cs:463` (`creationPath.Should().BeFalse(...)`). The sibling assertion on `:462`, which reads like the consistency guard, still passes under that edit, so the relaxation would not be caught by the assertion a reader would expect to catch it.

**Mandated direction:** the guard's constant keeps the value `"==="` exactly. Only its name and its XML documentation change. Any edit that alters that value, or that widens either `StartsWith` comparison, is out of scope and must be reverted.

- **D1 — Deletion, not aliasing, in `FolderSuggestionTree.cs`.** An aliasing declaration of the form `private const string BannerPrefix = BreadcrumbRowBuilder.BannerPrefix;` would still match AC2's declaration regex and would make AC2's expected count two instead of one. The declaration at `:16` is therefore deleted outright.
- **D2 — Relative namespace qualification, no new `using` directive.** `FolderSuggestionTree` is declared in `namespace UtilitiesCS` (`FolderSuggestionTree.cs:5`) and `BreadcrumbRowBuilder` in `namespace UtilitiesCS.OutlookObjects.Folder` (`BreadcrumbRowBuilder.cs:5`), so the reader at `:197` uses `OutlookObjects.Folder.BreadcrumbRowBuilder.BannerPrefix`. This touches one statement, adds no `using` line, and raises no ambiguity question against the two `using` directives the file already carries (`:2`, `:3`).
- **D3 — No comment in `FolderSuggestionTree.cs` may contain the token `BannerPrefix`.** AC5 asserts that file carries exactly one line matching that identifier. An explanatory comment naming the constant would make the count two and fail AC5. The rationale for the change is recorded in this plan and in the commit message instead.
- **D4 — AC6 and AC7 pass counts are read from the run's TRX `<Counters .../>` element, not from a console-line search.** `vstest.console.exe` pads its summary columns with variable whitespace, so a fixed-string search for a console figure is whitespace-sensitive and would not reliably match. The TRX `<Counters .../>` element is emitted on a single line with `passed="N"` and `failed="N"` attributes. The figures asserted are the same figures the acceptance criteria name.
- **D5 — Every occurrence assertion is scoped with the pathspec `-- '*.cs'` and anchored on the closing quote and semicolon.** The three-character literal is a prefix of the four-character literal, so an unanchored search for the shorter one also matches every longer declaration. The unscoped file count is scope-dependent and grows as this feature's own documents are authored; no unscoped figure is asserted anywhere in this plan.
- **D6 — Every count is derived twice by structurally different queries and the member sets compared,** not only the totals. A fixed-string search and a bounded-repetition regex fail differently, so agreement between them is evidence; agreement between two runs of the same query is not.
- **D7 — CSharpier print width is 100 (repository default; no `.csharpierrc` exists).** The two renamed call-site lines measure 92 characters after the rename and stay on one line, so the AC2 call-site search remains a single-line match. CSharpier does not reflow the contents of comments or string literals, so the XML-doc token and the FluentAssertions `because` token are likewise wrap-safe.
- **D8 — The mutating format pass runs only in Phase 2, after the Phase 0 read-only baseline.** A baseline captured after a formatter has repaired pre-existing drift records a repaired tree rather than the tree the work started from.
- **D9 — Long-running steps.** Each `msbuild /t:Rebuild` over the full solution and each full-suite test or coverage run takes many minutes. Launch them with a generous timeout and capture the transcript; do not abandon a run and record it as failed on a timeout alone.
- **D10 — `/InIsolation` is mandatory on every `vstest.console.exe` invocation.** Omitting it causes each assembly's `app.config` binding redirects to be ignored, producing a large number of phantom failures with empty messages and sub-millisecond durations. That is an assembly-load failure, not a regression.

delimiter suppresses expansion inside the body, and the result of a command substitution is not
expanded again. The concrete shape of that wrapping is the following, with the task's span placed
