## Design decisions locked in by this plan (read before executing)

1. **Evidence paths.** All evidence in this plan resolves to `docs/features/active/2026-06-29-qfc-item-controller-testability-227/evidence/<kind>/`, per `evidence-and-timestamp-conventions`. Baseline artifacts use `evidence/remediation-baseline/`; command-step QA artifacts use `evidence/qa-gates/`; the coverage-delta artifact uses `evidence/regression-testing/`. No `artifacts/baselines/`, `artifacts/qa/`, or `artifacts/coverage/` paths are used anywhere in this plan.
2. **Fix approach: modify the two existing tests in place, add one new test per overload for the untested branch.** `ToggleFocus_StateOverload_MarshalsThroughItemViewerInvoke` and `ToggleFocus_ParameterlessOverload_MarshalsThroughItemViewerInvoke` (`QfcItemController.FocusAndThemeTests.cs:123-151`) are kept (same names, same "On"/inactive-start branch they already exercise) but rewired to use `BuildExecutingViewer()` (lines 99-114) instead of a bare `new Mock<IItemViewer>()`, and extended with state-transition assertions. Two new tests cover the opposite branch of each overload (`Off`-from-active for the state overload; active→inactive for the parameterless overload), per `QfcItemController.FocusAndTheme.cs:27-67` (state overload) and `:83-123` (parameterless overload).
3. **Planning-time finding: the terminal `_themes[_activeTheme].SetQfcTheme(async: false)` call cannot complete against the handle-less `Theme` double exactly as `BuildFocusController()`/`BuildAllThemes()`/`BuildColorTheme()` build it today, for a reason distinct from the 14 already-passing `FocusAndTheme` siblings — flagged per the remediation-inputs scope-change clause rather than routed around silently:**
   - `Theme.SetQfcTheme(bool async)` (`UtilitiesCS/HelperClasses/ThemeHelpers/Theme.cs:414-432`) branches on `async`. When `async == false` (exactly what `ToggleFocus`/`ToggleFocus(Enums.ToggleState)` pass, lines 64 and 120 of `QfcItemController.FocusAndTheme.cs`), it evaluates `_lblItemNumber.InvokeRequired` (`Theme.cs:420`).
   - `BuildColorTheme` (`QfcItemController.TestSupport.cs:166-178`) constructs its `Theme` via the parameterless constructor `Theme()` (`Theme.cs:128`), which never assigns the private field `_lblItemNumber` (declared, uninitialized, `Theme.cs:110`). Calling `.InvokeRequired` on that null field throws `NullReferenceException`.
   - This differs from the 14 already-passing siblings: `SetThemeDark`/`SetThemeLight` call `SetQfcTheme(async: true)`, which takes the `_uiDispatcher.InvokeAsync(...)` branch (`Theme.cs:416-418`) and never touches `_lblItemNumber`; `ToggleFocusOnAsync`/`OffAsync` and the `ToggleFocusAsync` overloads never call the synchronous `SetQfcTheme(bool)` overload at all.
   - **Second, distinct finding: once `InvokeRequired` is satisfied, `SetQfcTheme(bool async)` falls through to a private, no-arg `SetQfcTheme()` overload in a SEPARATE partial-class file.** When `async == false` and `InvokeRequired == false`, `Theme.cs:426` calls `SetQfcTheme();` — the parameterless overload defined at `UtilitiesCS/HelperClasses/ThemeHelpers/Theme.Rendering.cs:8-103`, not the `bool`-parameter overload in `Theme.cs`. That method unconditionally touches 14 additional private fields that `BuildColorTheme` (`QfcItemController.TestSupport.cs:166-178`) never populates: `_tableLayoutPanels` (throws `NullReferenceException` first, on the `foreach` at `Theme.Rendering.cs:15`, since the field is null on a `Theme()`-constructed instance), `_tipsDetailsLabels` (`:21`), `_tipsExpanded` (:27), `MailRead` (delegate field, invoked at `:34`), `_buttons` (:44), `_menuItems` (:56), `_menuStrip` (:66-68), `_textboxSearch` (:71-72), `_textboxBody` (:75-76), `_comboFolders` (:79-80), `_topicThread` (:82-92), `_webView2` (:94, guarded by a null-`CoreWebView2` check so this one is safe unpopulated), `_viewer` (:101-102), and — via whichever branch `MailRead()` selects — `_lblSender`/`_lblSubject`.
   - **Proof of viability:** `UtilitiesCS.Test/HelperClasses/ThemeHelpers/Theme.DispatcherTests.cs:91-134` (`Constructor_BigOverload_WithNullUiDispatcher_DefaultsToWpfUiDispatcher`) demonstrates that every one of these fields accepts a minimal, handle-less double via the fully-parameterized `Theme` constructor (`Theme.cs:19-138`): `new Label()` (x3, for `_lblItemNumber`/`_lblSender`/`_lblSubject`), `new List<TableLayoutPanel>()`, `new List<Button>()`, `new List<System.ComponentModel.Component>()`, `new MenuStrip()`, `new List<IQfcTipsDetails>()` (x2, for `_tipsDetailsLabels`/`_tipsExpanded`), `new TextBox()` (x2, for `_textboxSearch`/`_textboxBody`), `new ComboBox()`, `new BrightIdeasSoftware.FastObjectListView()`, `new Microsoft.Web.WebView2.WinForms.WebView2()`, `new Panel()` (for `_viewer`, declared type `Control`), and `() => true` for `MailRead` — none require a live window handle or STA thread.
   - **Resolution (test-only, no shared-builder or production change):** a new private static helper, `EnableHandlelessThemeInvoke(FocusController controller)`, is added to `QfcItemController.FocusAndThemeTests.cs` (Phase 1, P1-T1). It reflection-reads the controller's `_themes` field (already populated by `BuildFocusController()` → `BuildAllThemes()` → `BuildColorTheme()`) and, for each `Theme` in `_themes.Values`, reflection-sets every one of the 16 private fields identified above (the `_lblItemNumber` field from the first finding plus the 14 fields from `Theme.Rendering.cs`'s `SetQfcTheme()`, less `_webView2` which tolerates null but is populated anyway for uniformity) to the handle-less doubles proven viable in `Theme.DispatcherTests.cs:91-134` — mirroring the exact reflection technique `BuildColorTheme` already uses for `_uiDispatcher` (`QfcItemController.TestSupport.cs:172-176`). `BuildFocusController`, `BuildAllThemes`, `BuildColorTheme`, and `BuildExecutingViewer` are not modified — only the new tests call the new helper on top of what those builders already produce, satisfying the remediation's "doubles reused without modification" condition while resolving both NREs.
4. **File size.** `QfcItemController.FocusAndThemeTests.cs` is 380 lines before this cycle (confirmed by direct read at plan-authoring time). `EnableHandlelessThemeInvoke` now injects 16 fields (one `typeof(Theme).GetField(...).SetValue(...)` line per field, inside a `foreach (var theme in themes.Values)` loop) instead of 1, so the helper is estimated at ~25 lines (declaration, XML doc comment, field lookup, loop header/footer, 16 `SetValue` lines) rather than ~10. Combined with two new tests (~15 lines each) and two modified tests (no net line-count change), the estimated addition is +55 lines, landing at roughly 435 lines, still under the 500-line cap. Phase 1 includes an explicit post-edit line-count check (P1-T6) rather than relying on this estimate.
