## F15's 7 generated / `Properties/` files — DEC-5 `measured-not-gated` classification

- **Epic child:** F15 (`quickfiler-form-viewers-bayesian-coverage`, issue #496), parent epic #136.
- **Governing ruling:** Epic Ruling DEC-5 (`docs/features/epics/quickfiler-per-file-coverage/epic.md`, § "Epic Ruling: DEC-5 — a `measured-not-gated` disposition for generated files"). Generated `*.Designer.cs` and generated `Properties/` files are **not** `ratified-exempt`; they are instrumented, measured, contribute to repository-wide totals, are **not** individually gated on the 80% line / 75% branch floors, and carry **no** `[ExcludeFromCodeCoverage]` attribute. This is distinct from `interface-only / not-measured` (no denominator at all) — generated files have a real denominator and a real numerator.

### Classification recommendation

All 7 files: **`measured-not-gated`** per DEC-5, with one refinement for file 5.

- **Files 1-4 (the four `*.Designer.cs` Viewer partials):** each has exactly one branch point, the standard `if (disposing && (components != null))` guard inside `Dispose(bool disposing)` — verified identical in shape across all four files this session. This matches the epic's own measurement (`epic.md`, DEC-5 section: "A designer file carries exactly **one** branching line... typically the `Dispose` null check"). Per DEC-5, these files are measured and counted toward totals but not individually gated on the 75% branch floor, because no test can meaningfully drive both operands of a framework-generated disposal guard beyond what construction-and-dispose already exercises (and DEC-1's ratified unshown-construction-and-dispose pattern for the paired `.cs` files already exercises both the `disposing == true` and `components != null` operands naturally). No shape-assertion test should be written to manufacture additional coverage for these four files — DEC-1's already-planned construction of the paired live type is the only coverage action needed, and it is a byproduct of covering `QfcFormViewer.cs`, `QfcItemViewerExpanded.cs`, `BayesianPerformanceViewer.cs`, and `ToolStripMenuItemCb.cs`, not a separate task.
- **File 5 (`AssemblyInfo.cs`):** this file has **zero executable lines** — it declares only assembly-level attributes, no type, no method body. It therefore falls into the epic's **`interface-only / not-measured`** bucket (per the epic's "Directives for F1's Ledger and Harness" § "A third ledger bucket"), not `measured-not-gated`, despite being listed as a "generated `Properties/` file" in the epic's F15 assignment. The distinction matters for F1's ledger: `measured-not-gated` implies a real Cobertura `<class>` element with real `<line>` children; `AssemblyInfo.cs` will emit **no Cobertura class element at all** (the same behavior the epic documents for interface-only files), because it declares no class. Recording it as `measured-not-gated` would misstate what the harness will actually report — F1's ledger should record it N/A / not-measured with the rationale "assembly-level attribute file, zero coverable lines," not as a percentage of any kind, echoing the epic's binding "never 0%" rule for zero-denominator files.
- **Files 6-7 (`Resources.Designer.cs`, `Settings.Designer.cs`):** genuinely `measured-not-gated`. Both declare a real class with real executable members. `Settings.Designer.cs` reports 0.0% today (per the epic's own below-floor table) precisely because nothing in the test suite touches `QuickFiler.Properties.Settings.Default` or any of its typed accessors — under DEC-5 this 0.0% is expected to remain unless some other child's test happens to touch a setting, and it is **not a gate failure** for F15 because DEC-5 exempts generated files from the floor regardless of the percentage. `Resources.Designer.cs` has at least one real branch (`ResourceManager` getter's null-check lazy-init), and any test elsewhere in the assembly that reads an embedded resource (e.g. `ToolStripMenuItemCb`'s constructor reading `Properties.Resources.CheckBoxChecked`) will naturally exercise part of it as a side effect — again a wanted, not engineered, coverage gain.

### Partial-type propagation effect — confirmed wanted, not incidental

Per the task brief and DEC-1's Approach A: removing the type-level `[ExcludeFromCodeCoverage]` attribute from `QfcFormViewer.cs` and `QfcItemViewerExpanded.cs` (per the two dedicated research artifacts for those files) will, as an automatic consequence of partial-type propagation, newly expose `QfcFormViewer.Designer.cs` and `QfcItemViewerExpanded.Designer.cs` to instrumentation — they currently emit no Cobertura class element at all (fully suppressed), and after the attribute removal plus a single DEC-1 unshown-construction test for each paired `.cs` file, both Designer files should jump from absent to a high line-coverage percentage (the `InitializeComponent()` methods in both are branch-free across their bulk, so one construction covers nearly all of each). This is exactly the epic's stated DEC-1/DEC-5 rationale ("removing the type-level attribute improves repository coverage... because `InitializeComponent()` is branch-free across thousands of lines and one construction covers ~99.95% of it") and is a **wanted effect that must not be avoided or worked around** — for example, the plan must not add a narrower member-level exemption to `QfcFormViewer.cs`/`QfcItemViewerExpanded.cs` merely to keep their Designer partials looking untouched; doing so would forfeit real, freely-obtained coverage and would itself risk the `#457` lambda-suppression trap if any member-level attribute were placed carelessly.

### Zero-branch caveat summary for this group

- `AssemblyInfo.cs`: zero coverable lines and zero branches — reports as `interface-only / not-measured`, never a percentage.
- `Settings.Designer.cs`: zero branch points (no conditional logic in any accessor) — reports line coverage as a real percentage (0.0% today) but branch coverage as **N/A**, never 0%, per the epic's binding zero-branch rule.
- `QfcFormViewer.Designer.cs`, `QfcItemViewerExpanded.Designer.cs`, `BayesianPerformanceViewer.Designer.cs`, `ToolStripMenuItemCb.Designer.cs`: exactly one branch point each (the `Dispose(bool)` guard) — real, non-zero `branches-valid`, so these do **not** qualify for the N/A rule; they report a genuine (currently ~50-75%) branch percentage, which DEC-5 explicitly declines to gate regardless.
- `Resources.Designer.cs`: at least one real branch point (`ResourceManager` getter) — real, non-zero `branches-valid`, reports a genuine percentage, not gated per DEC-5.
