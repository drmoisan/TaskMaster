**Deliverable intent:** Diagnostic instrumentation only (increment 3). This plan adds a controlled probe that measures the latency of the FIRST `Globals.Ol.OlReminders` access as a function of when that access occurs, to discriminate Possibility 1 (relocatable readiness wait — latency falls as the configured delay rises) from Possibility 2 (intrinsic first-access build cost — latency constant regardless of delay). It does NOT implement the corrective threading/loading fix (deferred to a follow-up issue once the latency-vs-delay curve is captured). The latency-vs-delay curve itself is a runtime capture across multiple Outlook launches performed manually by the user; it is NOT a unit test and is not produced by this plan's QC loop.

**Scope lock:** Exactly five files may change:
1. production `TaskMaster/Properties/Settings.settings` (add `RemindersProbeDelaySeconds`),
2. production `TaskMaster/Properties/Settings.Designer.cs` (add the generated accessor),
3. production `TaskMaster/app.config` (add the matching `<setting>` default),
4. production `TaskMaster/AppGlobals/AppEvents.cs` (route the first `OlReminders` access through the probe; COM + DispatcherTimer wiring only),
5. one NEW production helper file `TaskMaster/AppGlobals/RemindersProbeSchedule.cs` (the pure decision/scheduling type),
6. one NEW test file `TaskMaster.Test/AppGlobals/RemindersProbeScheduleTests.cs` (the unit-tested seam).

Files 5 and 6 are new sibling files in existing folders and are reported here before creation. Do NOT modify `ApplicationGlobals.cs`, `StartupTimingRecorder.cs`, `IntelligenceConfig.cs`, `PrettyPrinters`, or any other file. If the instrumentation cannot be done within these files (for example a touched file would exceed the 500-line cap and cannot be relieved by the planned helper extraction), STOP and report rather than widening scope.

**Settings pattern rule:** `RemindersProbeDelaySeconds` follows the existing `StartupTimingEnabled` user-scoped pattern verified at planning time across all three settings files: the `<Setting Name="..." Type="System.Int32" Scope="User">` entry in `Settings.settings` (sibling of `StartupTimingEnabled` at line 170), the generated `[UserScopedSetting]` + `[DefaultSettingValue("0")]` `public int RemindersProbeDelaySeconds` accessor in `Settings.Designer.cs` (sibling of the accessor at line 677), and the `<setting name="RemindersProbeDelaySeconds" serializeAs="String"><value>0</value></setting>` entry in `app.config` (sibling at line 609). Default value is `0` in all three files. Settings.Designer.cs is generated code and is COM/VSTO-exempt and not directly unit-tested; the pure helper that consumes the integer is the unit-tested seam.

**Probe design (decided here; exact timer wiring left to executor):**
- The PURE seam is `RemindersProbeSchedule` (new file): given the configured `RemindersProbeDelaySeconds` integer, it returns a decision value exposing (a) whether to defer (`ShouldDefer`, true only when the configured seconds is > 0) and (b) the resolved delay `TimeSpan` (`Delay`). Negative/zero configured values resolve to `ShouldDefer = false` and `Delay = TimeSpan.Zero`. This type contains no COM, no timer, no clock, and no I/O — it is fully deterministic and unit-tested in `TaskMaster.Test`.
- In `AppEvents.Hook()`: when `ShouldDefer` is false (default `0`), the first `OlReminders` access remains exactly the current synchronous assignment `OlReminders = Globals.Ol.OlReminders;` wrapped by the existing `remindersStopwatch` (behavior-preserving, I3-AC1). The cheap `ToDoFolder.Items` read and the inbox subscription loop remain synchronous and unchanged in all paths.
- When `ShouldDefer` is true (configured seconds > 0): the first `OlReminders` access is deferred by `Delay` using a `System.Windows.Threading.DispatcherTimer` (an STA message-pumping timer that does NOT block the STA), performed exactly once on the timer's first `Tick`, after which the timer is stopped to guarantee single execution. The deferred access is timed by its own `System.Diagnostics.Stopwatch` (latency), and the elapsed-since-`Hook`-entry at the access point is read from a `Stopwatch` started at `Hook()` entry (the existing `hookStopwatch`, or an equivalent Stopwatch started synchronously at entry — never a wall-clock API). Latency and elapsed-since-startup are emitted on one readable line via the existing log4net `LogStartupTiming` / `logger` helper in `[Startup timing]`-consistent style (I3-AC2).
- State-equivalence (I3-AC3): the deferred `Tick` handler performs exactly the same assignment `OlReminders = Globals.Ol.OlReminders;` through the same `OlReminders` synchronized property as the synchronous path, so after the access `OlReminders` holds the same value and the reminders subscription/behavior matches. `ToDoFolder.Items` and inbox subscriptions are untouched by the probe in both paths.

**Guardrail: net48 type constraints.** Target framework is net48. Do NOT introduce positional `record struct` (its compiler-generated `init` accessors require `System.Runtime.CompilerServices.IsExternalInit`, unavailable on this target → CS0518). Implement `RemindersProbeSchedule` (and any decision value it returns) as a plain `class` or `readonly struct` with an explicit constructor, following the increment-1/increment-2 `ResourceTimingRow` precedent.

**Guardrail: banned APIs (BannedApiAnalyzers RS0030).** No `DateTime.Now`, `DateTime.UtcNow`, `Random.Shared`, `Thread.Sleep`, or `Task.Delay`. Latency and elapsed-since-startup use `System.Diagnostics.Stopwatch`. The delay uses `System.Windows.Threading.DispatcherTimer` only. The plan introduces no sleep/Task.Delay-based deferral.

**Guardrail: file-size cap.** No production/test file may exceed 500 lines. Pre-change line counts are captured in Phase 0 (P0-T3). `AppEvents.cs` was 437 lines at planning input; the probe-routing additions plus the DispatcherTimer wiring are estimated to keep it under 500 because the pure decision/scheduling logic is extracted into the new `RemindersProbeSchedule.cs` file rather than inlined. P1 includes an explicit post-edit line-count gate (P1-T7); if `AppEvents.cs` would exceed 500 lines, STOP and report before any further extraction.

**Guardrail: COM/VSTO coverage exemption (UT5 explicit-exception call-out).** `AppEvents.Hook()` depends directly on `Microsoft.Office.Interop.Outlook` (`Globals.Ol.OlReminders`, `Globals.Ol.ToDoFolder.Items`, `Globals.Ol.Inboxes`) with no injectable seam and is in the documented COM/VSTO coverage-exempt set in `CLAUDE.md`. The `DispatcherTimer` wiring inside `Hook()` is scheduling/logging glue around that COM access and is exempt by inspection (no live-Outlook test, no live-timer test introduced). `Settings.Designer.cs` is generated code and is exempt. The pure `RemindersProbeSchedule` type is NOT COM-bound and IS unit-tested by deterministic MSTest in `TaskMaster.Test`. This is the explicit exception required by General Unit Test Policy UT5.

**Runtime-validation call-out (not a unit test):** Confirming the actual deadlock / latency-vs-delay behavior requires launching Outlook multiple times with varying `RemindersProbeDelaySeconds` and reading the emitted log lines. This is a manual runtime capture, explicitly NOT a unit test, and is NOT part of this plan's QC loop. The QC loop validates only the pure scheduling seam, the toolchain gates, and behavior-preservation at default `0`.
