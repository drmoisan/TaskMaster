The `Work Mode: minor-audit` marker in `issue.md` governed the prior diagnostic increments (1–3) only; this corrective fix is the large-path refactor authored from `spec.md` per the maintainer directive (2026-06-21).

**Deliverable intent:** Replace the synchronous, unconditional readiness-dependent COM hookups in `AppEvents.Hook()` with a real Outlook store-readiness gate driven by a `DispatcherTimer` poll, so the STA always pumps and no single COM call blocks for a prolonged period during cold start. Introduce a testable readiness seam (`IOutlookReadinessGate` + production `OutlookReadinessGate`) and a pure, unit-tested `HookReadinessCoordinator` state machine (tick → check gate → run-once / retry / continue). Harden `AppOlObjects.LoadInboxes()` so a transient not-ready COMException routes to retry instead of silently dropping the inbox subscription. Offload non-COM compute in `ProcessMailItemAsync` after STA primitive extraction. Remove the superseded increment-3 deferral scaffolding while retaining the increment-1/2 timing logs. Bring all touched files ≤ 500 lines (extract a junk-folder partial from `AppOlObjects.cs`).

**Out of scope (do NOT modify):** `UtilitiesCS/EmailIntelligence/IntelligenceConfig.cs`, `ApplicationGlobals.cs` load sequencing, and the Teams-attributed `Task.Run` continuation path (the ~115 s IntelConfig-phase residual is external STA starvation, maintainer decision 2026-06-21). The existing `IntelligenceConfig` deserialization and `helper.Tokens` offloads are already correct and are left unchanged.

**Scope lock (production files that may change):**

**Guardrail: net48 type constraints.** Target framework is net48. Do NOT introduce positional `record struct` (its compiler-generated `init` accessors require `System.Runtime.CompilerServices.IsExternalInit`, unavailable on net48 → CS0518). Implement any new value type (e.g. coordinator state/decision) as a plain `class`, an `enum`, or a `readonly struct` with an explicit constructor, following the prior `RemindersProbeSchedule`/`ResourceTimingRow` precedent.

**Guardrail: banned APIs (BannedApiAnalyzers RS0030).** No `DateTime.Now`, `DateTime.UtcNow`, `Random.Shared`, `Thread.Sleep`, or `Task.Delay` in new or touched code. Any timing uses `System.Diagnostics.Stopwatch`; polling uses `System.Windows.Threading.DispatcherTimer` only. (Note: a pre-existing `Task.Delay(100)` exists in `AppEvents.ProcessNewInboxItemsAsync` error-retry path at the current line ~456; it is NOT a line touched by this fix and is out of scope to change. Do not introduce any NEW banned-API call site.)

**Guardrail: COM apartment reality.** Outlook COM objects are apartment-bound to the STA on which they were created. COM property reads, event subscriptions, `Restrict` calls, and `SetUdf` writes MUST execute on the STA — moving them to a worker thread marshals back to the STA and does not free it. Only pure compute on already-extracted .NET primitives (strings/ints) may run on a worker.

**Guardrail: file-size cap.** No production/test file may exceed 500 lines. Pre-change line counts are captured in Phase 0 (P0-T3). `AppOlObjects.cs` is 523 lines at planning input (over the cap) and is touched by this fix; the cohesive junk-folder region (`ReadJunkCertainSetting`/`WriteJunkCertainSetting`/`ReadJunkPotentialSetting`/`WriteJunkPotentialSetting`/`ApplyJunkFolderSelections`/`RefreshJunkFolderSelections`/`LoadJunkPotential`/`LoadJunkCertain` and the `_junkPotential`/`_junkCertain` backing fields + `JunkPotential`/`JunkCertain` properties, current lines ~199–310, ~112 lines) is extracted into the new `AppOlObjects.JunkFolders.cs` partial. Each phase that edits a file includes an explicit post-edit line-count gate.

**Guardrail: COM/VSTO coverage exemption (UT5 explicit-exception call-out).** `OutlookReadinessGate` (live `App.Session.DefaultStore.GetDefaultFolder` probe), the `DispatcherTimer` wiring, `AppEvents.Hook()`, `AppEvents.ProcessMailItemAsync` COM touches, and `AppOlObjects.LoadInboxes` COM enumeration depend directly on `Microsoft.Office.Interop.Outlook` with no injectable seam and are in the documented COM/VSTO coverage-exempt set in `CLAUDE.md`; they are verified by inspection (no live-Outlook test, no live-timer test). `Settings.Designer.cs` is generated code and is exempt. The pure `HookReadinessCoordinator` decision/state-machine logic and the `IOutlookReadinessGate`-mediated decisions are NOT COM-bound and carry the new-code coverage obligation (≥ 90%), unit-tested by deterministic MSTest with a `Mock<IOutlookReadinessGate>`.
