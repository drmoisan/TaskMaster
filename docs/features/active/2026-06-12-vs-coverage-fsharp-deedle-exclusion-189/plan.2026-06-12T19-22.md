## Why this revision (do not re-litigate)

The prior plan (v1.0) assumed a single mechanical edit to `TaskMaster.runsettings` could (a) clear the Visual Studio static-coverage `VerificationException` and (b) be CLI-verified as opt-in. Two empirical findings (`evidence/other/scope-change-finding.2026-06-12T19-45.md`) invalidated that:

1. Standalone `vstest.console` uses **dynamic** coverage and does **not** reproduce the Visual Studio **static** coverage (`datacollector://microsoft/CodeCoverage/2.0`) `VerificationException`. The exclusion's effect therefore **cannot be CLI-verified**; Visual Studio confirmation is the authoritative acceptance (AC8, user action).
2. At the CLI, the mere presence of a `<DataCollector friendlyName="Code Coverage">` block (with no `enabled` attribute) **force-activates** coverage on a plain run. Because #188 made the VS Code task scripts pass the runsettings to `vstest.console`, the coverage collector block **must not live in the file those scripts consume**.

Option A resolves both by splitting the runsettings:

- The repo-root `TaskMaster.runsettings` (Visual Studio auto-detects this) carries the coverage exclusion block — this is where VS "Analyze Code Coverage" reads it.
- A new off-root CLI runsettings (`scripts/vscode/TaskMaster.cli.runsettings`) carries parallelization only and is what the VS Code scripts consume — so a plain CLI run collects no coverage.
