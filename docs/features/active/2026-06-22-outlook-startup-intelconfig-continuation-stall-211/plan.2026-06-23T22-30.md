## Verified context (do not re-litigate)

- The Phase 3.1 probe covered ONLY the `Engines` phase. The 2026-06-23T21-55 capture showed the latency was in IntelConfig (60 s) and ToDo (55.7 s), not Engines (2.65 s); GC was disproven (`[gc-delta] gen0=1 gen1=0 gen2=0`). The slow phase varies run-to-run.
- The probe scope must be widened across ALL phases of `LoadSequentialAsync` so the next capture shows whether the STA is actually frozen during the slow phase (heartbeat gaps ≈ phase duration) or whether an async continuation merely waits while the STA stays responsive.

## Hard constraints (guardrails — apply to every implementation task)

- Behavior-preserving / diagnosis-only. MUST NOT change phase order, phase set, or load semantics. No added awaits in the phase path beyond what already exists. The heartbeat and GC reads must not perturb the phases.
- `Stopwatch` only. NO banned APIs: `DateTime.Now`, `DateTime.UtcNow`, `Random.Shared`, `Thread.Sleep`, `Task.Delay` (enforced by BannedApiAnalyzers / `BannedSymbols.txt`). Target framework net48.
- All touched files MUST remain `<= 500` lines. Baseline `ApplicationGlobals.cs` is ~359 lines. If the change would exceed 500, extract logic into `StartupDiagnosticsProbe` (coverable) rather than growing the call site.
- Reuse the existing `StartupDiagnosticsProbe` coverable helper for ALL pure formatting/aggregation. Keep `DispatcherTimer`/`Dispatcher` scheduling, the per-tick `Stopwatch`, and live `GC.*`/`GCSettings.*` reads in the thin `protected internal virtual` seam methods on `ApplicationGlobals`. The existing test subclasses no-op-override these seams; this MUST be preserved so headless MSTests do not construct a live `DispatcherTimer`.
- Do NOT touch `PreserveReferencesHandling.All` or any engine/serialization logic. Keep the existing Phase 1 `[continuation-resume]` and Phase 3 `[engine-init]` lines unchanged.
- Deterministic MSTest (MSTest + Moq + FluentAssertions) for any new/changed pure logic (phase-annotation formatting, per-phase GC-delta formatting). No live COM/timer/Dispatcher/filesystem/network; no temporary files. New code `>= 90%` coverage; no repository-wide regression.
- C# toolchain order is mandatory per implementation task and at final QA: CSharpier -> .NET analyzers -> nullable/TWAE -> MSTest with coverage (`/TestCaseFilter:"TestCategory!=LiveOutlook"`). Restart the loop from CSharpier if any step changes files or fails.

## Acceptance criterion introduced by this plan

- **AC14 — All-phase UI-heartbeat + per-phase GC, phase-annotated.** The 250 ms `DispatcherTimer` UI heartbeat starts BEFORE the first phase (`LoadIntelConfigPhaseAsync`) and stops AFTER the last phase (Events / end of `LoadSequentialAsync`), so it covers the entire sequential startup, not only Engines. Each `[ui-heartbeat]` line is annotated with the currently-active phase name (the phase whose body/await is in flight when the tick fires), maintained by a current-phase marker field updated at each phase boundary. A `[gc-delta]` line is emitted per phase (GC counts/allocated bytes captured before and after each phase await), each annotated with its phase name and carrying `isServerGC`/`latencyMode`. Pure phase-annotation and per-phase GC-delta formatting live in `StartupDiagnosticsProbe` (coverable, not `[ExcludeFromCodeCoverage]`) and are covered by deterministic MSTest. The host-bound scheduling and live GC reads stay in the `protected internal virtual` seams. Phase order/set/semantics are unchanged; the existing `[continuation-resume]` and `[engine-init]` lines are unchanged. New code reaches `>= 90%` coverage with no repository-wide regression; the full C# toolchain passes in order.
