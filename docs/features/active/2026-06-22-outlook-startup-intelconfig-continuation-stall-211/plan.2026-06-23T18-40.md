## Objective

Empirically determine whether the UI/STA thread is actually starved or suspended during the `Engines`-phase SpamBayes engine deserialization (which the verified Phase 3 evidence places on a thread-pool thread, not the UI thread), and attribute any observed UI stall to a concrete cause (e.g., blocking GC) rather than assuming it. This is diagnosis-only instrumentation; it must not change phase order, the engine set, or load semantics, and it must not implement any latency fix.

Three measurements are added around the `Engines` startup phase in `ApplicationGlobals.LoadSequentialAsync`:
1. A UI-thread responsiveness heartbeat scheduled on `UiThread.Dispatcher` (the decisive measurement): each tick records the ACTUAL elapsed interval since the previous tick via `Stopwatch`; large gaps prove starvation/suspension, regular ticks prove responsiveness.
2. A GC probe capturing `GC.CollectionCount(0/1/2)` and `GC.GetTotalMemory(false)` before/after the phase, plus `GCSettings.IsServerGC` and `GCSettings.LatencyMode`, emitting one structured delta line.
3. Worker-thread context added to the per-engine probe path: `Thread.CurrentThread.Priority` and `Thread.CurrentThread.IsThreadPoolThread` for the engine-init thread.

## Expected Outcome

- A recurring UI-thread heartbeat runs on `UiThread.Dispatcher` at a fixed nominal interval (250 ms) for the duration of the `Engines` phase and stops/disposes when the phase completes. Each tick emits one structured `[ui-heartbeat]` line via `log4net` recording the nominal interval, the actual measured interval, and the gap (actual minus nominal) using `Stopwatch` only. Phase order/semantics are unchanged (AC11).
- One structured `[gc-delta]` line is emitted via `log4net` after the `Engines` phase recording Gen0/Gen1/Gen2 collection-count deltas, the allocated-bytes delta (`GC.GetTotalMemory(false)` before/after), `IsServerGC`, and `LatencyMode` (AC12).
- The existing `[engine-init]` probe line (or a parallel line) additionally records `threadPriority=` and `isThreadPoolThread=` for the engine-init thread (AC12 worker-thread context).
- The pure gap-computation/formatting logic and the pure GC-delta-formatting logic are extracted into a new coverable helper (NOT marked `[ExcludeFromCodeCoverage]`), unit-tested with MSTest + Moq + FluentAssertions, deterministic, with no live COM/timer/Dispatcher/filesystem/network and no temporary files; new code reaches `>= 90%` coverage with no repository-wide regression (AC13).
- Maintainer non-debugger cold-start re-capture instructions plus an evidence placeholder so the probe output (heartbeat-gap lines, GC-delta line) can be recorded under `evidence/other/`. Running Outlook is NOT performed by this plan.

## Design Decision — Testable Seam (drives AC13)

`ApplicationGlobals` and the Dispatcher/`DispatcherTimer` scheduling are COM/UI-host bound and not unit-testable without a live Outlook/WPF runtime. Writing the gap and GC-delta math inline would be uncoverable. Therefore the pure measurement/formatting logic is extracted into a new coverable helper class `StartupDiagnosticsProbe` (NOT `[ExcludeFromCodeCoverage]`), mirroring the existing `EngineInitTimingProbe`:

- A heartbeat-tick method that takes the nominal interval and the measured elapsed interval (both `TimeSpan`/`double` ms supplied by the call site's `Stopwatch`) and emits one `[ui-heartbeat]` line through an injected `Action<string>` sink (production passes `s => logger.Debug(s)`).
- A GC-delta method that takes before/after collection counts (Gen0/1/2), before/after allocated bytes, `isServerGC`, and `latencyMode` (all captured by the thin call site from the framework GC APIs) and emits one `[gc-delta]` line through the sink.

The `DispatcherTimer`/`Dispatcher.InvokeAsync` scheduling, the `Stopwatch` start/stop per tick, and the live `GC.*`/`GCSettings.*` reads stay in the thin (excluded) call site in `ApplicationGlobals`. Only the pure delta/format logic lives in `StartupDiagnosticsProbe`, so the helper is testable by passing plain numeric inputs and capturing emitted lines into a `List<string>`. The worker-thread context fields are added to the existing `EngineInitTimingProbe` (already coverable) so the `[engine-init]` line carries `threadPriority=`/`isThreadPoolThread=` and the addition is covered by the existing test class.
