**Working-directory and worktree rule (standing; in force from P0-T1 onward).** The executing agent is not worktree-isolated, because the Bash tool's isolation filter refuses pwsh and this plan invokes pwsh throughout. Its inherited working directory is therefore the coordinator session worktree, which is a different tree on a different branch, and not this item's worktree. The item worktree root is supplied to the executor by the binding worktree directive in its own delegation prompt; wherever this plan writes `<item worktree root>` the executor substitutes that root. No absolute host path is written into this plan, into any workflow file, or into any committed artifact. The rule has four parts and it governs every task in this plan, including tasks whose own text does not repeat it.

1. Git is addressed as `git -C "<item worktree root>"`. Supplying a bare dot as the repository-directory argument is prohibited everywhere in this plan, because it resolves to the coordinator session worktree. This matters most at P0-T3: git tags are repository-global, so an anchor tag created from the session worktree's HEAD is created without error, and every `plan-869-base..HEAD` gate in this plan would then compare against a commit on an unrelated branch, silently and with no failing command to reveal it.

2. Every pwsh invocation made with `-Command` begins with the worktree prologue. This plan writes that prologue as the token `<worktree prologue>` at the head of each payload, and the executor expands it to exactly these two statements: `Set-Location -LiteralPath "<item worktree root>"; [Environment]::CurrentDirectory = "<item worktree root>"`. Both statements are required. `Set-Location` alone governs neither `System.IO` calls nor native child processes, because .NET's `CurrentDirectory` is a separate process-wide value that `Set-Location` does not update, and a native child inherits the latter. With the prologue in force, every repo-relative path inside that payload resolves against the item worktree and needs no further rewriting.

3. A pwsh invocation made with `-File` carries no payload and therefore cannot carry the prologue, so its script path is written absolute, as the item worktree root joined with the repo-relative script path. That absolute path is load-bearing beyond reaching the right file: both scripts this plan invokes with `-File` derive the repository root from their own location rather than from the working directory, `scripts/vscode/Invoke-MSTestWithCoverage.ps1` at its line 305 and `scripts/dev-tools/run-actionlint.ps1` at its line 4, so an absolute `-File` path is what fixes the tree they operate on. For the same reason the argument `-SearchRoot .` is correct as written and must NOT be changed to an absolute path: line 306 of that script joins the supplied search root onto the script-derived repository root, and PowerShell's `Join-Path` does not collapse an absolute second argument, so an absolute search root would yield an invalid path and the existence check at line 308 would throw `Search root not found`.

4. Every path passed to the Read, Write, Edit, Grep or Glob tools is absolute, formed as the item worktree root joined with the repo-relative path this plan names. Every artifact path, source path and test path in this plan is stated repo-relative for readability and is joined in this way at the point of use. This part is in force from P0-T1, which writes the first artifact of the plan: a repo-relative path handed to the Write tool resolves against the agent's working directory and would place that artifact in the coordinator session worktree.

Exemption, and it is the only one. Content written INTO `.github/workflows/_pester.yml`, `.github/workflows/_mstest-coverage.yml` and `.github/workflows/ci.yml` keeps its repo-relative form.
