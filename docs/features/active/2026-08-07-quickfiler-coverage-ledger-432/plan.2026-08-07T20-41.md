## Toolchain Contract (PowerShell)

Run in this exact order; restart from stage 1 whenever any stage fails or modifies a file:

1. **Format** — MCP tool `mcp__drm-copilot__run_poshqc_format`, `workspace_root` = the executor's own current worktree root.
2. **Analyze** — MCP tool `mcp__drm-copilot__run_poshqc_analyze`, same `workspace_root`.
3. **Type check** — not applicable to PowerShell; skipped by policy (`.claude/rules/powershell.md` line 17).
4. **Test** — MCP tool `mcp__drm-copilot__run_poshqc_test`, same `workspace_root`. The tool's parameter schema is `workspace_root` plus `scan_folders` only; it exposes no coverage switch and emits coverage unconditionally, so no "coverage enabled" argument is supplied.

VS Code task wrappers are not an approved substitute. No C# toolchain stage runs in this plan.

The analyze stage carries a pre-existing repository baseline recorded in `[P0-T5]`. "Stage fails" means the stage's diagnostic count exceeds that baseline or the stage modified a file — not merely a non-zero exit code. `[P11-T4]` applies the same definition.

The test stage carries the same baseline-delta treatment, for the same reason. A recorded prior observation in this repository is that `mcp__drm-copilot__run_poshqc_test` can exit `-1` (`4294967295`) with no accompanying detail in TaskMaster worktrees, at baseline as well as post-change. **A failing test stage therefore means a non-zero `failures` total or a non-zero `skipped` total across the `<testsuite>` entries in `artifacts/pester/pester-junit.xml`, or an exit code that is worse than the `[P0-T6]` baseline exit code — not merely a non-zero exit code.** The tool's exit code is recorded verbatim as an observation on every test-stage artifact and is compared against the `[P0-T6]` baseline value. `[P9-T49]`, `[P10-T16]`, `[P11-T3]`, and `[P11-T4]` apply this definition.

## Decisions Record (planning-time choices the executor must not re-litigate)

1. **Research decisions D1-D17 are settled specification.** They are sequenced into tasks below, not re-opened. Where the epic manifest and the research artifact disagree, the research artifact wins and the manifest's figure is recorded as a reconciliation note, never as a target.
2. **Verified attribute figures.** 40 attribute usages across 21 compiled files; 14 type-level; 26 member-level; 24 compiled files fully coverage-suppressed once partial-class inheritance is applied; 11 informational `inherited` rows. The manifest's 33 decomposes without residual as 21 compiled-with-attribute + 5 compiled-comment-only + 7 not-compiled. The figure 33 must not appear anywhere in this feature's deliverables as a target.
3. **Disposition unit is the attribute usage, not the file (D2).** `kind` is one of `type`, `member`, `inherited`. `inherited` rows are informational and are excluded from the count of 40.
4. **Classification and disposition are separate axes.** Phases 2 and 3 record dispositions only. Phase 4 records the per-file `classification`. A file may be `ratified-exempt` (for example a generated designer file) while the type-level attribute that currently suppresses it is disposed `remove`; the two statements are consistent and both are recorded.
5. **`source_commit` is the executor's own HEAD short SHA at ledger-authoring time,** recorded in `[P0-T3]`. It is not hard-coded to the research artifact's `74be1964`. The compiled-surface invariant (`Compile Include` count equals 121) is the gate, not the SHA; drift is a halt condition, not a silent adjustment.
6. **Entry function returns an exit code; it does not call `exit`.** `Invoke-PerFileCoverageGate` performs all reads, writes `-OutputPath` when supplied, emits per-row diagnostics via `Write-Error`, and returns `[pscustomobject] @{ ExitCode = <int>; ReportText = <string> }`. The dot-source-safe script guard writes `ReportText` via `Write-Output` and calls `exit $result.ExitCode`. This is what makes exit codes `0`, `1`, `2` assertable against the entry function in Pester without terminating the test host, as `spec.md` requires.
7. **One internal helper beyond the spec's five named functions is permitted:** `ConvertTo-CoveragePathKey`, the backslash/`OrdinalIgnoreCase` path normalisation shared by `Get-CoberturaPerFileCoverage` and `Test-PerFileCoverageThreshold` (D11). The spec's function list is a minimum public surface, not a maximum; duplicating normalisation in two functions would violate the reusability rule in `.claude/rules/general-code-change.md`.
8. **`schema_version` validation is pure and lives in `Test-PerFileCoverageThreshold`,** which raises a bare `throw` with a specific literal message on an unrecognised value, matching `Invoke-MSTestWithCoverage.Helpers.ps1:113`. The entry function catches and maps to exit `2`.
9. **`scripts/temp-extract-coverage.ps1` is deleted (D13),** not deprecated in place. The rejected alternative — a deprecation comment — preserves the risk of a sibling child using it for no benefit.
10. **The reference Cobertura sample used for cross-checks and the smoke run is** `docs/features/active/2026-08-06-quickfiler-high-confidence-queue-init-stall-424/evidence/qa-gates/coverage-final.cobertura.xml`. It is read-only input. The smoke run in `[P8-T6]` is expected to exit `1` because wave-1 coverage work has not happened yet; that expected non-zero result is recorded as an observation and is **not** a QC gate.
11. **Coverage gate figures.** `.claude/rules/powershell.md` requires line coverage >= 85% and branch coverage >= 75%, and treats coverage regression on changed lines as blocking. The change-scoped gate applied by this plan is: the two new production scripts each reach >= 85% **line** coverage, and the repository-wide PowerShell line-coverage figure does not regress against the `[P0-T6]` baseline. The >= 75% branch-coverage requirement in `.claude/rules/powershell.md` is not measurable by the PowerShell toolchain (Pester's JaCoCo output emits no BRANCH counter); that gap is recorded as an out-of-scope observation in `[P11-T5]` and is not re-legislated by this feature. If the recorded baseline repository-wide line figure is already below 85%, that pre-existing state is recorded numerically in the delta artifact and the no-regression rule governs; it is not silently ignored and it is not remediated by this feature. The two new scripts' >= 85% line figure is measured by a supplementary direct `Invoke-Pester` run scoped to those two files, recorded in `[P11-T3]`. The MCP tool's repository-wide figure is a hooks-only figure by construction and is used solely for the no-regression comparison; that scope limitation is recorded, not remediated. The feasibility of the supplementary mechanism is proven in Phase 0 by `[P0-T12]`, so a missing Pester v5 or a non-functioning `New-PesterConfiguration` halts the plan at Phase 0 rather than at Phase 11.
12. **Tests read repository files but create none.** Reading `QuickFiler/QuickFiler.csproj`, `coverage-ledger.json`, and `coverage-ledger.md` from `$PSScriptRoot`-relative paths is required by the drift assertion and is permitted. The prohibition in `.claude/rules/general-unit-test.md` is on **creating** temporary files; no test in this plan creates, writes, or deletes a filesystem path. The `-OutputPath` write is asserted through a mocked `Set-Content`.

Phase 0 therefore proves scan membership for the two target directories by scoped invocation and observable effect (format, analyze) and by `artifacts/pester/pester-junit.xml` suite entries (test); Phase 11 confirms all **six** new file paths the same way. A negative Phase 0 result is a Blocking finding to be recorded and escalated, never worked around by relocating the files.
14. **`scripts/vscode/` is not analyzer-clean at baseline.** Verified at a clean working tree: `mcp__drm-copilot__run_poshqc_analyze` exits `1` repo-wide with 24 issues, and exits `1` with 16 issues when scoped to `["scripts/vscode"]`; all 16 live in `scripts/vscode/`. `tests/scripts/vscode/` is clean at 0. 15. **The Phase 9 Pester harness suite is authored as three files from the outset.** `tests/scripts/vscode/Get-PerFileCoverage.Helpers.Cobertura.Tests.ps1` holds the Cobertura document-reading cases (`Merge-CoberturaFileLines` and `Get-CoberturaPerFileCoverage`), `tests/scripts/vscode/Get-PerFileCoverage.Helpers.Verdict.Tests.ps1` holds the verdict and report-rendering cases (`Test-PerFileCoverageThreshold` and `Format-PerFileCoverageReport`), and `tests/scripts/vscode/Get-PerFileCoverage.Tests.ps1` holds the entry-function and exit-code-contract cases. This supersedes the "two test files" phrasing in the `spec.md` "Constraints & Risks" section, the two-file enumeration in AC5's *Verification* paragraph, and the "four new file paths" phrasing in AC6's *Verification* paragraph, AC4's *Verification* paragraph, and the `## API / CLI Surface` **Files (D6)** table, without changing any acceptance-criterion checkbox text. This Decisions Record entry is the supersession mechanism.
16. **Three harness test files do not require a change-budget override.** `.claude/rules/powershell.md` caps a batch at 3 production files and 3 test files. This plan creates 2 production files and 4 test files, but the cap is per batch, not per feature: Phase 9 creates the three harness test files (at the cap, not over it) and Phase 10 creates the ledger-completeness test file in a separate batch. No batch exceeds three test files, so no override is required. Splitting into three harness files rather than two is a deliberate margin decision — the two-file split projected one file at roughly 522 lines against the 500-line limit, and a 500-line breach at execution time is a Blocking halt. Measured local density supports the projection: `tests/scripts/vscode/Invoke-MSTest.RunSettings.Tests.ps1` is 451 lines for 25 `It` blocks (18.0 lines per `It`) and `tests/scripts/vscode/Invoke-MSTestWithCoverage.Helpers.Tests.ps1` is 222 lines for 8 (27.8). That distribution is not the even 14 / 14 / 13 because the five function groups are indivisible at sizes 4, 8, 12, 5, and 12, and no partition of those whole groups into three subsets yields 14 / 14 / 13; the alternative with a smaller maximum (16 / 13 / 12) pairs unrelated functions in both of its larger files and was rejected on cohesion. The 17-case file carries the two lowest-density groups — the threshold cases assert one value each against a shared fixture builder, and the rendering cases assert one rendered string each — so its projection at the 18.0 lines-per-`It` local density is roughly 306 case lines plus a fixture section, comfortably inside 500. `[P9-T48]` enforces the limit per file and escalates any overage rather than creating a further file.
