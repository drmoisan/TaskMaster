- **D2 — The diff anchor is captured at execution time, never fixed as a literal when this plan is written.** [P0-T2] runs `git rev-parse HEAD` before any task of this plan has edited a file, and records the printed 40-character hexadecimal SHA as the `BASE-SHA:` field of `docs/features/active/2026-09-08-quickfiler-teardown-review-residuals-823/evidence/baseline/p0-t2-branch-and-base.md`. Every command span in this plan that needs the anchor writes the bare token `BASE-SHA` as the diff's left ref operand. Before running such a span the executor reads that field with the Read tool and substitutes the literal 40-character SHA in place of the token. Substituting it is mandatory rather than optional: a command left carrying the token addresses no commit and fails, which is the intended failure mode rather than a silent pass. No unanchored `git diff` is permitted anywhere in this plan, because a diff with no ref operand and no `--cached` compares the worktree against the index, which is ambient state, and therefore passes vacuously once the change is committed; and every anchored name-listing diff of the form `git diff --name-only BASE-SHA...HEAD` is paired in its own task with a `git add` span or with `git status --porcelain --untracked-files=all`, because a name-listing diff enumerates tracked changes only and is structurally blind to an untracked path. Why the anchor may not be a literal: a three-dot diff degenerates into a two-dot diff whenever its left operand is an ancestor of its right, because the merge base is then the left operand itself; a literal anchor therefore bills this feature for every commit that lands between that literal and the executor's own work. The degeneration is not hypothetical here. The predecessor draft of this plan fixed the anchor to the head of `epic/review-residuals-2026-09-08-integration` as it stood when that draft was written, and recorded a one-path three-dot diff against it as a measurement. The epic-planner then fanned sibling preparation work into that same integration branch, and the same command on the same branch now lists twenty-one paths: ten under `.claude/agent-memory/`, eight owned by the sibling feature folders `docs/features/active/2026-09-08-coverage-aggregation-double-counts-method-rows-815/` and `docs/features/active/2026-09-08-console-out-aggressors-and-banned-symbol-promotion-826/`, and this feature's own three documents. `epic-orchestrator` branches this feature's execution worktree from that integration branch at execution time, after further sibling fan-ins, so any literal fixed now is an ancestor of that future head and the same degeneration recurs one generation later. A self-anchor cannot degenerate: the HEAD recorded by [P0-T2] is read before this plan's first commit, so it is by construction not an ancestor of any commit that is not the executor's own, and the three-dot diff against it therefore contains this feature's work and nothing else. Under a degenerated anchor the footprint criteria AC26, AC27 and AC28 would report sibling-owned and epic-owned files against this delivery.
