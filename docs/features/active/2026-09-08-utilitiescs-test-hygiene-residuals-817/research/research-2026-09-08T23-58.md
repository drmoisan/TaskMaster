# Research: Splitting `FolderPredictorTests.cs` under the 500-line file limit (#817)

Scope: `UtilitiesCS.Test/OutlookObjects/Folder/FolderPredictorTests.cs` (1067 lines, single
`[TestClass][DoNotParallelize] public class FolderPredictorTests`, 39 `[TestMethod]`s, 5 private
static helper methods, 2 nested private test-double classes). Read in full; line numbers below are
1-indexed and refer to the file as it exists at research time.

## 1. Partial-class feasibility

**Confirmed precedent exists in this repo already; this is not a novel pattern.** MSTest discovers
`[TestMethod]`s correctly on a `partial class` split across files, with `[TestClass]` /
`[DoNotParallelize]` present on only one of the partial declarations. This is the repo's
established convention for keeping test files under the 500-line limit, used dozens of times,
including files that are already live in CI:

- `UtilitiesCS.Test/OutlookObjects/Store/StoreWrapperController_Tests.cs` (primary — carries
  `[TestClass]` + `[DoNotParallelize]` on `public partial class StoreWrapperController_Tests`) plus
  four siblings with no class attributes, just `public partial class StoreWrapperController_Tests`:
  `StoreWrapperController_Tests.ButtonAndPopulate.cs`, `.ExcludeStore.cs`, `.Launch.cs`, `.Display.cs`.
- `UtilitiesCS.Test/OutlookObjects/Folder/OutlookFolderTreeServiceTraversalCancellationTests.cs` +
  `.Coverage.cs`.
- `UtilitiesCS.Test/OutlookObjects/AppointmentItem/MeetingItemHelperTests.cs` + `.Part2.cs`.
- `TaskMaster.Test/AppGlobals/AppEventsTests.cs` + `AppEventsTests.Helpers.cs` — this sibling is a
  direct precedent for a **helpers-only partial file with no test methods**: it contains only
  `private static` factory methods (`CreateGlobalsWithNoEngines`, `CreateMailItem`,
  `BuildUnprocessedInboxItems`, etc.), consumed by the primary file's test methods via ordinary
  partial-class member visibility.
- Also observed at scale in `QuickFiler.Test/Controllers/` (`QfcItemController.*Tests.cs` +
  `.Part2.cs`/`.Part3.cs`, `QfcHomeController*Tests.cs` + `.Part2.cs`/`.Part3.cs`,
  `BreadcrumbBridgeRouterTests.cs` + `.Selection.cs`, etc.) and `Tags.Test/TagControllerSeamTests.cs`
  + `.KeyboardNavigation.cs`.

Mechanism: the C# compiler merges all `partial class` declarations of the same type (same
namespace, same assembly) into one type before MSTest's reflection-based discovery runs, so
class-level attributes declared on any one part apply to the whole merged type, and
`private`/`private static` members declared in one part are visible from all other parts. Class
attributes must appear on exactly one part (repeating `[TestClass]` on more than one part is not
done anywhere in the repo's existing splits and is unnecessary).

**Known trap** (already recorded in `.claude/agent-memory/atomic-executor/project_test_file_name_vs_partial_class_name.md`,
confirmed instance from issue #498): a split file's **file name** is not the same as its **type
name** — e.g. `BreadcrumbStateModelSequenceTests.cs` declares `partial class
BreadcrumbStateModelTests`. A vstest `/TestCaseFilter:FullyQualifiedName~<FileName>` that assumes
file name == type name silently matches zero tests and exits 0. For #817 the recommendation is to
**keep the type name `FolderPredictorTests` identical across all split files** and give each file a
distinct, behavior-descriptive file name (see §2), so this trap does not apply directly here, but
any acceptance-gate filter written against a split file's name (rather than the type name
`FolderPredictorTests`) must be checked against this precedent before being trusted.

example in the repo (e.g. the `StoreWrapperController_Tests` family, 5 files, each repeating the
same 9-line `using` block).

## 3. `UtilitiesCS.Test.csproj` mechanics

The project is a legacy non-SDK `packages.config` project with explicit `<Compile Include="...">`
entries (confirmed; roughly 470 such entries observed in the file). The exact existing entry and
surrounding context for `FolderPredictorTests.cs`:

```
406:    <Compile Include="OutlookObjects\Store\StoreWrapperControllerTests.cs" />
407:    <Compile Include="OutlookObjects\Folder\FolderWrapperStateTests.cs" />
408:    <Compile Include="OutlookObjects\Folder\FolderWrapperTraversalTests.cs" />
409:    <Compile Include="OutlookObjects\Folder\FolderTreeTests.cs" />
410:    <Compile Include="OutlookObjects\Folder\FolderPredictorCoverageExpansionTests.cs" />
411:    <Compile Include="OutlookObjects\Folder\FolderPredictorTests.cs" />
412:    <Compile Include="OutlookObjects\Folder\FolderRowTests.cs" />
413:    <Compile Include="OutlookObjects\Folder\FolderWrapperCoverageExpansionTests.cs" />
414:    <Compile Include="OutlookObjects\Folder\MAPIMethodsTests.cs" />
415:    <Compile Include="Properties\Resources.Designer.cs">
```

**Entries are not alphabetically sorted; they are in arbitrary/append order** (e.g. `FolderScoreTests.cs`
appears at line 368, well before `FolderPredictorTests.cs` at line 411, and `FolderProbabilityAdapterTests.cs`
appears at line 318 — alphabetically `FolderPredictorTests` < `FolderProbabilityAdapterTests` <
`FolderRowTests` < `FolderScoreTests`, but the file order is
`FolderProbabilityAdapterTests`(318), `FolderScoreTests`(368), `FolderPredictorTests`(411),
`FolderRowTests`(412) — not sorted by any visible rule). This was cross-checked against a second,
unrelated cluster in the `Store` folder group (`StoreWrapperController_Tests.cs` family), which is
also non-alphabetical (`.cs`, `.ButtonAndPopulate.cs`, `.ExcludeStore.cs`, `.Launch.cs`,
`.Display.cs`).

**Convention for adding new sibling entries** (matching the existing pattern for every multi-file
split found, e.g. the `StoreWrapperController_Tests` block): insert the new `<Compile Include>`
lines for the 4 new sibling files **immediately after** the existing
`<Compile Include="OutlookObjects\Folder\FolderPredictorTests.cs" />` line (currently line 411),
before `FolderRowTests.cs` (currently line 412), in the same order as the files are introduced.
This reads as a minimal, localized 4-line insertion rather than a reordering, satisfying the hard
constraint against reordering or reformatting unrelated entries (relevant given 5 sibling features
may also touch this csproj concurrently).

## 4. Test-count verification mechanism (real discovery, not source grep)

The repo already has a proven, non-vacuous two-sided verification pattern for exactly this
scenario (test-file split under the 500-line limit), documented in
`docs/features/archive/2026-08-07-winforms-message-pump-test-seam-230/evidence/qa-gates/compile-include-wiring.2026-08-07T23-40.md`
(issue #230, task P7-T8, "Static `[TestMethod]` enumeration versus `/ListTests` discovery"):

1. Resolve `vstest.console.exe` via `vswhere` (pattern used repo-wide):
   ```powershell
   $vswhere = Join-Path ${env:ProgramFiles(x86)} 'Microsoft Visual Studio\Installer\vswhere.exe'
   $vstest = & $vswhere -latest -products * -find 'Common7\IDE\Extensions\TestPlatform\vstest.console.exe' | Select-Object -First 1
   ```
2. Full rebuild first (`MSBuild.exe UtilitiesCS.Test/UtilitiesCS.Test.csproj -t:Rebuild -p:Configuration=Debug -p:Platform="AnyCPU" -v:m`), so the discovered assembly reflects the current `<Compile>` set exactly (a `/t:Build` incremental no-op would not catch an unwired new file).
3. Discovery: `& $vstest UtilitiesCS.Test\bin\Debug\UtilitiesCS.Test.dll /ListTests`.
4. `/ListTests` enumerates every discovered test's fully-qualified name
   (`UtilitiesCS.Test.OutlookObjects.Folder.FolderPredictorTests.<MethodName>`) for the **whole
   assembly**; there is no `/ListTests`-plus-class-filter combination proven in this repo, so
   scoping to just `FolderPredictorTests` is done by **post-filtering the `/ListTests` text output**
   for lines ending in `.FolderPredictorTests.<MethodName>` (all 39 methods share the type's fully
   qualified name prefix regardless of which of the 5 files they now live in, since they are all
   the same merged partial type).
5. Compare that filtered count against a **static enumeration taken from source** (grep every
   `[TestMethod]`-preceded method name across the 5 post-split files) run both **before** the split
   (39, from the single file) and **after** the split (must still be 39, summed across the 5
   files). Equal pre/post counts on both the static side and the `/ListTests` side, with the two
   sides agreeing with each other, is the non-vacuous acceptance condition — this mirrors the #230
   evidence file's "Check 2" methodology exactly (§2a static count, §2c discovery count, §2d
   comparison).

**Caution carried over from item 1's known trap**: any `/TestCaseFilter:FullyQualifiedName~<X>`
used as a shortcut must filter on the **type name** `FolderPredictorTests`, never on any of the new
**file names** (`SuggestionsAndRecents`, `FolderLookupAndUiSeams`, `CreateFolderWorkflows`,
`TestSupport`) — those strings do not appear in any test's fully-qualified name, so a filter built
from a file name silently selects zero tests and exits 0 with `No test matches`, exactly as
happened in the confirmed #498 incident. `/ListTests`-then-grep is the safer verification because
it lists absolute fully-qualified type+method names, sidestepping this ambiguity entirely.

## 5. CSharpier interaction

`.csharpierignore` excludes `**/evidence/**`, `*.cobertura.xml`, `*.coverage`, `*.coveragexml`,
`*.trx`, `*.csproj`, `*.props`, `*.targets`. **It does not exclude `UtilitiesCS.Test/**` or any
`*.cs` path**, so all 5 new/modified `.cs` files under `UtilitiesCS.Test/OutlookObjects/Folder/`
are subject to `dotnet tool run csharpier format .` / `check .` exactly like every other test file
in the project. The `.csproj` edit itself (adding 4 `<Compile Include>` lines) is correctly outside
CSharpier's scope per the ignore file.

`.editorconfig` sets `csharp_style_namespace_declarations = block_scoped:silent` — a silent-severity
*preference* for block-scoped namespaces, not an enforced rule. The existing file already uses
block-scoped (`namespace X { ... }`), and every precedent split file found in §1 (StoreWrapperController_Tests
family, AppEventsTests.Helpers.cs, etc.) also uses block-scoped namespaces, so the new files should
match that existing block-scoped style for consistency, though `.editorconfig` would not fail a
build on a file-scoped alternative (severity is `silent`).

Two other `.editorconfig` facts relevant to safety of this change: `dotnet_analyzer_diagnostic.severity = suggestion`
is the global catch-all default (only `MSTEST0032` is elevated to `warning`), so any unused-`using`
diagnostic (IDE0005) introduced by giving every partial file a full copy of the original `using`
block stays at `suggestion` severity and cannot be promoted to a build error by
`/p:TreatWarningsAsErrors=true` (that flag only promotes `CS86xx` nullable diagnostics, and none of
these files carry `#nullable enable`, so nullable analysis does not apply to them at all — see
CLAUDE.md's `C#1.3` nullable-opt-in note).

## 6. Coverage exemption applicability

**Not applicable.** `FolderPredictorTests.cs` and its proposed successors are C# **test files**
under `UtilitiesCS.Test/`, not production code under test. The COM/VSTO/WinForms coverage
exemption defined in `.claude/rules/general-unit-test.md` and CLAUDE.md's "General Unit Test
Policy" section applies only to production classes (VSTO lifecycle classes, WinForms
Designer-generated code, Outlook Interop event handlers without an injectable seam) that are
*measured for coverage*. Test files are excluded from the coverage denominator entirely by the
policy's own baseline rule ("Configure coverage tooling to exclude test files"), independent of the
COM/VSTO exemption. The planner should not invoke or reference that exemption anywhere in the
#817 plan; it has no bearing on splitting a test file.

## Rejected alternatives

- **Non-partial-class split (extract shared setup into a separate `[TestClass]` or a base class
  with `[TestInitialize]`)**: rejected because it would change `TestContext`/lifecycle semantics
  and is not the pattern used anywhere else in this repo for the identical problem (file-size-only
  split of a single cohesive `[TestClass]`). Partial classes preserve identical MSTest discovery
  and runtime behavior with zero behavioral risk, and are proven in dozens of existing files.
- **Splitting along test-list alphabetical/insertion order rather than behavior** (e.g. mechanical
  `.Part2.cs`/`.Part3.cs`/`.Part4.cs`): viable and lower-effort, but the objective specifically
  requests behavioral groupings; the `.{GroupName}.cs` convention is equally well precedented (e.g.
  `StoreWrapperController_Tests.Launch.cs`) and produces a more legible diff and future
  maintenance path, so it is preferred here.
