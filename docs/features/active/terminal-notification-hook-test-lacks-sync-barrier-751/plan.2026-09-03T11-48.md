- **Long-running commands (binding on P0-T14, P0-T15, P3-T2, and P4-T5 — ten runs in total: one for P0-T14, three for P0-T15, five for P3-T2, one for P4-T5).** "Ten" counts recorded **runs**, not process launches. Step 4 below permits up to three launch attempts per run, so the launch budget across this plan is at most thirty; the ten figure is the number of results this plan records. A full-suite vstest run can exceed the agent tool timeout, and the vstest argument `/Logger:trx;LogFileName=<name>` does not survive re-quoting reliably through a `Start-Process -ArgumentList` array. Two consequences follow and this convention handles both.

  First, each such run is written to its own script file and launched as a file, never as an argument array carrying the vstest switches.

  Second, the launch is **detached**. `-Wait` is deliberately not used. `-Wait` blocks the launching shell for exactly as long as a direct invocation would, so it does not avoid the timeout it would exist to avoid; and an exit code that lives only in the launching shell's `$proc.ExitCode` is destroyed together with that shell if the shell is interrupted, with no way to recover it afterwards. The exit code is therefore made durable **by the script itself, on disk**, before any shell reads it.

  Step 1 — write a self-contained script. `coverage\logs\<task-id>.ps1` runs in a fresh process and inherits no variable from the launching shell. It must therefore begin with `Set-Location (git rev-parse --show-toplevel)`, then re-resolve `$vswhere` and `$vstest` internally exactly as the Toolchain resolution convention above specifies, and then run the vstest command line that the task names inside exactly this try/catch/finally form:

  ```powershell
  $ErrorActionPreference = 'Stop'
  $exitFile = 'coverage\logs\<task-id>.exit.txt'
  $code = $null
  try {
      $LASTEXITCODE = $null
      & $vstest <the vstest arguments this task names>
      $code = $LASTEXITCODE
      if ($null -eq $code) { $code = 9001 }
  }
  catch {
      $code = 9002
      $_ | Out-String | Set-Content -LiteralPath 'coverage\logs\<task-id>.fault.txt' -Encoding UTF8
  }
  finally {
      Set-Content -LiteralPath $exitFile -Value $code -Encoding UTF8
  }
  exit $code
  ```

  The `$LASTEXITCODE = $null` reset is load-bearing: the mandatory `Set-Location (git rev-parse --show-toplevel)` line that opens the script sets `$LASTEXITCODE` to 0, so without the reset an unresolved or unlaunchable `$vstest` would leave that stale 0 in place and be recorded as a successful run. `9001` means vstest never set an exit code; `9002` means a terminating error was caught. **`9001` and `9002` are not test results and must never be recorded as a task's `EXIT_CODE:`.** The `finally` block guarantees the exit file is written even when the run throws.

  Step 2 — launch detached and record the process id. Delete any stale exit file, any stale fault file, and this run's entire `/ResultsDirectory` first, so a leftover artifact from an earlier attempt can never be mistaken for this attempt's result. Purging the results directory is required for the same reason the exit file is purged and is not covered by it: step 4's completion witness is the TRX this run's `/Logger:trx;LogFileName=` names inside this run's `/ResultsDirectory`, and both a step-4 relaunch and a Restart-semantics restart of the Phase 4 pass re-run the identical command line into the identical directory, so a surviving TRX would satisfy the witness and would supply the Total/Passed/Failed counts the artifact records. Every run now owns its `/ResultsDirectory` exclusively (see the per-run subdirectory list in the Test-run output location convention above), so this purge cannot destroy a sibling run's evidence.

  ```powershell
  Remove-Item -LiteralPath '<this run''s /ResultsDirectory>' -Recurse -Force -ErrorAction SilentlyContinue
  New-Item -ItemType Directory -Path 'coverage\logs' -Force | Out-Null
  Set-Content -LiteralPath 'coverage\logs\<task-id>.ps1' -Value $scriptLines -Encoding UTF8
  Remove-Item -LiteralPath 'coverage\logs\<task-id>.exit.txt' -Force -ErrorAction SilentlyContinue
  Remove-Item -LiteralPath 'coverage\logs\<task-id>.fault.txt' -Force -ErrorAction SilentlyContinue
  $proc = Start-Process -FilePath 'pwsh' `
      -ArgumentList '-NoProfile', '-File', 'coverage\logs\<task-id>.ps1' `
      -WorkingDirectory (git rev-parse --show-toplevel) `
      -NoNewWindow -PassThru `
      -RedirectStandardOutput 'coverage\logs\<task-id>.out.txt' `
      -RedirectStandardError  'coverage\logs\<task-id>.err.txt'
  'LaunchedPid: {0}'   -f $proc.Id
  'LaunchedStart: {0}' -f $proc.StartTime.ToString('o')
  ```

  `-PassThru` is required because the printed pid is what step 3 polls and step 5 targets; `-WorkingDirectory` is required so the child's working directory does not depend on the launching shell's process-level current directory; `-Wait` must not be added. Record both printed values in the task's artifact as `LaunchedPid:` and `LaunchedStart:`. The launched child's working-directory correctness therefore rests on `-WorkingDirectory`, not on inherited shell state; the script's own opening `Set-Location (git rev-parse --show-toplevel)` is the second, independent guarantee of the same property. On every step-3 poll that reports the process alive, capture the descendant set and union it into the recorded `ChildPids:`, keeping first-observed order and each pid's `CreationDate`. A single capture is insufficient: under `/InIsolation` a new `testhost` is created per test assembly, so descendants of later assemblies do not exist at first-poll time and a set captured only then would leave them running after step 5. The capture query is:

  ```powershell
  Get-CimInstance Win32_Process -Filter 'ParentProcessId=<the recorded pid>' |
      Select-Object ProcessId, Name, CreationDate
  ```

  Repeat the query once for each returned `ProcessId` so `testhost` grandchildren of `vstest.console.exe` are captured, on each poll. If no poll ever reports the process alive — that is, the first poll already reports it not alive — no descendant set is observable and the artifact records `ChildPids: none captured (process exited before the first poll)`; step 5 then has no child pid to terminate and operates on the recorded `LaunchedPid:` alone.

  Step 3 — poll for completion in separate short shell invocations, so no single invocation is exposed to the run's full duration. Each poll runs `Get-Process -Id <the recorded pid> -ErrorAction SilentlyContinue` and treats the process as alive only when a process is returned AND its `StartTime.ToString('o')` equals the recorded `LaunchedStart:`. A returned process whose start time differs is an unrelated process that has inherited a recycled pid; treat it as not alive and record that fact. An empty return, or a start-time mismatch, is the completion signal. Each poll invocation begins with a bounded wait rather than an immediate read, so that the poll count maps to a known quantity of wall-clock time: run `Wait-Process -Id <the recorded pid> -Timeout 120 -ErrorAction SilentlyContinue` first, then perform the `Get-Process` check described above. Poll at most 40 times, which bounds a single attempt at approximately 80 minutes, and record the poll count and each poll's wall-clock timestamp in the task's artifact. A poll not preceded by its bounded wait does not count toward the 40 and must not be recorded: the 40-poll cap is a wall-clock bound expressed in polls, so an unwaited poll consumes the cap without giving the run time to progress and converts the hung-detection threshold into a few minutes. If the 40th poll still reports the process alive, stop polling, treat the run as hung, apply step 5 to terminate it, record the header `RUN_HUNG` with the sanitized tail of `coverage\logs\<task-id>.err.txt`, and relaunch under the step-4 attempt cap.

  Step 4 — read the durable exit code. Only after step 3 has produced a completion signal — an empty return or a start-time mismatch — run `Get-Content -LiteralPath 'coverage\logs\<task-id>.exit.txt'`. The `EXIT_CODE:` recorded in the artifact is that value and only that value; it is never taken from `$proc.ExitCode` and never from any other in-memory value in a launching shell. An exit code is accepted only together with a completion witness: the TRX named by this run's `/Logger:trx;LogFileName=` must exist under this run's `/ResultsDirectory` and must parse. Because step 2 purged that directory before the launch, the witness cannot be a survivor from an earlier attempt. The run did NOT complete, and the header `RUN_INCOMPLETE` applies, in any of these cases: the exit file is absent after the process exited; the exit file contains `9001` or `9002`; or the exit file contains a value but the witness TRX is absent or unparseable. In every `RUN_INCOMPLETE` or `RUN_HUNG` case the artifact records the header together with the sanitized tail of `coverage\logs\<task-id>.err.txt` and, when present, the content of `coverage\logs\<task-id>.fault.txt`, and the run is relaunched from step 1. A run may be relaunched at most twice, three attempts in total. If the third attempt is also `RUN_INCOMPLETE` or `RUN_HUNG`, stop: record the header `RUN_UNRECOVERABLE`, record no numeric `EXIT_CODE:`, and report the task as failed to the caller. The artifact always records how many attempts preceded the recorded result.

  Step 5 — before relaunching any run, and whenever step 3 declares a run hung, terminate that attempt's processes child-first: each pid recorded under `ChildPids:` in reverse capture order, then the recorded `LaunchedPid:`. Before each `Stop-Process -Id <pid> -Force -ErrorAction SilentlyContinue`, verify that the live process's `StartTime` (or `CreationDate` for a `ChildPids:` entry) matches the value recorded for that pid; a pid whose start time does not match has been reused by an unrelated process and must NOT be terminated. Never terminate by image name. A sibling worktree on this machine may be running its own `vstest.console.exe` and `testhost` concurrently, and an image-name kill would destroy that unrelated run rather than this plan's stalled one.

  The `Command:` field recorded in the artifact is the vstest command line written into the script file, and the artifact must also state that the command was executed from `coverage\logs\<task-id>.ps1`. `coverage\logs\` and every `.ps1`, `.out.txt`, `.err.txt`, `.exit.txt`, and `.fault.txt` file inside it are already ignored, so none of them can reach the porcelain output that the P4-T8 and P5-T14 gates depend on: `.gitignore:144` ignores `coverage/*` and `.gitignore:145` re-includes only `coverage/.gitkeep`, while `.gitignore:348` ignores `logs/`. All three line numbers were re-derived against the current tree in this pass.
- **Restart semantics.** The Phase 4 toolchain pass is exactly P4-T1 through P4-T5. If any of those five steps fails **its own stated acceptance**, or rewrites any tracked file, the pass is void: restart from P4-T1 and do not mark any of P4-T1 through P4-T5 complete from the void pass. ## Selected fail-before route (decision recorded here, executed in Phase 1)

`spec.md` Test Strategy offers two fail-before routes and requires exactly one to be executed. **This plan selects route 2: the `no-fail-before-rationale` dossier paired with the repeat-run stress record.** The reasons, which P1-T1 transcribes into the route-selection artifact:

1. Route 1 requires temporary instrumentation that defers the fixture's increment past the assertion point. Every deterministic deferral mechanism available at that site is barred by a constraint this plan must hold. A wall-clock deferral is a banned determinism API under `.claude/rules/general-unit-test.md` ("Determinism Infrastructure") and under spec AC8. A gate-object deferral requires a new field or a new `TaskCompletionSource` in `TaskMaster.Test/AppGlobals/AppOlObjectsFolderTreeServiceLifecycleTests.cs`, which stands at 490 of 500 lines and whose remaining headroom spec AC7 protects. A deferral that merely biases the scheduler is not deterministic, so it does not produce a reliable red.
2. The red route 1 would produce is manufactured by an edit that changes the fixture's own ordering. It demonstrates that deferring the increment makes an unsynchronised read observe 0, which restates the race rather than reproducing it, and the artifact is not reproducible from the landed tree because the instrumentation is reverted.
3. `spec.md` conditions route 2 on route 1 being "judged to exceed the change budget or the remaining line headroom". Reason 1 is exactly that condition, and P1-T1 records it as the invoked condition rather than as a general preference.
4. Route 2 has two in-repo precedents named by `spec.md`: the dossier shape at `docs/features/active/2026-09-02-test-determinism-and-hygiene-debt-729/evidence/other/no-fail-before-rationale.2026-09-02T10-30.md` and the repeat-run shape at `docs/features/archive/2026-08-08-wpf-dispatcher-yield-test-order-dependent-508/evidence/qa-gates/repeat-run-comparison.2026-08-08T17-03.md`. Both files were confirmed present in this worktree during plan authoring.
5. Route 2 is strengthened here beyond the minimum: P0-T15 captures a **pre-fix** three-run series and P3-T2 captures a **post-fix** five-run series under the same CI-shaped invocation, so the dossier's claim about pre-fix behaviour is backed by a recorded pre-fix observation rather than asserted. That observation is allowed to come out either way. If all three pre-fix runs are green, the dossier's negative claim ("a natural red is not reliably producible") stands and is evidenced. If any of the three records the target test as `Failed`, P0-T15's `NATURAL_RED_OBSERVED` branch applies: that is a genuine natural fail-before on the unmodified tree, it falsifies the negative claim, and P1-T2 must then cite the preserved TRX as the fail-before evidence instead of asserting non-reproducibility. The route selection is unaffected in either case, because route 1's defining act — adding temporary instrumentation — is still not performed.

Because route 2 is selected, **no instrumentation is added to any file at any point in this plan.** The AC6 clause "If route 1 is taken, no instrumentation remains in the branch diff" is satisfied vacuously and is additionally covered by the footprint gates P4-T8 and P4-T10.

## Coverage evidence approach (numeric pair captured; applicability re-derived by P4-T11)

- **Denominator argument, retained as a supporting statement rather than as the whole case.** The three edits this plan makes are all inside `TaskMaster.Test`.
