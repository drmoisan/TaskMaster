## Overview

Deliver a minimal C# bug fix that keeps Outlook COM access on the main STA/UI thread while reducing startup UI lockup by making store-rewire completion awaitable, moving only background-safe computation, parsing, deserialization, and disk I/O off-thread, and adding cooperative yield boundaries between heavy startup phases. The plan keeps the fix constrained to the startup coordinator and the identified `AppToDoObjects` risk paths; it does not authorize feature flags, schema changes, or unrelated startup architecture work.

## Scope Guardrails

- Outlook COM access must remain on the main Outlook STA/UI thread, including `Application`, `NamespaceMAPI`, `Store`, `Folder`, `Items`, reminder collections, inbox event hookup, and any COM-backed `MailItem` materialization.
- Only computation, parsing, deserialization of non-COM objects, classifier/model loading that does not dereference COM, and disk I/O may move to background work.
- The primary production-file budget for the fix is `TaskMaster/ThisAddIn.cs` only if coordinator entry behavior must change, `TaskMaster/AppGlobals/ApplicationGlobals.cs`, `TaskMaster/AppGlobals/AppOlObjects.cs`, `UtilitiesCS/OutlookObjects/Store/StoresWrapper.cs`, and `TaskMaster/AppGlobals/AppToDoObjects.cs`.
- `TaskMaster/AppGlobals/AppEvents.cs`, `TaskMaster/AppGlobals/AppAutoFileObjects.cs`, and `TaskMaster/AppGlobals/AppItemEngines.cs` remain out of scope unless the inspection artifact in [P1-T2] records direct evidence that one of those files must change to preserve COM affinity or startup responsiveness for issue `#141`.
- No new runtime configuration keys, no persisted-data/schema changes, and no redesign of unrelated startup subsystems are permitted.
