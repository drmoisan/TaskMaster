## Root-Cause Summary (verified against source)

- **Findings A and B (tests 1, 2, 3)** share a root cause in `UtilitiesCS/HelperClasses/FileSystem/FilePathHelper.cs`. Commit `0883d0f7` moved `PropertyChanged += FilePathHelper_PropertyChanged;` to the first line of the `(string fileName, string folderPath)` constructor (lines 26-32) and the private seed constructor (lines 34-47). The terminal `FilePath = Path.Combine(_folderPath, _fileName);` then re-enters the handler on the `FilePath` case (lines 356-381), which rewrites `_folderPath = Path.GetDirectoryName(_filePath)` and `_fileName = Path.GetFileName(_filePath)`. In the seed constructor `_fileName` is `""` at that line, so the combine yields the folder itself (`C:\data`), and the handler corrupts `FolderPath` to `C:\` and `FileName` to `data`. The `FolderPath`/`FileName`/`FileStemSeed` setters already recompute `_filePath` through the handler (lines 343-354, 382-402), so the terminal `FilePath = ...` assignment is redundant and is the corruption source.
- **Finding B (test 3)** routes through `UtilitiesCS/NewtonsoftHelpers/FilePathHelperConverter.cs` `ReadJson` (lines 26-39), which returns `new FilePathHelper(fileName, folderPath)`. The chosen FilePathHelper initialization must leave `_filePath` correctly computed for the direct-constructor path AND yield `Config.Disk.FileName == "pplkey.json"` after deserialization. The sibling test `People_DeserializeShortcut_CanDeserializePatternCorrectly` (PeopleScoConverter path, not ignored) is the working reference; it must remain passing.
- **Finding C (test 4)** in `UtilitiesCS/EmailIntelligence/SubjectMap/SubjectMapSco.Orchestration.cs` `Consume<T>` (lines 47-69) reports progress eagerly once (`progress.Report(0, ...)`, line 51) and otherwise only via a wall-clock `System.Threading.Timer` firing every 500ms (lines 53-64). The per-item `WithProgressReporting(count, x => completed = x)` callback (line 66) updates only a local `int` and never calls `progress.Report`. The test asserts `tracker.Reports.Count >= 2` within a 1-second `SpinWait`, which is wall-clock-timer dependent and flaky in CLI/CI. The deterministic seam is to drive per-item progress reporting through the existing `progress` tracker as the sequence is enumerated, so the "reports at least twice" intent no longer depends on the timer firing. This is an in-line reporting seam, not a sleep/retry/timing hack.
