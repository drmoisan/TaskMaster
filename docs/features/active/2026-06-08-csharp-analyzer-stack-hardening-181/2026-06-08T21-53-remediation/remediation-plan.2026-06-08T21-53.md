## Root-Cause Summary (verified against source this cycle)

- **Finding A (tests 1 and 2)** — `UtilitiesCS/HelperClasses/FileSystem/FilePathHelper.cs`. The private seed constructor `FilePathHelper(fileNameSeed, fileExtension, fileNameSuffix, folderPath)` (lines 34-47) ends with `FilePath = Path.Combine(_folderPath, _fileName);` (line 46). After commit `0883d0f7` moved `PropertyChanged += FilePathHelper_PropertyChanged;` to the first line of the constructor, that terminal assignment re-enters the `FilePath` handler while `_fileName` is empty (the seed setters populate `FileStemSeed`/`FileStemSuffix`/`FileExtension` but `_fileName` is empty at line 46), so the combine yields the folder itself and the handler then rewrites `_folderPath`/`_fileName`, corrupting `FolderPath` (`C:\data` -> `C:\`). The `FileStemSeed`/`FileStemSuffix`/`FileExtension`/`FolderPath` setters already recompute derived state via the handler, so the terminal `FilePath = Path.Combine(...)` is redundant and is the corruption source. This was confirmed correct in cycle 4. Fix: remove or guard that terminal assignment in the seed constructor. Touch point: `FilePathHelper.cs`.
- **Finding B (test 3)** — root cause is in the serialization layer, NOT `FilePathHelper.cs` (cycle-4 diagnostics in `evidence/regression-testing/scope-change-finding-B.2026-06-08T21-23.md` proved `new FilePathHelper("pplkey.json", folderPath)` already yields `FileName == "pplkey.json"` and that `FilePathHelperConverter.ReadJson` is never invoked for `Disk` in this test). Verified against source this cycle: `UtilitiesCS/NewtonsoftHelpers/WrapperScoDictionary.cs` declares `RemainingObject` as `object` (line 25). `ScoDictionaryConverter<TDerived,TKey,TValue>.ReadJson` (`UtilitiesCS/NewtonsoftHelpers/ScoDictionaryConverter.cs` lines 16-28) deserializes into `WrapperScoDictionary<...>` then calls `ToDerived()`. The test sets `settings.TypeNameHandling = TypeNameHandling.None` (`PeopleScoDictionaryNewTests.cs` line 243), so Newtonsoft binds the untyped `RemainingObject` to a `JObject` (no `$type` to bind a concrete type). `WrapperScoDictionary.ToDerived()` (lines 39-142) then reflects over `RemainingObject.GetType()` for `<Config>k__BackingField` / `_Config` field or a `Config` property (lines 54-73); on a `JObject` all those lookups return null, `configValue` stays null, and `derivedInstance.Config` is left at its default (`new NewSmartSerializableConfig()` with an empty `Disk`, so `Config.Disk.FileName == ""`). The working sibling `People_DeserializeShortcut_CanDeserializePatternCorrectly` (lines 261-279) uses the different `PeopleScoConverter` path and passes; it is the no-regression reference. Required fix: apply the minimal change in `WrapperScoDictionary.cs` and/or `ScoDictionaryConverter.cs` so deserialization under `TypeNameHandling.None` reconstitutes `Config` from the `JObject` (for example, reading the `Config` member out of the `JObject` and materializing a typed `NewSmartSerializableConfig`, or binding `RemainingObject` to a concrete type), yielding `people.Config.Disk.FileName == "pplkey.json"` while leaving the `PeopleScoConverter`/shortcut path and all other `ScoDictionaryConverter` consumers behaviorally unchanged. Touch points authorized for Finding B: `UtilitiesCS/NewtonsoftHelpers/WrapperScoDictionary.cs` and/or `UtilitiesCS/NewtonsoftHelpers/ScoDictionaryConverter.cs`. If a correct fix requires any other production file, HALT and escalate per G5 (Scope-Change Rule) — do not widen scope in place.
- **Finding C (test 4)** — `UtilitiesCS/EmailIntelligence/SubjectMap/SubjectMapSco.Orchestration.cs`. `Consume<T>` (lines 47-69) reports progress eagerly once (`progress.Report(0, ...)`, line 51) and otherwise only via a wall-clock `System.Threading.Timer` firing every 500ms (lines 53-64); the per-item `WithProgressReporting(count, (x) => completed = x)` callback (line 66) only updates a local `int` and never calls `progress.Report`. The test asserts `tracker.Reports.Count >= 2` within a 1-second `SpinWait` and a report `JobName.StartsWith("Consuming ")` (`SubjectMapSco_Orchestration_Tests.cs` lines 144-163), which depends on the timer firing and is flaky under full-suite load (passes in isolation). Deterministic fix: report progress per consumed item through the existing injected `progress` tracker (so the per-item callback both updates `completed` and calls `progress.Report(..., $"Consuming ... of ...")`), removing the test's reliance on the wall-clock timer for the "reports at least twice" behavior. This is an in-line reporting seam, not a sleep/retry/timing hack. Touch point: `SubjectMapSco.Orchestration.cs`.
