Both forms are used deliberately below: the collapsed form where a directory-level statement is what the gate needs, and the `--untracked-files=all` form where individual artifact paths must be enumerable.

**DIFF BASE.** Every `git diff` in this plan is anchored to one commit, captured once by [P0-T2] as `git merge-base HEAD origin/main` and recorded there under the label `Diff base:`. Below, the token `<DIFF-BASE>` stands for that recorded value, which the executor substitutes verbatim as the ref operand. The tasks that take it are [P2-T6], [P5-T7], [P5-T9] and [P5-T10]. Anchoring to the literal ref `origin/main` is prohibited in this plan: the current `HEAD` is a merge commit whose second parent is `origin/main`, and that remote ref can advance under this branch mid-run, which would silently change what every one of those four gates measures without any of them failing. Pinning the base makes all four gates measure the same span whenever they run.

This does not conflict with the rule in [P0-T2] that no commit SHA is a plan expectation, and the two statements are reconciled here rather than left in tension. A plan expectation would be an acceptance condition asserting that some SHA equals a value written into this plan; no task in this plan contains one, and the specific SHAs quoted in the delegation context are deliberately absent from every acceptance condition. `<DIFF-BASE>` is used only as a command **operand**: the executor passes the recorded value to `git diff`, and the acceptance conditions are about the diff's content, never about the operand's value. An operand read from an artifact at run time is therefore permitted, while an expected-SHA assertion remains prohibited.

## Coverage collection procedure (replaces the runner script)

**COVERAGE COLLECTION PROCEDURE.** `pwsh -File scripts\vscode\Invoke-MSTestWithCoverage.ps1` must not be invoked as a script anywhere in this plan. Re-derived this pass, its test-assembly discovery at `scripts/vscode/Invoke-MSTestWithCoverage.ps1:296-303` ends with the predicate `$_.FullName -notmatch '\\\.claude\\'` at `:301`. This worktree's own absolute path contains the segment `\.claude\`, so every built assembly in it fails that predicate, `$testAssemblies` is empty, and the script throws `"No test assemblies found under ... Build first."` at `:305-307` and writes no Cobertura document at all. That is an environment defect tracked as repository issue #752, not a defect in this issue's fix; this plan works around it and does not fix it.

Both [P0-T9] and [P5-T5] instead perform the following procedure, which reuses the script's own collection seam rather than hand-rolling a `vstest.console.exe` command line. Hand-rolling is prohibited here because `Get-DotnetCoverageArgumentList` appends `"/Settings:$RunSettingsPath"`, `/InIsolation` and `/TestCaseFilter:TestCategory!=LiveOutlook` to the inner vstest invocation at `scripts/vscode/Invoke-MSTestWithCoverage.ps1:76`, and a bare vstest command that omitted that filter would attempt the live-Outlook tests.

1. Build first, with `msbuild TaskMaster.sln /t:Build /m /p:Configuration=Debug "/p:Platform=Any CPU"`, so the assemblies exist.
2. Dot-source both `scripts/vscode/Invoke-MSTestWithCoverage.ps1` and `scripts/vscode/Invoke-MSTestWithCoverage.Helpers.ps1`. Dot-sourcing the first is safe: its entry point is guarded by `if ($MyInvocation.InvocationName -ne '.')` at `:348`, so nothing runs at dot-source time except the function declarations and the two preference statements at `:245-246`. Dot-sourcing the second brings in `ConvertTo-KoverageCoberturaXml` (`scripts/vscode/Invoke-MSTestWithCoverage.Helpers.ps1:405`) and, through the three dot-sources at `Invoke-MSTestWithCoverage.Helpers.ps1:2-4`, also `Remove-CoberturaExemptClosureCoverage` (`scripts/vscode/Invoke-MSTestWithCoverage.ClosureFilter.ps1:235`) and `Assert-CoberturaLineCoverageThreshold` (`scripts/vscode/Invoke-MSTestWithCoverage.Threshold.ps1:3`).
3. **Strict-mode note.** Dot-sourcing executes `Set-StrictMode -Version Latest` and `$ErrorActionPreference = 'Stop'` in the calling scope (`Invoke-MSTestWithCoverage.ps1:245-246`, and `Invoke-MSTestWithCoverage.Helpers.ps1:1`). Every snippet the executor writes afterwards must therefore read XML attributes through `GetAttribute('...')` rather than bare property access, which is why the repository's own helper does so and says so at `Invoke-MSTestWithCoverage.Helpers.ps1:197-201`.
4. Build the test-assembly list mechanically, by the script's own rule minus the one broken predicate: enumerate `*.Test.dll` recursively under the worktree root, keep those whose full path matches `\\bin\\Debug\\` and does not match `\\obj\\` or `\\ref\\`, and then apply the nested-worktree exclusion to the path **relative to the worktree root** — `[IO.Path]::GetRelativePath($worktreeRoot, $_.FullName) -notmatch '(^|\\)\.claude\\'` — rather than to the absolute path. Applying it to the absolute path is exactly the defect being worked around: the worktree root itself contains that segment. Applying it to the relative remainder preserves the predicate's actual purpose, which is to exclude assemblies belonging to a nested agent worktree. The leading `(^|\\)` alternation is load-bearing and must not be reduced to the script's `\\\.claude\\`: `GetRelativePath` returns a remainder with no leading separator, so a nested worktree's assembly would begin `.claude\worktrees\...` with no backslash before it, and the separator-only form would fail to exclude the very paths the predicate exists to exclude.
5. Resolve `vstest.console.exe` with the same vswhere invocation the rest of this plan uses: `& "${env:ProgramFiles(x86)}\Microsoft Visual Studio\Installer\vswhere.exe" -latest -products * -find "Common7\IDE\Extensions\TestPlatform\vstest.console.exe"`, taking the first result.
6. Ensure the `coverage` directory exists before collecting. `Invoke-DotnetCoverageCollection` writes a derived settings file adjacent to the requested output (`Get-DerivedCoverageSettingsPath`, `Invoke-MSTestWithCoverage.ps1:118`) and removes it in a `finally` block, so the output's parent directory must already exist. `coverage/.gitkeep` is present in the tree this pass, so the directory exists; create it if it does not.
7. Call `Invoke-DotnetCoverageCollection` with all five of its mandatory parameters (`Invoke-MSTestWithCoverage.ps1:172`, parameters at `:181-196`): `-OutputPath` set to the RAW path for this phase, `-CoverageConfig` set to the repository-root `coverage.config` (which is the file the script itself resolves at `:321`), `-VsTestPath` set to the resolved vstest console, `-TestAssembly` set to the list from step 4, and `-RunSettingsPath` set to `scripts\vscode\TaskMaster.cli.runsettings` (the file `Resolve-RunSettingsPath` resolves at `:15-39`). Passing `-TestAssembly` explicitly is what bypasses the broken discovery while preserving every other collection semantic.
8. **Wrap the call in `try`/`catch` and continue past a failure.** `Invoke-DotnetCoverageCollection` throws at `:235-237` when the inner run exits non-zero, which is what a failing test produces — but that throw happens after `dotnet-coverage` has already written the raw Cobertura document. Record the outcome as `0` when the call returned without throwing, and otherwise as the non-zero child exit code the thrown message reports, and then continue to step 9 regardless. Redirect the call's full console output (`*>&1`) through a streaming writer to a file — `Tee-Object -FilePath` on the redirected pipeline, or an enclosing `Start-Transcript` — so that the vstest total/passed/failed/skipped summary lines and the failing- and skipped-test name lists are on disk before the throw reaches the `catch`. Assigning the redirected output to a variable is prohibited and is not an equivalent option: a terminating error aborts the assignment statement, so the variable keeps its prior value and the whole summary is lost in exactly the failing-run state that Axis C row C3 and [P0-T9]'s name-list acceptance depend on. The throw at `:235-237` happens after the child process has already printed those lines, so a streaming writer captures them; nothing else does.
9. **Post-process explicitly.** Read the raw document, call `ConvertTo-KoverageCoberturaXml -XmlContent <raw content> -RepoRoot <worktree root absolute path>`, and write the returned string to the PROCESSED path for this phase. Do not write it back over the raw path. Because this step runs outside the try/catch, both documents this plan produces are always in the `processed` state, whatever the test outcome was.

All four are under `coverage/`, which is gitignored at `.gitignore:144` (`coverage/*`, with only `!coverage/.gitkeep` re-included at `:145`, re-derived this pass), so none of them enters any Phase 5 porcelain or anchored-diff gate.

## DEGRADED-RUN STATE MODEL

Phase 5 and Phase 6 contain several conditional gates. Every branch condition those gates use is declared once here and referenced by row name from [P5-T1], [P5-T2], [P5-T5], [P5-T6], [P5-T7] and [P6-T18]. Those six tasks do not re-derive the branch conditions locally. This block exists because a previous revision let each task derive its own condition, which produced two tasks making contradictory claims about the same state.

**The two source inputs.**

Exactly two facts observed in Phase 0 are inputs to any Phase 5 or Phase 6 branch:

- **Input F** — the exit code [P0-T6] records for `dotnet tool run csharpier check .` on the pre-change tree.
- **Input T** — the test-run outcome [P0-T9] records for the COVERAGE COLLECTION PROCEDURE on the pre-change tree: `0` when `Invoke-DotnetCoverageCollection` returned without throwing, and otherwise the non-zero child exit code the thrown message reports.

**The Cobertura document state is no longer a branch input.** It was one in earlier revisions of this plan, when the runner script's own control flow decided whether the on-disk document had been post-processed. Under the COVERAGE COLLECTION PROCEDURE the executor calls `ConvertTo-KoverageCoberturaXml` itself, at step 9, outside the `try`/`catch` that absorbs a failing test run, and writes the result to a separate processed path. Both the Phase 0 document and the Phase 5 document are therefore always in the `processed` state, whatever the test outcome was, and a raw/processed mismatch between the two is unreachable by construction. The `Cobertura document state:` line that [P0-T10] and [P5-T6] each record is retained as a cheap audit assertion rather than as a discriminator: the accepted value is `processed` in both, and if either records anything else the executor stops and reports a blocked coverage comparison rather than selecting a row on a false premise.

A missing document is a blocked state rather than a degraded one. If the processed document for a phase is absent after that phase's collection, the dependent extraction task cannot produce its numeric values; the executor stops and reports a blocked toolchain rather than continuing.

Also derived rather than independent: **[P5-T5]'s own exit code is constrained by Input T.** When Input T is 0, [P5-T5]'s acceptance requires a test outcome of 0, so a non-zero [P5-T5] result in that state is a failure of [P5-T5] and the Phase 5 preamble restarts the loop from [P5-T1].
