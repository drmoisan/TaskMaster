## DEGRADED-RUN STATE MODEL

Phase 5 and Phase 6 contain several conditional gates. Every branch condition those gates use is declared once here and referenced by row name from [P5-T1], [P5-T2], [P5-T5], [P5-T6], [P5-T7] and [P6-T18]. Those six tasks do not re-derive the branch conditions locally. This block exists because a previous revision let each task derive its own condition, which produced two tasks making contradictory claims about the same state. The derivation below is also audited rather than assumed: [P0-T10] and [P5-T6] each cross-check the document state they observe against the exit code that is supposed to determine it, and stop and report if the two disagree.

**The two source inputs, and what is derived from them.**

Exactly two facts observed in Phase 0 are independent inputs to any Phase 5 or Phase 6 branch:

- **Input F** — the exit code [P0-T6] records for `dotnet tool run csharpier check .` on the pre-change tree.
- **Input T** — the exit code [P0-T9] records for `pwsh -File scripts\vscode\Invoke-MSTestWithCoverage.ps1 -SearchRoot . -Configuration Debug` on the pre-change tree.

The Cobertura **document state** (`raw` or `processed`) is **not** a third independent input. It is a deterministic function of the exit code of the run that produced the document. Re-derived against the current tree this pass: `scripts/vscode/Invoke-MSTestWithCoverage.ps1` invokes the collection at `:326-331`, and `Invoke-DotnetCoverageCollection` throws at `:236` (`throw "MSTest with coverage failed with exit code $coverageExitCode"`) whenever the `dotnet-coverage`/vstest child process exits non-zero, which is what a failing test produces. If that throw does not occur, the script reads the document at `:339`, converts it at `:340`, asserts the 80 percent repository floor at `:341`, and only then writes the converted content back over `coverage\coverage.cobertura.xml` at `:343`. The floor assert is `Assert-CoberturaLineCoverageThreshold`, which throws at `scripts/vscode/Invoke-MSTestWithCoverage.Helpers.ps1:487-489`. `Set-StrictMode -Version Latest` and `$ErrorActionPreference = 'Stop'` are set at `Invoke-MSTestWithCoverage.ps1:245-246`, so either throw terminates the script and line `:343` never runs. Therefore, for the exact command this plan runs — which never passes `-NoExecute`, the one switch that would return at `:323` before any collection or write:

- a recorded exit code of **0** means the on-disk `coverage\coverage.cobertura.xml` is in the **`processed`** state;
- a recorded **non-zero** exit code means that document is in the **`raw`** state, or that no document was produced at all.

The second disjunct is a blocked state rather than a degraded one. If `coverage\coverage.cobertura.xml` is absent after [P0-T9], [P0-T10] cannot produce its five numeric values; the executor stops and reports a blocked toolchain rather than continuing into Phase 1.

Also derived rather than independent: **[P5-T5]'s own exit code is constrained by Input T.** When Input T is 0, [P5-T5]'s acceptance requires exit 0, so a non-zero [P5-T5] result in that state is a failure of [P5-T5] and the Phase 5 preamble restarts the loop from [P5-T1]. The pair (Input T, [P5-T5] exit code) therefore has three reachable values, not four.

**AXIS F — format baseline.** Governs [P5-T1] and [P5-T2], and contributes one conjunct to [P6-T18]. Independent of Axis C.

| Row | Condition | [P5-T1] | [P5-T2] |
|---|---|---|---|
| **F-CLEAN** | [P0-T6] recorded `EXIT_CODE: 0` | repository-wide `dotnet tool run csharpier format .` | `dotnet tool run csharpier check .` |
| **F-DRIFT** | [P0-T6] recorded a non-zero exit code | scoped format over exactly the eleven PLAN WRITE SET source paths | scoped check over the same eleven paths |

F-DRIFT exists because pre-existing repository-wide formatting drift means a repository-wide format rewrites files this issue does not own, which would breach the [P5-T9] scope gate.

**AXIS C — coverage baseline and coverage re-run.** Governs [P5-T5]'s bar, both documents' states, whether [P5-T6] Branch A is available at all, whether [P5-T7]'s changed-line comparison is in force, and the other conjunct of [P6-T18].

| Row | Input T | [P5-T5] exit | Baseline doc ([P0-T10]) | This-run doc ([P5-T6]) | Doc states | [P5-T5] bar | [P5-T6] branch | [P5-T7] changed-line gate | Coverage gate actually in force | [P6-T18] AC17 |
|---|---|---|---|---|---|---|---|---|---|---|
| **C1** | 0 | 0 (required) | `processed` | `processed` | match | absolute: exit 0 and failed count 0 | A or B, selected by Axis D | in force, hard gate | changed-line no-regression | check off when Axis F is F-CLEAN |
| **C2** | non-zero | 0 | `raw` | `processed` | **differ** | subset-of-baseline; the failing list is necessarily empty because exit 0 implies no test failed, but the skipped-list subset check still applies | **B, forced** | **not in force** | the 80 percent absolute floor, which necessarily passed | check off when Axis F is F-CLEAN |
| **C3** | non-zero | non-zero | `raw` | `raw` | match | subset-of-baseline failing and skipped name lists | A or B, selected by Axis D | in force, hard gate | changed-line no-regression | leave unchecked |
| **C-X** | 0 | non-zero | — | — | — | unreachable | — | — | — | — |

**C-X is unreachable and no procedure is given for it.** It would require Input T of 0 together with a non-zero [P5-T5] exit code, but [P5-T5]'s bar for an Input-T-of-0 baseline requires exit 0 with a failed count of 0. A non-zero [P5-T5] result in that state is a failure of the task, and the Phase 5 preamble restarts the loop from [P5-T1] and rewrites all the artifacts, so [P5-T6] and [P5-T7] never run with that precondition. If the executor nevertheless observes this combination, it stops and reports a blocked coverage comparison rather than improvising a procedure.

**Invariant: exactly one coverage gate is in force in every reachable row, and it is never vacuous.** In C1 and C3 the two documents are in the same post-processing state, so the per-line `hits` comparison in [P5-T7] compares like with like and is a hard gate. In C2 they are not, so no no-regression comparison — repository-wide or changed-line — is available at all; but C2 is reachable only when [P5-T5] exited 0, which by the derivation above means the run reached `Invoke-MSTestWithCoverage.ps1:343`, which means the `:341` floor assert passed, which means post-change repository line coverage is at or above the 80 percent absolute floor. No reachable row leaves this plan claiming a coverage gate it does not have, and no reachable row leaves it with no coverage evidence.

**AXIS D — denominator comparability.** Axis D is **not** collapsible into Axis C and does not become extra rows of it. Axis C is derived entirely from two Phase 0 exit codes, which are known before [P5-T6] runs. Axis D is a measurement taken from the two coverage documents' own numbers at [P5-T6] time, and its outcome is not determined by either exit code: two runs that both exited 0 can still report different `lines-valid` figures, because `dotnet-coverage` instruments whichever assemblies were loaded at run time. It is therefore an orthogonal axis with its own two rows, applied within an Axis C row rather than crossed into the table above.

| Row | Condition | [P5-T6] branch |
|---|---|---|
| **D-COMPARABLE** | the two `lines-valid` figures differ by at most 1 percent of the baseline figure | Branch A |
| **D-INCOMPARABLE** | they differ by more than 1 percent of the baseline figure | Branch B |

Axis D is measured and applied only in rows C1 and C3. **In row C2, Branch B applies regardless of the Axis D arithmetic**, because a `raw` document counts third-party packages and unfiltered closure lines that a `processed` one does not — `ConvertTo-KoverageCoberturaXml` removes the non-allowlisted packages at `Invoke-MSTestWithCoverage.Helpers.ps1:417-421` and calls `Remove-CoberturaExemptClosureCoverage` (`scripts/vscode/Invoke-MSTestWithCoverage.ClosureFilter.ps1:211`) at `:427` — so the two denominators are not two measurements of the same population and the Axis D arithmetic would be meaningless rather than merely borderline.

**Unit note for Axis D and Branch A.** The Cobertura `line-rate` attribute is a **fraction in the closed interval 0 to 1**, not a percentage. Re-derived this pass: `Assert-CoberturaLineCoverageThreshold` range-checks it with `if ($lineRate -lt 0 -or $lineRate -gt 1)` at `scripts/vscode/Invoke-MSTestWithCoverage.Helpers.ps1:482-484` and multiplies it by 100 to obtain a percentage at `:486`. Every bar this plan states against `line-rate` is therefore stated in rate units. Branch A's bar is **0.005 in rate units**, which is the intended half-percentage-point bar; stating that bar as "0.5" against two raw fractions would be a bar no measurement on this harness could breach.
