## Executive Summary

This is a minimal, well-targeted bug fix. `QfcDatamodel.InitEmailQueue` previously had no guard for `batchSize <= 0`, so High-Confidence mode's intentional zero-batch call fell through to an unconditional Deedle slice-and-project (`_frame.GetRowsAt(Enumerable.Range(0, 0))` -> `GetRowsAs<IEmailSortInfo>()`), which throws on an empty column index. The fix adds a short early-return guard before the existing clamp/slice logic, leaving the `batchSize > 0` path unchanged (confirmed by diff inspection). A companion `RemainingEmailLoader` injectable-delegate seam was added so the new tests (which necessarily start a real `BackgroundWorker`) do not trigger the production `MessageBox.Show`/live-Outlook-COM path.

Independent verification performed for this re-review: read the full production diff; re-ran `dotnet tool run csharpier check` on both touched `.cs` files (clean, exit 0); confirmed the `batchSize > 0` branch is textually unchanged below the new guard; confirmed both file sizes remain under the 500-line limit (471 and 212 lines); confirmed no banned APIs (`Thread.Sleep`, `Task.Delay`, `DateTime.Now`) appear in the new/changed lines; confirmed the code under review is byte-identical to what cycle-1's code-review evaluated (no new commits touched `.cs`/`.csproj` files between cycles).

No functional defects were found in the shipped fix. The two non-blocking quality observations from cycle 1 remain open as documented follow-up recommendations. The cycle-1 blocking, process-level coverage-artifact gap is now resolved at the policy level by the governance exception `244-COV-001` (see `policy-audit.2026-07-06T19-37.md` sections 5, 8, 10) and is not treated as a code defect here.
