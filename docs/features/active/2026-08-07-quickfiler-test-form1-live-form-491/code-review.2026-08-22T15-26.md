## Detailed Analysis Against the Review Focus Areas

### 1. Guard-test design (reflection-only, no live construction)

Verified sound by full read of `NoLiveFormInTestAssemblyTests.cs`. The single test method reflects over `Assembly.GetExecutingAssembly().GetTypes()`, filters with `formType.IsAssignableFrom(candidate)`, and asserts the result is empty via FluentAssertions with a descriptive `because` string. There is no `new Form(...)`, no control construction, no `BackgroundWorker`, and no `Show()`/`ShowDialog()` call anywhere in the file. The `GetLoadableTypes` helper catches only `ReflectionTypeLoadException` and returns the loaded-types subset — a narrowly scoped resilience measure against a large test assembly hitting an unrelated type-load failure, not a broad catch-all that could mask the guard's own assertion. The guard is scoped exclusively to the executing assembly (never a referenced assembly), matching the acceptance criterion's wording exactly.

### 2. Load-bearing proof: the guard caught a real defect mid-execution

The guard is not merely well-formed; it demonstrably works. During Phase 1, before `Form1` was deleted, the guard correctly failed red (exit 1) naming `Form1`-adjacent state, but the FluentAssertions failure message read from the log named a *different* type: `QuickFiler.Controllers.Tests.QfcHomeControllerTests+QfcFormViewerDerived`. The executor investigated rather than assuming the failure was `Form1`-related, discovered the type was a dead nested test-double (`git grep` confirmed zero instantiations anywhere in the repository), and correctly classified it as squarely within issue #491's own defect class (a `Form`-derived type compiled into the test assembly with no caller) rather than an unrelated, scope-widening finding. The disposition record (`remediation-inputs.2026-08-22T09-40.md`) documents this reasoning explicitly and correctly, including why the alternative (declaring it out-of-scope and narrowing the guard) was rejected.

### 3. `.csproj` edit confinement

Independently diffed the full file against the merge base. The edit removes exactly the two `Form1.cs`/`Form1.Designer.cs` `<Compile Include>` entries and the one `Form1.resx` `<EmbeddedResource Include>` `<ItemGroup>`, and adds one `<Compile Include="NoLiveFormInTestAssemblyTests.cs" />` line in the same block that held the removed entries. A separate independent grep confirmed all `<Reference Include>` lines (`System.Drawing`, `System.Drawing.Design`, `System.Windows.Forms`, and every other reference) are present and byte-identical at head. `git log --grep` for the sibling epic children's issue numbers (#511, #571, #445, #449) against this same `.csproj` file confirms only #449 has touched it historically, and its own commit (`05156a3a`) is not part of this branch — no live overlap was found on this branch.

### 4. Test quality (positive/negative coverage of the guard's own behavior)

The guard is a single-assertion structural test by design — the acceptance criterion calls for exactly one behavior (no `Form`-derived type compiled into the assembly), and a single test fully covers that behavior's positive case (empty result -> pass) and its negative case was exercised twice in practice: first against `Form1` (red, then fixed), then against the newly discovered `QfcFormViewerDerived` (red, then fixed). This is a stronger demonstration of negative-path coverage than a synthetic unit test could provide, since both red states were genuine pre-existing defects rather than constructed fixtures.

The `Form1` type and its associated designer/resx assets are deleted; the assembly no longer compiles any `Form`-derived type (verified: the guard is green post-remediation, and the full 6438-test suite passes with the guard included). The permanent guard converts this from a one-time fix into a standing structural invariant, which is the strongest available proof that the defect class cannot silently recur.
