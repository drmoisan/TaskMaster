## 3. Fixed execution rules (binding on every task in this plan)

1. **Shell.** Every C# toolchain command runs through `pwsh -NoProfile -Command` or `pwsh -NoProfile -File`. Never invoke MSBuild, vstest, csharpier, or nuget through the Bash tool: the Bash tool is Git Bash and rewrites MSBuild `/switch` arguments into paths (`/m` becomes `M:/`, producing `error MSB1008`). This is a hard requirement.
2. **Restore first.** A clean build fails with CS0246 on `log4net` / `SvgDocument` until `nuget restore TaskMaster.sln` has run. Run the restore (P0-T5) before any build.
3. **Absolute tool paths.** `csharpier`, `MSBuild.exe`, and `vstest.console.exe` are not on PATH. Use `<CSHARPIER>`, `<MSBUILD>`, `<VSTEST>` exactly as tabulated above. `nuget` is on PATH.
4. **CSharpier subcommands only.** Formatting gates use `csharpier format <paths>` (mutates on disk) followed by `csharpier check` returning `EXIT_CODE: 0`. `csharpier pipe-files` is prohibited as a gate: it writes to stdout only, never mutates, and produces a false "stable" result.
5. **CSharpier scope guard.** `csharpier format` is invoked with the explicit scope-locked `.cs` path list from section 4 and is NEVER invoked repo-wide, and NEVER with `TaskMaster\AppGlobals\AppItemEngines.cs` or `UtilitiesCS\Interfaces\IGlobals\IAppItemEngines.cs` in its argument list. Reason: a repo-wide `csharpier format .` would reformat any file that is unformatted at the merge-base, which would break the AC15 zero-line-diff requirement. `csharpier check .` (read-only) is still run repo-wide as the comparison gate.
6. **Legacy csproj wiring is mandatory and is part of each file-creation task.** `TaskMaster\TaskMaster.csproj` and `TaskMaster.Test\TaskMaster.Test.csproj` are non-SDK `packages.config` projects that enumerate every source file with an explicit `<Compile Include>` item and no glob. A new `.cs` file WILL NOT COMPILE into the assembly without its own `<Compile Include>` entry. Each file-creation task below has a single binary outcome that includes both the file and its csproj entry. Do not add a `<Compile Include>` entry before its target file exists — MSBuild fails the build when a `Compile` item points at a missing file.
7. **Pre-existing baseline failure handling.** The merge-base test suite is NOT green. `YieldAsync_WithoutDispatcher_RemainsStrict` in `UtilitiesCS.Test\OutlookObjects\Folder\WpfDispatcherYieldTests.cs` is a pre-existing order-dependent flake already promoted to issue **#508** and is explicitly OUT OF SCOPE for #503. 8. **No HEAD SHA is pinned as a plan expectation.** P0-T4 records the current HEAD for the audit trail. All later gates are expressed as tree invariants (clean `git status --porcelain`, and no `.cs` / `.csproj` / `.xml` diff outside the scope lock relative to `<MERGE_BASE>`), never as equality against a recorded SHA.
9. **One acceptance criterion per check-off task.** Phase 7 check-off tasks each flip exactly one `- [ ]` to `- [x]` in `<FEATURE>\spec.md`, with that criterion's own evidence pointer. Batched check-offs are prohibited.

#### 5.3 Readiness contract

Engine key `k` is ready if and only if: the accessor returns a non-null `IAppItemEngines`; `InboxEngines` is non-null; `InboxEngines.TryGetValue(k, out var e)` is `true`; and `e` is not null. String comparison is the `ConcurrentDictionary` default — ordinal and case-sensitive, so `"spam"` is not `"Spam"`. Readiness is recomputed on every query and never cached in the gate. A null or whitespace `engineName` yields `false`.

#### 5.4 Runner contract

`RunAsync(controlId, action)`: a null `action` throws `ArgumentNullException` before any readiness evaluation. When `IsCommandEnabled(controlId)` is `false`, emit exactly one notification through the injected `Action<string>` sink and return a completed task WITHOUT invoking `action`. Otherwise `await action()` and let any exception propagate unchanged.

Notification content: for a mapped control id the message contains both the control id and the engine key. For an unmapped/unknown/null/empty control id the message contains the supplied control id (rendered as `(null)` when null) and the literal token `(unmapped)` in place of an engine key. This branch is pinned here so tests and implementation cannot disagree.

#### 5.5 Readiness accessor

`RibbonController.EngineCommands.cs` builds `new EngineReadinessGate(() => Globals?.Engines)`. The `?.` is what makes the pre-`SetGlobals` case safe. Do NOT use the existing `RibbonController.Engines` (`RibbonController.Intelligence.cs:204`) as the accessor — it is not null-safe on `Globals`. Do NOT route the readiness decision through `RibbonController.SB` / `Triage` / `TriageAsync`: those getters install a real `WindowsFormsSynchronizationContext` on the calling thread as a side effect.

#### 5.6 Notification presentation (recorded decision, see section 9 item D3)

The sink implementation lives in the `[ExcludeFromCodeCoverage]` shim and writes one `logger.Warn(message)` line through the existing log4net logger and one `MessageBox.Show(message)` call, matching the established user-facing notice mechanism already used at `RibbonViewer.cs:413`, `RibbonController.cs:80,167,189,196`, and `RibbonController.FolderTree.cs:250,263`. No `Form`, `MessageBox`, or message pump is constructed in any test; tests assert on the injected `Action<string>` sink only.
