## 1. Objective and expected outcome

Fix three causally coupled defects in the Spam Config and Triage Config ribbon submenu callbacks of `TaskMaster\Ribbon\RibbonViewer.EngineCommands.cs`:

1. **#505** — `SpamBayesEnabled_GetPressed` and `TriageEnabled_GetPressed` are `async Task<bool>`; Office requires a synchronous `public bool <Name>(Office.IRibbonControl control)` and VSTO silently ignores the mismatch, so the toggles never reflect real engine activation state.
2. **#506** — `SpamBayesEnabled_Click` and `TriageEnabled_Click` discard the `Task` returned by `ToggleEngineAsync`; no completion ordering, faults become unobserved tasks.
3. **#518** — ten `Controller.Engines.<member>` call sites dereference the (post-#507) null-returning `Engines` property with no guard.

Expected outcome: one new host-neutral `internal sealed EngineToggleStateCoordinator` (cached synchronous `getPressed`, at-most-one async prime per key, awaited toggle with update-before-invalidate ordering, observed-and-logged click boundary) plus a sibling `EngineToggleCatalog` engine-key-to-control-id map, both deliberately NOT `[ExcludeFromCodeCoverage]` and tested to >= 90% line coverage; the four toggle/getPressed sites routed through the coordinator; the six save/info command sites routed through the existing `RibbonController.RunEngineCommandAsync` gate backed by six new `EngineCommandCatalog` entries and matching `getEnabled="EngineCommand_GetEnabled"` attributes in `RibbonExplorer.xml`; R1-R5 regression tests demonstrated red before the fix and green after. `RibbonController.Intelligence.cs`, `AppItemEngines.cs`, `IAppItemEngines.cs`, `ThisAddIn.cs`, `RibbonViewer.cs`, and the three #503 seam types other than `EngineCommandCatalog` take a zero-line diff.

#### 5.2 `EngineToggleStateCoordinator` surface

```csharp
internal EngineToggleStateCoordinator(
    Func<IAppItemEngines> enginesAccessor,      // returns null before SetGlobals; supported
    Action<string> invalidateControl,           // receives a ribbon control id
    Action<string> notifyUnavailable,           // one message per blocked toggle click
    Action<string, Exception> logError)         // observed prime/toggle faults

internal bool GetPressed(string engineName)              // sync cache read + lazy prime start
internal Task HandleToggleClickAsync(string engineName)  // boundary: guard -> toggle -> refresh -> invalidate; catches and logs
internal Task ExecuteToggleAsync(string engineName)      // no catch; propagates — the testable core ordering
internal Task GetPrimeTask(string engineName)            // test observability: in-flight/last prime task, Task.CompletedTask when none
```

Any null constructor argument throws `ArgumentNullException` (matching `EngineGatedCommandRunner.cs:60-65`). Zero `Microsoft.Office.*` / `Microsoft.Office.Interop.Outlook` references, no `MessageBox`, no WinForms types, no logger reference (logging is the injected delegate), no `[ExcludeFromCodeCoverage]`. State: `ConcurrentDictionary<string, bool>` cache plus an in-flight prime tracking map. `IAppItemEngines` lives in namespace `UtilitiesCS`.

#### 5.3 Coordinator semantics (B1-B5 of `spec.md`, restated as the implementation contract)

- **GetPressed (B2).** Null/whitespace/unmapped key: return `false`; start nothing; invalidate nothing. Cached key: return the cached value (dictionary read only; never await, block, or throw). Cache miss with `enginesAccessor()` returning null: return `false`; start nothing. Cache miss with engines available: start at most one prime per key (`GetOrAdd`-style in-flight guard); the prime awaits `enginesAccessor().EngineActiveAsync(name)`, stores the result, then invokes `invalidateControl(<mapped control id>)`. A second read during an in-flight prime starts no second prime. A prime fault is observed and routed to `logError` with a message containing the engine key; the cache is not updated; the in-flight marker is cleared so a later read may re-prime; no unobserved task remains.
- **ExecuteToggleAsync (B3).** In order: `await ToggleEngineAsync(name)` -> `await EngineActiveAsync(name)` -> cache update -> `invalidateControl(<mapped control id>)`. Update-before-invalidate is the load-bearing invariant. No catch; faults propagate unchanged. A null/whitespace/unmapped engine key throws `ArgumentException` (fail fast; observed at the boundary).
- **HandleToggleClickAsync (B4, B5).** When `enginesAccessor()` returns null: invoke `notifyUnavailable` exactly once with a message containing the engine key; invoke nothing else; do not throw. Otherwise `await ExecuteToggleAsync(name)` inside the single boundary `try/catch`: on fault, format a message containing the engine key, invoke `logError(message, exception)`, do not rethrow, do not invalidate.
- Notification and log messages must contain the engine key so tests can assert `Contains(engineName)` without pinning full sentence text.
