## 1. How the gate derives the "deployed version"

`scripts/dependencies/BindingRedirectVerification.psm1` `[V]`:

- `ConvertTo-ReferenceVersionMap` (lines 31-72) parses every supplied csproj text with `ConvertFrom-ProjectFileText` and keeps only `Reference` records whose `Include` matches `^\s*(?<name>[^,]+?)\s*,\s*Version=(?<version>[^,\s]+)` (line 58). Versions are unioned across all csproj texts per assembly name (lines 61-66). A `Reference` with no `Version=` contributes nothing (lines 37-41).
- `Find-StaleBindingRedirect` (lines 74-134) parses one app.config with `ConvertFrom-AppConfigText`, skips blocks with no `bindingRedirect` (line 109), and for each remaining block asks the provider for the assembly's deployed versions. No versions returned: the name goes to `Unverifiable` and is not a finding (lines 114-117). `newVersion` not in the returned set: a finding (lines 118-124). `oldVersion` is never compared (lines 82-84).
- The repository test `tests/scripts/dependencies/BindingRedirectVerification.Tests.ps1:275-334` builds the provider from every `*.csproj` directly under a root-level directory (lines 277-292), runs the detector over every `app.config` directly under a root-level directory (lines 278-282, 317-324), and asserts the sorted-unique finding set equals `$expectedDebt` (lines 293-309, 331) and the sorted-unique unverifiable set equals `$expectedUnverifiable` (lines 310, 332). The examined count must equal the raw `<bindingRedirect` element count (lines 319-321, 330).

Consequence: the only "deployed version" the gate recognises is a csproj `Reference Include="Name, Version=X"` string. `packages.config` and `HintPath` are not consulted by the gate (module header lines 10-13). They are consulted below only to establish that the csproj side is the correct side.

### 2.5 Root-cause mechanism (drift pattern) `[V]`

A redirect is current exactly in the projects whose own `packages.config` installs the package, and stale in projects that carry the assembly only transitively:

- Microsoft.Bcl.Memory is 10.0.0.12 in the five configs whose packages.config lists it (UtilitiesCS:171-172, QuickFiler:166-167, TaskMaster:178-179, ToDoModel:171-172, UtilitiesCS.Test:174-175) and 10.0.0.7 in the ten that do not.
- Microsoft.Bcl.Numerics is 10.0.0.12 only in UtilitiesCS/app.config:183-184, the one project that installs it; 10.0.0.5 in the other twelve carrying a redirect.
- The six production configs of projects that do not install Azure.Core, System.ClientModel, MSAL or Diagnostics.Abstractions (Tags, TaskTree, TaskVisualization, QuickFiler, TaskMaster, ToDoModel) are stale for all four; the ten projects that install them are current.
- The seven IdentityModel assemblies are current only in UtilitiesCS and UtilitiesCS.Test, the two projects that install them; test projects that install only Microsoft.IdentityModel.Abstractions are current for that one name (for example Tags.Test/app.config:178-179 at 8.23.0.0) and stale for the other six.

NuGet rewrites redirects only in the project it is updating. A config that redirects an assembly its own project does not install is never rewritten, which is the "package updates advanced deployed versions without a matching sweep" cause the issue records. The #953 gate now detects the drift; it does not prevent it.

## 5. Redirect-down analysis (Q3)

### 5.1 Structural argument

Every correction raises `newVersion` from a version that is not on disk to the one version that is on disk and that every csproj compiles against. A redirect to the installed version can be "below a compile-time reference" only if some installed consumer was compiled against a version higher than the installed one. The nuspecs below show each consumer's declared lower bound at or below the installed version, and NuGet's packages.config restore does not install a dependency below a consumer's lower bound. The current state, by contrast, redirects every request at or below the stale version to an assembly that does not exist (the #418 class: `.../418/runbooks/verify-winforms-designer-load.runbook.md:22-28`), and leaves requests between the stale version and the installed version unredirected, which on .NET Framework is a strict-version bind that also fails. Each correction therefore removes failure modes and introduces none.
