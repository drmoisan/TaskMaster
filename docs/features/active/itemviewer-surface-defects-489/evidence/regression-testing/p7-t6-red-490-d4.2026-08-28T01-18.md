## How the tests reach the read-back without touching Outlook

`FlagTasks` is constructed through the injected `_flagTasksFactory` seam, but its own constructor is
Outlook-bound — it calls `globals.Ol.App.ActiveExplorer()` and can show a `MessageBox` — and `Run`
is not virtual, so it cannot be mocked. The Part2 helper `BuildInertFlagTasks()` therefore produces
the instance with `System.Runtime.Serialization.FormatterServices.GetUninitializedObject`, which
runs no constructor. `FlagTasks.Run(bool)` opens with `if (_controller is not null)`, and on an
uninitialised instance that field is null, so `Run(modal: true)` returns `DialogResult.None`
immediately without showing a dialog. Control then reaches the assignment and the read-back, which
is precisely what has to be observed.

Because `Mock<IItemViewer>` does not store property values unless told to, the subsequent get
returns `default(DialogResult)`, which is `DialogResult.None` and not `DialogResult.OK`, so the
`FlagTaskBackColor` branch is not taken and no theme dictionary is needed. Both tests are therefore
deterministic and touch no COM object, no live form and no filesystem.
