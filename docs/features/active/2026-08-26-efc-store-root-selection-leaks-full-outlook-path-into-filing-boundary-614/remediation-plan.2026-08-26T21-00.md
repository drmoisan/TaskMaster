## Design decision — how the filing guard obtains the archive root (recorded)

**Chosen: pass the archive root to the guard as a second `string?` parameter, resolved in `ActionOkAsync` through a new throw-tolerant helper `EfcSelectionGuard.ResolveArchiveRootOrEmpty(Func<string> readArchiveRoot, Action<string> logDiagnostic)`.**

- `EfcFormController` already reaches the root as `_globals.Ol.ArchiveRootPath` (existing uses at `:492`, `:502`, `:771`, `:781`, `:891`). After the #614 D6 fix, that getter throws `InvalidOperationException` when the archive root is unresolvable or cross-store (`TaskMaster/AppGlobals/AppOlObjects.cs:250-267`). On the OK-button path an unhandled throw would crash the form, so the read is wrapped: on `InvalidOperationException` the helper invokes the diagnostic sink with a fixed redaction-safe message and returns `string.Empty`, and the guard then rejects rooted selections (an empty root fails `TryMakeArchiveRelative`) while relative stems still file normally. The catch is narrow (only the documented `InvalidOperationException` contract); any other exception propagates (fail fast). The underlying D6 diagnostic is not lost: `AppOlObjects` logs it through its own sink before throwing.
- The helper lives in `EfcSelectionGuard.cs`, takes delegate seams (mirroring the `Action<string>` sink pattern of `ArchiveRootPathGuard.RequireResolvedArchiveRoot`), and is therefore 100% unit-coverable, including the catch branch — new logic added to `EfcFormController.cs` (uncoverable WinForms glue) is held to ~7 lines.

**Alternatives considered and rejected:**

1. *Inline try/catch in `ActionOkAsync`.* Functionally equivalent, but it adds ~12 permanently uncoverable lines to `EfcFormController.cs` (baseline 1072 against a 1084-line ceiling — zero margin after the `:1038` reformat) and puts the new catch branch beyond unit-test reach. Rejected on file-size and coverage grounds.
2. *Resolving the root inside `IsValidFilingSelection` (guard receives `IOlObjects` or a bare accessor).* Couples the pure predicate to exception handling and to the globals object graph, making every predicate test carry a fake accessor. Rejected: the predicate stays pure over two strings; resolution is a separate, separately-tested concern.
3. *One shared root-aware predicate for both call sites.* Forces the folder-creation path (`IsValidSelection`, consumed at `:468` and `:752`) to take a root it does not need and to perform a throwing read on every property evaluation. Rejected in favor of splitting into two predicates (below), which is also what the CR-1 required outcome demands ("the paths must take differently-scoped predicates").

**Predicate split (CR-1 required outcome):** `IsValidFilingSelection(string? selection, string? archiveRoot)` carries NO minimum-length rule; a new `IsValidCreationSelection(string? selection)` keeps today's full rule set (null/whitespace, banner, `Length >= MinimumCreationLength` where `MinimumCreationLength = 3`, and full-path rejection) and becomes the target of the `IsValidSelection` property at `:1038`. Recorded consequence: the creation path retains its pre-remediation full-path rejection (a rooted value is never a valid creation stem for `CreateFolderAsync`, which concatenates the selection under the archive root); CR-2's router-agreement requirement is scoped to the filing/OK path only.

**Root-exact consequence (recorded):** with the CR-2 fix, a rooted value exactly equal to the archive root passes the filing guard, because `TryMakeArchiveRelative` returns true for the exact root and `BreadcrumbBridgeRouter.SelectRow` (the guard's agreement target, `:481-491`) admits at-or-under-root rooted targets verbatim. This mirrors the required outcome verbatim ("reject a rooted value only when it genuinely fails `TryMakeArchiveRelative`"). `SelectHierarchyPath`'s root-exact non-selection (`:506-513`) is a different surface and is untouched.

**Spec AC16 interaction (recorded, no spec edit this cycle):** AC16's "reject a full Outlook path" is executed post-remediation as "reject a full Outlook path that is not resolvable against the archive root" — the D1/D4/D9 protection (store-root, cross-store, above-root all still rejected, because they fail `TryMakeArchiveRelative`). The narrowing is mandated by the remediation-inputs CR-2 required outcome under the orchestrator's disposition override. `spec.md` is not edited (rule 11); the reading is documented in the P5-T9 change-description update.
