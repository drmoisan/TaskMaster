## Fail-closed rules

- **Evidence rule.** Every command-bearing task writes an artifact under
  `docs/features/active/itemviewer-breadcrumb-lifecycle-defects-488/evidence/<kind>/`, where `<kind>` is
  one of `baseline`, `regression-testing`, `qa-gates`, `issue-updates`, `other`. Each command-step
  artifact records `Timestamp:`, `Command:`, `EXIT_CODE:`, and `Output Summary:`. A task with a missing
  or field-incomplete artifact stays unchecked. Paths under `artifacts/baseline/`, `artifacts/baselines/`,
  `artifacts/qa/`, `artifacts/qa-gates/`, `artifacts/coverage/`, `artifacts/regression-testing/`,
  `artifacts/post-change/`, and `artifacts/evidence/` are forbidden and must not be used by any task here.
- **No-SKIPPED rule.** Every command task in this plan executes its stated command. `EXIT_CODE: SKIPPED`
  is not a passing outcome for any task here.
- **Expect-fail rule.** Tasks tagged `[expect-fail]` must record a non-zero `EXIT_CODE:` together with
  `ExpectedExitCode: 1` and the named failing test result. A task tagged `[expect-fail]` that records a
  pass is a failure of that task.
- **No absolute host paths in artifacts.** No artifact may embed a user account name, a home directory,
  or a machine name. `vstest.console.exe` names a default TRX after the account and host, so every test
  task supplies `LogFileName=` explicitly.
- **Unmodified-file rule.** Several `spec.md` criteria conjoin a behavioural claim with an
  **"unmodified"** or **"byte-identical"** claim about a file (criteria beginning
  "`BreadcrumbDropDownIntegrationTests.ItemViewerDisposal_OwnsHostAndDetachesBothSurfaces` passes",
  "`QfcItemControllerBreadcrumbDropDownTests.ConfigureBreadcrumbDropDown_RepeatedSameEnvironmentReusesPopupHost`",
  "`QfcItemControllerBreadcrumbDropDownTests.ConfigureAndAttachBreadcrumbAsync_CachesCurrentThemeAndCreatesOneCandidatePerSession`",
  "`QfcItemControllerBreadcrumbDropDownTests.ConfigureBreadcrumbDropDown_PassesExistingEnvironmentAndDarkThemeLazily`",
  and "`QuickFiler.Test/Viewers/BreadcrumbDropDownIntegrationTests.cs` remains at exactly 500 lines").
  **A passing test result does not establish that its file is unmodified, and a line count does not
  establish byte-identity**: a red test can be made green by editing it, and a file can be edited without
  changing its line count. Every artifact cited by a check-off task for such a criterion must therefore
  additionally record the empty output of `git diff --name-only <BASE_SHA> -- <the named file>`. The
  tasks that produce those artifacts — [P1-T6], [P1-T9], [P2-T6], and [P8-T8] — carry that requirement in
  their own acceptance text.

`UiSyncContext == null` escape in the D4 design is not reachable by construction. It is reachable only by
a test that nulls the private `_context` field reflectively, which is the shape [P6-T5] uses.

file under `QuickFiler.Test` for the fixed string `ItemViewer()`. It is the complete set; an earlier

list, not that one.

## Decisions Record

- **D-1 — Toolchain gate commands are the CLAUDE.md commands verbatim, with `/t:Rebuild`.** The two
  msbuild gate tasks use `/t:Rebuild`. MSBuild's up-to-date check does not invalidate on a command-line
  property change, so a warm `/t:Build` returns exit 0 with `CoreCompile` skipped on every project and the
  analyzer and nullable gates cannot fail.
- **D-2 — Intermediate builds are not gates.** Tasks that only need a fresh `QuickFiler.Test.dll` in order
  to run a test use `/t:Build` against `QuickFiler.Test\QuickFiler.Test.csproj`. **This clause is binding
  on every `/t:Build` invocation in this plan without exception**, whether or not the individual task text
  repeats it: [P1-T4], [P1-T6], [P2-T3], [P2-T5], [P3-T2], [P3-T4], [P4-T3], [P4-T6], [P5-T2], [P5-T4],
  [P6-T4], [P6-T6] (both of its builds), and [P6-T8]. Each of those artifacts must record the line
  `GATE: none (intermediate build)` alongside its `Command:` and `EXIT_CODE:` fields, so that a reviewer
  cannot mistake a warm `/t:Build` for an analyzer or nullable gate. The only analyzer and nullable gates
  in this plan are [P0-T10], [P0-T11], [P8-T3], and [P8-T4], all of which use `/t:Rebuild` against
  `TaskMaster.sln`. A `/t:Build` result may never be cited as evidence for a criterion naming either
  msbuild gate command.
- **D-3 — No solution-wide nullable property.** `/p:Nullable=enable` must not be added to any command in
  this plan. Nullable enforcement here is per-file opt-in through `#nullable enable`, and the property
  conscripts every file that has never adopted the pragma.
- **D-4 — MSBuild and vstest are invoked from PowerShell.** Every `msbuild` and `vstest.console.exe`
  invocation runs under `pwsh -NoProfile` with absolute executable paths resolved in [P0-T4]. A bash shell
  mangles the parallel-build switch into a drive-letter path and fails with MSB1008. Neither `msbuild` nor
  `vstest.console.exe` nor `vswhere.exe` is on `PATH` in this environment.
- **D-5 — CSharpier 1.2.6 requires a subcommand.** `dotnet tool run csharpier format` and
  `dotnet tool run csharpier check .`. The bare-path form does not run, and `pipe-files` writes to stdout
  and enforces nothing.
- **D-6 — The mutating format pass is scope-locked.** [P8-T1] runs `csharpier format` against the seven
  owned file paths explicitly, not `format .`. A repository-wide mutating pass would rewrite files that
  were already unformatted at the baseline and break the changed-file-set criterion. The repository-wide
  read-only `csharpier check .` remains the gate in [P8-T2], compared against the baseline unformatted set
  recorded in [P0-T9].
- **D-7 — Every TRX run gets its own results directory.** `/Logger:trx` writes to `TestResults\` relative
  to the working directory unless `/ResultsDirectory:` is supplied, and a shared results directory makes
  "the TRX for this task" ambiguous once an `[expect-fail]` run has deposited one. Each test task supplies
  a `/ResultsDirectory:` ending in its own `p#-t#` segment and an explicit `LogFileName=`.
- **D-8 — The D4 regression tests call the two-argument `InitializeBreadcrumbPipeline` overload.** The
  one-argument overload evaluates `BreadcrumbPopupUiOperations.CaptureCurrent()` as an **eager argument**,
  and that method already throws `InvalidOperationException` under a null ambient context. A D4 test
  written against the one-argument overload would therefore pass under ambient-null **before the guard
  exists**, for the wrong reason. Every D4 negative test passes injected operations to the two-argument
  overload and additionally asserts that the thrown exception's message names the operation, which the
  dispatcher's own message does not.
- **D-9 — `ObjectDisposedException` derives from `InvalidOperationException`.** Any assertion of the form
  `Should().Throw<InvalidOperationException>()` is satisfied by an `ObjectDisposedException`. Every D3 and
  D4 negative assertion therefore adds `.Which.Should().NotBeOfType<ObjectDisposedException>()` so a D5
  throw cannot satisfy a D3 or D4 test.
- **D-10 — The #475 seam-preservation test nulls `ItemViewer._context` reflectively.** Under C6 a
  constructed viewer always has a non-null `UiSyncContext`, so the D4 guard would reject the three-argument
  `ConfigureBreadcrumbDropDown` call inside `InvokeAmbientNull` and the seam test could never assert
  `NotThrow`. `spec.md` explicitly names "a viewer constructed with a null `UiSyncContext`" as a real test
  shape (see its "Interaction between the fixes"), and reflection on the private field is the only way to
  produce it **from a viewer that has run its constructor**. That qualifier is load-bearing and must not be
  dropped: it is *not* the only way to obtain an `ItemViewer` instance whose `_context` is null in general,
  because `QfcThemeHelperTests.CreateItemViewer()` at
  `QuickFiler.Test/Helper Classes/QfcThemeHelperTests.cs:247-249` already produces one through
  `CreateUninitialized<ItemViewer>()`, which bypasses the constructor entirely. That route is unusable for
  [P6-T2], which needs a viewer whose breadcrumb pipeline has been seeded through
  `InitializeBreadcrumbPipeline`; an uninitialized object cannot supply one. **No task may state the
  unqualified "the only way" claim in a delivered artifact, doc comment, or evidence file**, because it is
  false as written. This is a test-only affordance: it adds no production member, widens no accessibility,
  and uses no thread and no timing construct.
- **D-10a — The D1 regression test needs a third assertion, because the spec's two named observations
  cannot fail on their own.** `BreadcrumbDropDownHost.Close` returns `false` when `_disposed` is set, but
  it also returns `false` on the fall-through path, because with no pending open the lifetime helper's
  cancel attempt returns `false` from its `_openCompletion == null` guard. A host that was never opened
  therefore returns `false` from `Close` **before and after** the fix. Likewise `DropDown.IsDisposed`
  becomes `true` after the queue is drained in both states, because the pre-fix release path disposes the
  outgoing host too; only the *ordering* differs, and ordering is not observable from that flag. The
  discriminating observation is `SetTheme` on the captured host: it reaches the host's disposal guard and
  throws `ObjectDisposedException` once the host is disposed, and succeeds silently when it is not. The
  test therefore asserts all three, with the `SetTheme` assertion first, and the artifact records which of
  the three is the discriminating one. This is the same accepted residual the [P1-T7] dossier describes,
  observed deliberately rather than encountered accidentally.
- **D-11 — `InvokeAmbientNull` is reachable only in its generic form.**
  In `QuickFiler.Test/Viewers/BreadcrumbSelectorToggleUiBoundaryTests.cs`, the generic
  `InvokeAmbientNull<T>(Func<T>)` is declared `internal static` at line 325, on the `public sealed class`
  declared at line 22, and is therefore reusable from another test class in the same assembly. Its `Action`
  overload at line 339 is `private static` and is **not**. Every call from
  the new file therefore wraps the operation in a `Func<bool>` returning `true`. The five other harnesses
  the research names are `private` and must not be reused or widened.
- **D-12 — One acceptance criterion per check-off task.** Each check-off task flips exactly one `spec.md`
  checkbox and leaves its text unmodified. A check-off task cites exactly one evidence artifact, with two
  enumerated exceptions where the criterion is an explicit **conjunction of facts produced by different
  command steps** and no single artifact can carry both: [P6-T16] (the red-then-green seam-preservation
  criterion, citing `475-lazy-fail.md` and `475-pass.md`) and [P9-T1] (the Phase 0 baseline criterion,
  which conjoins the `QuickFiler.Test` pass/fail counts with the pre-change **coverage** figures, citing
  `evidence/baseline/quickfiler-test.md` and `evidence/baseline/coverage.md`). No other check-off task may
  cite more than one artifact. Where a criterion's conjuncts could instead be brought into a single
  artifact, the producing task's acceptance is widened rather than a third exception added; that is what
  the unmodified-file rule, [P7-T9], [P8-T7], and [P8-T10] do.
- **D-13 — Coverage is captured as Cobertura.** `scripts/vscode/Invoke-MSTestWithCoverage.ps1` emits
  Cobertura. The repository-wide figure is the root `coverage` element's `line-rate`; per-member figures
  come from the `method` elements' `line-rate`. Async state machines and lambdas are emitted as separate
  `class` elements, so per-member figures are aggregated by `filename` rather than read from a single
  element.
- **D-14 — Follow-up promotion writes under `docs/features/potential/`.** The scope criterion enumerates
  the source files this feature may change; the follow-up criterion compels creating potential entries.
  The two are reconciled by reading the scope criterion as constraining **source** files, so [P7-T2]'s
  changed-file check admits paths under `docs/features/active/itemviewer-breadcrumb-lifecycle-defects-488/`
  and `docs/features/potential/` alongside the owned source files, and nothing else.
- **D-15 — In `EnsureBreadcrumbResourceOwnership` the affinity guard precedes the disposal throw, and the
  two criteria that describe that member are reconciled by reading "statement" and "action" as distinct.**
  Two criteria constrain the head of this member. The criterion beginning "The helper is invoked as the
  first statement of `InitializeBreadcrumbPipeline(provider, operations)`" requires
  `ThrowIfOffUiBoundary` to be the **first statement**; the criterion beginning
  "`EnsureBreadcrumbResourceOwnership` throws `ObjectDisposedException` as its first action" requires the
  disposal throw to be the **first action**. Read as two claims about statement position they are in
  direct conflict, and only one of them could be delivered. They are reconciled as follows and no task may
  adopt the other order. `ThrowIfOffUiBoundary` is the first statement; it is a **precondition check that
  returns without effect** on the UI boundary and when `UiSyncContext` is null, so on every path that
  reaches the member's own logic it has performed no action. The `ObjectDisposedException` throw is
  therefore the first statement that acts: it is the first thing that inspects the member's own subject
  (the viewer's teardown state), it precedes the already-owned early return, and it precedes every
  container creation and every `BreadcrumbResourceOwner` addition. Both criteria are satisfied under this
  reading, which is why [P5-T3] requires the delivered order to be stated explicitly in the source rather
  than left for a reviewer to infer. Reversing the order would place a `SynchronizationContext`
  comparison after a throw that is supposed to run first, and would break the "first statement" criterion
