## Execution Conventions

All commands run from the workspace root (the git worktree root that contains `TaskMaster.sln`), in PowerShell (`pwsh -NoProfile`).

**Toolchain resolution.** Neither `msbuild` nor `vstest.console.exe` is on `PATH` in this environment. Resolve both through `vswhere`, whose own path is not on `PATH` either:

```powershell
    $vswhere = Join-Path ${env:ProgramFiles(x86)} 'Microsoft Visual Studio\Installer\vswhere.exe'
    $msbuild = & $vswhere -latest -requires Microsoft.Component.MSBuild -find 'MSBuild\**\Bin\MSBuild.exe' | Select-Object -First 1
    $vstest  = & $vswhere -latest -products * -find 'Common7\IDE\Extensions\TestPlatform\vstest.console.exe' | Select-Object -First 1
```

Each artifact must record the resolved absolute path it used alongside the argument list.

**MSBuild is invoked directly, not through `scripts/vscode/Invoke-VSBuild.ps1`.** The wrapper calls `scripts/vscode/Sync-PackageReferences.ps1` (`Invoke-VSBuild.ps1:152-155`), which rewrites `<HintPath>` elements in every `*.csproj` whose package path does not resolve on disk. `QuickFiler/QuickFiler.csproj` is on this feature's forbidden-file list, so a wrapper-driven rewrite of it would be a scope violation produced by the build itself. Invoking `MSBuild.exe` directly with the argument list mandated by `CLAUDE.md` avoids that path entirely. The argument list after the executable is character-for-character the mandated command.

**Long-running commands.** The full-suite coverage run exercises every `*.Test.dll` in the solution and takes far longer than a single foreground tool call tolerates. Launch it detached and poll:

```powershell
    $p = Start-Process -FilePath 'pwsh' -ArgumentList @('-NoProfile','-File','scripts\vscode\Invoke-MSTestWithCoverage.ps1','-SearchRoot','.','-Configuration','Debug','-CoverageOutput','<output path>') -PassThru -RedirectStandardOutput '<log path>' -RedirectStandardError '<err path>' -WindowStyle Hidden
    $p.Id
```

Record the PID, poll the log with short waits, and take `EXIT_CODE:` from `$p.ExitCode` once `$p.HasExited` is true. Before any retry, kill the whole process tree (the `pwsh` runner, `dotnet-coverage`, `vstest.console`, and every `testhost` child).

**Scoped test runs.** For every filtered test run:

```powershell
    & $vstest QuickFiler.Test\bin\Debug\QuickFiler.Test.dll /Settings:scripts\vscode\TaskMaster.cli.runsettings /InIsolation /TestCaseFilter:"FullyQualifiedName~A|FullyQualifiedName~B" /Logger:trx /ResultsDirectory:<per-task directory>
```

`/InIsolation` is mandatory for the Moq-based assemblies. vstest 18.x rejects `OR` inside `/TestCaseFilter:`; join clauses with `|`. Every `/Logger:trx` invocation must carry a `/ResultsDirectory:` whose value is that task's own private subdirectory under the task's evidence kind, so a TRX-count acceptance is unambiguous. Each task below names its directory explicitly.

**Compile-observation builds.** Tasks that only need to observe whether the test assembly compiles use `/t:Build` on the solution. That is sound here because each such task has just edited a source file, so `CoreCompile` cannot be skipped by the up-to-date check. The analyzer and nullable gates in Phase 0 and Phase 4 use `/t:Rebuild` exactly as `CLAUDE.md` requires.

**Loop discipline.** In Phase 4, if any step fails or rewrites a file, restart the phase from the formatter task. The phase is complete only when one consecutive pass of the four steps produces no failure and no file rewrite.

## Decisions Record

These decisions resolve points the spec or the research artifact left to implementation time. An executor must not re-decide them.

1. **`options` is not guarded.** Spec §D4 item 3 leaves the `options` guard to implementation time and research §9 item 4 records the SDK's null tolerance as UNVERIFIED. That tolerance cannot be verified without the Evergreen runtime, which no unit test may require. Guarding on an unverified contract would narrow behaviour on unmeasured grounds, so `CreateEnvironmentAsync` guards `cacheFolder` only, and the interface XML documentation states that `options` is forwarded to the SDK unguarded because its null tolerance is unverified. `environment` is likewise not guarded, per spec AC.

2. **The internal constructor's third parameter is declared `BreadcrumbUiDispatcher?`.** The public two-argument constructor chains to the internal three-argument constructor passing `null`, because under variant V1 no dispatcher exists at construction time. `?` is a nullability annotation, not a different parameter type, so the constructor signature `(WebView2, IWebViewCoreInitializer, BreadcrumbUiDispatcher)` required by the spec is satisfied. `WebView2BreadcrumbHost.cs:1` is `#nullable enable`, so the field and every use of it must be null-checked.

3. **`InitializeAsync` assigns the dispatcher field only when it is currently null.** Otherwise the internal constructor's injected dispatcher — the seam the whole #476 defect-1 regression test rests on — would be discarded the moment `InitializeAsync` ran. Two named tests pin both directions.

4. **A second internal observation member, `HasUiDispatcher`, is added.** Spec §"Functions/classes impacted" contemplates a "new internal observation member"; two are needed because `IsAttached` observes the #458 registry state and `HasUiDispatcher` observes the #476 defect-1 dispatcher installation. Both are trivial, measured, and assembly-visible through `QuickFiler/Properties/AssemblyInfo.cs:5`.

5. **`InitializeAsync` is measured, not exempt.** Spec §"Coverage and Exemption Impact" names `InitializeAsync` as "principally" host-bound, but its only SDK-reaching statements go through the mockable `IWebViewCoreInitializer` seam, and two tasks in this plan exercise it end-to-end with a `Mock<IWebViewCoreInitializer>`. Applying an exemption to a member this plan demonstrably tests would recreate the exact false-rationale defect #477 reports. The operative acceptance criterion is the one requiring member-level attributes "only" on genuinely host-bound members; the genuinely host-bound members after this change are `OnCoreInitializationCompleted`, `OnWebMessageReceived`, and the two extracted SDK forwards. This reconciliation is recorded again at the Phase 5 check-off for that criterion.

6. **Two new test files, not one.** `QuickFiler.Test/Viewers/WebView2BreadcrumbHostContractTests.cs` holds the reflection and structural assertions; `QuickFiler.Test/Viewers/WebView2BreadcrumbHostTests.cs` holds the pump-hosted behavioural tests. A single file carrying both would approach the 500-line ceiling in `.claude/rules/general-code-change.md`. Both `Compile Include` entries are inserted immediately after `QuickFiler.Test/QuickFiler.Test.csproj:159`, contiguously, and the surrounding ItemGroup is not re-sorted.

7. **A declaration-only seam task opens Phase 2.** The tests for #476 defect 1, #458, and the dispatcher installation reference members that do not exist yet, so at the end of Phase 1 the test assembly does not compile and their failure is a compile error rather than an assertion failure. `[P2-T1]` declares those members with no behaviour change, and `[P2-T2]` then runs all eleven tests and records that every one of them fails at assertion time against the unfixed production behaviour. That artifact is the authoritative fail-before record. No behavioural fix precedes it.

8. **The repository-wide coverage figure is measured first, then gated conditionally.** `CLAUDE.md` §UT2 requires `>= 80%` repository-wide and `>= 90%` for new code, while `.claude/rules/general-unit-test.md` and `.claude/rules/quality-tiers.md` require a uniform `>= 85%` line and `>= 75%` branch. Which of those floors the repository actually meets is not asserted here; it is measured by `[P0-T11]` and recorded in `baseline-4-tests-coverage.<timestamp>.md` before any change lands. The rule `[P4-T5]` applies to the measured pair is: for each floor, if the recorded Phase 0 baseline already sits below that floor, the post-change repository-wide figure is recorded and reported non-blocking for that floor, because a bug-fix branch of this size cannot be required to close a pre-existing repository-wide gap; if the baseline meets that floor, a post-change figure below it is blocking. Independently of that, the change-scoped gates — no regression on changed lines, and `>= 90%` line coverage on the newly measured members — are blocking unconditionally. The threshold conflict between the two policy documents is reported in the Phase 5 status summary regardless of which branch applies.

9. **Formatting is applied file-scoped and verified repository-wide.** `CLAUDE.md` §C#1.1, `.claude/rules/csharp.md` item 1, and the final acceptance criterion in `spec.md` all name `dotnet tool run csharpier format .`. `[P4-T1]` runs `csharpier format` against this feature's six files instead, because a repository-wide apply would rewrite any pre-existing formatting deviation in a file on this feature's forbidden list, producing a scope violation manufactured by the toolchain rather than by the change. The gate that CI actually enforces is the read-only `dotnet tool run csharpier check .`, and `[P4-T1]` runs that at full repository scope with a two-part acceptance: none of the six touched files may be reported, and no file may be reported that was not already reported in the `[P0-T8]` baseline. That pair is strictly stronger evidence than a repository-wide apply, because an apply hides pre-existing debt by silently rewriting it. `[P5-T38]` must record this deviation and this reasoning in its check-off note rather than checking the criterion off silently.

### Phase 1 — Failing Regression Tests

Per the Bugfix Workflow in `CLAUDE.md`, every test in this phase is authored before any production change. Each task is tagged `[expect-fail]` and each produces its own evidence artifact under `docs/features/active/webview2-host-initializer-defects-476/evidence/regression-testing/`.

Tasks `[P1-T1]` and `[P1-T2]` add tests that compile against the current production code, so their failure is observed as an assertion failure in a real test run. Tasks `[P1-T3]` through `[P1-T8]` add tests that reference seams which do not exist yet, so from `[P1-T3]` onward the test assembly does not compile and each of those tasks records a compile-time red state. `[P2-T2]` then re-runs all eleven tests at assertion time and is the authoritative fail-before record for the whole set.

Every test in this phase uses MSTest `[TestClass]`/`[TestMethod]`, Moq for mocks, FluentAssertions `.Should()` with an explicit `because:` argument on each non-obvious assertion, and explicit `// Arrange`, `// Act`, `// Assert` comments. No test may create a temporary file, call `Task.Delay` or `Thread.Sleep`, wait on wall-clock time, or depend on an external process, the network, or the WebView2 Evergreen runtime. Every test that needs a `WebView2` control constructs its own distinct instance on `WinFormsPumpHost` via `host.InvokeAsync(() => new Microsoft.Web.WebView2.WinForms.WebView2())`, so the process-wide owner registry cannot couple tests, and carries a `[Timeout(...)]` attribute following the precedent at `QuickFiler.Test/Controllers/QfcItemController.InitializationTests.Part3.cs:355`.
