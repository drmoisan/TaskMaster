## Executive Summary

1. **All four defects are confirmed from repository files.** The format command is v0 syntax
   against a v1.2.6-pinned tool; the nullable command uses `/t:Build`, which MSBuild's
   timestamp-based up-to-date check does not invalidate on a `/p:` change; and it carries
   `/p:Nullable=enable`, which `.github/workflows/ci.yml` deliberately omits.

2. **Independent corroboration of the vacuity claim (#512) was found that no issue cites.** Across
   roughly a dozen committed evidence artifacts the documented nullable step records an elapsed
   time of **0.89 s to 1.51 s**, while the analyzer step over the same solution records
   **6.29 s to 17.02 s**. An 18-project solution cannot compile in 1.2 s. The artifact
   `docs/features/active/2026-08-08-wpf-dispatcher-yield-test-order-dependent-508/evidence/baseline/msbuild-nullable.2026-08-08T16-19.md`
   states the conclusion outright and adds a second independent signal: the `CS2002` warning, which
   is emitted by the `CoreCompile` target, is present in the analyzer log and absent from the
   nullable log.

3. **The true site count is materially higher than the issues, and higher than the orchestrator's
   pre-count.** The orchestrator enumerated 11 nullable sites and 11 csharpier sites. The
   authoritative inventory in Q1 finds **13 documentation sites inside the epic's authorized
   surface**, **17 sites in the Codex/Copilot mirror tree**, and — the most significant addition —
   **an executable carrier of the same defect that no issue and no prior enumeration mentions**:
   `scripts/vscode/Invoke-VSBuild.ps1` hardcodes `/t:Build` (line 64) and maps `-EnableNullable` to
   `/p:Nullable=enable` (line 107). `.vscode/tasks.json` lines 142-167 wire both into the
   `type-check: TaskMaster.sln (nullable warnings as errors)` task, and
   `tests/scripts/vscode/Invoke-VSBuild.Tests.ps1` lines 36 and 60 pin the defective behavior as
   asserted expectations.

4. **The `AGENTS.md` / `.agents/` mirror is out of scope, and the reason is stronger than
   scope-width.** `AGENTS.md` line 3 declares itself generated, names its sixteen source files, and
   says "Do not edit this file manually." The generator it names,
   `scripts/dev-tools/sync-agents-from-instructions.ps1`, **does not exist in this repository**
   (`scripts/dev-tools/` contains only `run-actionlint.ps1`). `.agents/skills/*/SKILL.md` self-describe
   as "Legacy C# variant resource for Codex push-down" and are installed by the external `drm-copilot`
   MCP tool `push_down_codex_and_agents_customizations`. Editing them is both unauthorized and
   non-durable. This is the same upstream-ownership pattern the epic already used to exclude
   issue #513.

5. **Recommended nullable command: adopt CI's exact command verbatim** —
   `msbuild TaskMaster.sln /t:Rebuild /m /p:Configuration=Debug "/p:Platform=Any CPU" /p:TreatWarningsAsErrors=true`.
   This is the only option that satisfies all three required properties simultaneously (executes,
   enforces, agrees with CI) without touching the out-of-scope nullable debt. Confidence: **High**.

6. **`ci.yml` should not change.** Confidence: **High**. One premise in the delegation prompt needs
   correcting, though: `ci.yml` line 8 carries a `workflow_dispatch:` trigger, and the
   `modified-workflow-needs-green-run` rule explicitly accepts a green `workflow_dispatch` run
   against the branch head. A green run would therefore be *obtainable* on this branch. The
   recommendation against changing `ci.yml` rests on it already being correct, not on the gate being
   unsatisfiable.

7. **One adjacent factual error is confirmed wrong and should be corrected** (Q5): `CLAUDE.md`
   line 188's claim that csharpier "formats only `*.cs` without touching project files" is refuted
   by `.csharpierignore` lines 9-14, which exist precisely because CSharpier v1 *does* reach
   `*.csproj`, `*.props`, and `*.targets`.

### Sync tooling — searched and characterized

- **The named generator does not exist in this repository.** `scripts/dev-tools/` contains exactly
  one file, `run-actionlint.ps1`. A repository-wide grep for `sync-agents-from-instructions` returns
  only the `AGENTS.md` header and four `.github/agents/*.agent.md` files that use it as a worked
  *example* in atomic-planning templates. There is no CI job that regenerates or drift-checks
  `AGENTS.md`.
- **`.agents/skills/**` is not generated from `.claude/skills/**`.** No sync script references
  `.agents/skills`. Each of `.agents/skills/csharp/SKILL.md` (line 11),
  `.agents/skills/csharp-qa-gate/SKILL.md` (line 8) and `.agents/skills/invoke-csharp-engineer/SKILL.md`
  (line 8) carries the self-description "Legacy C# variant resource for Codex push-down."
- **The push-down direction is inbound from an external repository.**
  `.agents/skills/repo-automation-adapter/SKILL.md` lines 41 and 59 name the MCP tool
  `push_down_codex_and_agents_customizations` and its legacy VS Code command
  `drmCopilotExtension.pushDownCodexAndAgentsCustomizations`. This agent's own memory record
  `project_push_down_claude_dir.md` documents that these commands copy bundled resources out of the
  `drm-copilot` extension (`resources/<...>-customizations/`) *into* the target workspace. `.agents/`,
  `.codex/` and `.github/` are therefore downstream artifacts of `drm-copilot`, not first-party
  TaskMaster sources.

### Argument for including the mirrors

Leaving them stale reproduces the exact defect for any Codex-driven or Copilot-driven session. A
Codex agent reading `.agents/skills/csharp/SKILL.md` line 19 will run the unpassable
`/p:Nullable=enable` command and manufacture the same false blocking findings that required human
override on #507 and #508. The epic's stated outcome is that the documented commands agree with CI;
`AGENTS.md` and `.agents/` are documented commands, and after this feature merges they would be the
*only* remaining sites that disagree. That is arguably worse than the status quo, because the
divergence becomes host-dependent and therefore harder to diagnose.

### Argument against including the mirrors

Four independent reasons, in descending strength:

1. **Non-durability.** `.agents/` and `.codex/` are overwritten wholesale by the next
   `push_down_codex_and_agents_customizations` invocation. An edit here is not a fix; it is a change
   that will be silently reverted. The durable fix belongs in the `drm-copilot` bundled resources.
   This is precisely the reasoning the epic already applied to issue #513, which it excluded as a
   Non-Goal because "TaskMaster consumes `collect_pr_context` as an installed MCP extension and
   contains no copy of that source."
2. **`.github/instructions/` is under the same hard constraint as `.claude/rules/`, and the epic did
   not authorize it.** `.claude/skills/policy-compliance-order/SKILL.md` line 32 states: "Do NOT
   modify policy documents under `.claude/rules/` **or `.github/instructions/`**." The epic's
   "Execution Authorization Required" section (lines 183-197) suspends this constraint only for
   `CLAUDE.md`, `.claude/rules/csharp.md`, `.claude/rules/general-unit-test.md` and
   `.claude/rules/quality-tiers.md`. `.github/instructions/` is named in the constraint and *not*
   named in the authorization. It is therefore still hard-blocked. This directly answers the
   delegation prompt's question of whether the mirrors "fall under a comparable constraint": for
   `.github/instructions/` the constraint is not merely comparable, it is the *same clause*.
3. **`AGENTS.md` forbids manual editing and its generator is missing.** Editing it by hand violates
   its own stated contract, and the correct alternative — regenerating it — is impossible in this
   repository.
4. **Diff width.** Tier 3 adds 17 sites across 7 files to a feature the epic scoped to 3 files.

### Recommendation

**Exclude the entire Tier 3 mirror tree from this feature.** Confidence: **High**.

Reason 2 alone is dispositive for `.github/instructions/` — it is an unsuspended hard constraint, and
the correct response to an unsuspended constraint is to stop, not to widen scope. Reasons 1 and 3
then make `AGENTS.md` and `.agents/` follow automatically, since `AGENTS.md` is a pure function of
`.github/instructions/` and `.agents/` is a pure function of an external repository.

**Required accompanying action:** file a follow-up issue via the MCP promotion lifecycle
(`new_potential_bug_entry` then `potential_to_issue`) titled to the effect of "Codex/Copilot
instruction mirrors still document the v0 csharpier and unpassable nullable commands", listing the 17
Tier 3 sites from Q1 and naming `drm-copilot` as the owning repository for `.agents/` and `.codex/`
and `.github/instructions/` as requiring a separate authorization grant. Without this, the residual
divergence is recorded only in this research artifact, which disappears from the working set at
merge.

## Q3 — Corrected Nullable Command Design

### Evidence base

**Vacuity of `/t:Build` (#512) — corroborated three independent ways.**

| Signal | Source | Value |
|---|---|---|
| Elapsed time of the documented nullable step | ~12 committed evidence artifacts under `docs/features/**` | 0.89 s - 1.51 s |
| Elapsed time of the analyzer step over the same solution | same artifacts | 6.29 s - 17.02 s |
| `CoreCompile`-emitted `CS2002` warning present in analyzer log, absent in nullable log | `.../508/evidence/baseline/msbuild-nullable.2026-08-08T16-19.md` lines 18-30 | conclusive for that run |
| `Skipping target "CoreCompile"` count under `/t:Build` after a prior build | `.claude/agent-memory/orchestrator/msbuild-analyzer-gate-vacuous-without-rebuild.md` (measured on #505) | 18 skips, 0 `csc.exe` invocations, EXIT 0 |

**Conflicting evidence, reported for completeness.**
`docs/features/active/2026-08-06-quickfiler-high-confidence-queue-init-stall-424/evidence/baseline/nullable-build-baseline.2026-08-06T22-23.md`
lines 27-32 asserts the opposite: 18 `CoreCompile` executions and 0 up-to-date short-circuits under
`/t:Build` with `/p:Nullable=enable`, at EXIT 0 with 0 errors. That artifact also records
`Time Elapsed 00:00:01.20`-class behavior implicitly by claiming a full 18-project compile. Two
days later the `/t:Rebuild` probe with identical properties produced 195 errors. Both cannot be true
unless `UtilitiesCS` acquired 195 nullable errors in 48 hours. The likelier explanation is that the
08-06 non-vacuity measurement counted `CoreCompile:` log *headers* rather than executions. The
08-08 artifact's two signals (elapsed time and `CS2002` presence) are more robust because neither
depends on log-line-shape interpretation. **This does not change the recommendation**, because the
recommended command is correct under either reading: it is `/t:Rebuild` (defeating vacuity if
present) *and* CI-verbatim (resolving divergence regardless).

The agent-memory record `.claude/agent-memory/atomic-executor/project_nullable_pragma_gate_mechanics.md`
line 15 propagates the 08-06 claim as a current "STATUS" and instructs agents not to preflight-block
on it. That memory entry is stale relative to the 08-08 measurement and should be corrected by
whichever agent owns it; it is flagged here, not edited.

**Divergence from CI (#522).** `ci.yml` lines 106-116 carry the rationale in-line and run
`/t:Rebuild /m ... /p:TreatWarningsAsErrors=true` with no `/p:Nullable=enable`. Verified: **no
`.csproj` in the repository contains a `<Nullable>` element** (grep across all 18 `*.csproj` returned
no matches) and **no `Directory.Build.props` exists anywhere** in the worktree. Nullable participation
is therefore entirely per-file pragma-driven, exactly as `ci.yml` states.

**Destructive failure mode of `/t:Rebuild` when it fails.** `.../508/evidence/baseline/msbuild-nullable.2026-08-08T16-19.md`
lines 85-99 records that the failed `/t:Rebuild` probe "deleted all build outputs and then failed at
`UtilitiesCS`, leaving `UtilitiesCS\bin\Debug\UtilitiesCS.dll` and
`UtilitiesCS.Test\bin\Debug\UtilitiesCS.Test.dll` absent," requiring a restorative build. Corroborated
by `.claude/agent-memory/atomic-executor/project_repo_sdk_and_nullable_rebuild.md` line 29: Rebuild
"issues Clean+Build to every project in the solution before the first CoreCompile runs, so a mid-build
failure ... leaves ALL projects' `obj`/`bin` outputs deleted." This is a decisive argument against any
option under which the gate is expected to fail routinely.

### Options evaluated

**(a) Adopt CI's exact command verbatim — RECOMMENDED.**
`msbuild TaskMaster.sln /t:Rebuild /m /p:Configuration=Debug "/p:Platform=Any CPU" /p:TreatWarningsAsErrors=true`

- *Executes:* yes. `/t:Rebuild` forces `Clean` then `Build`, so `CoreCompile` runs unconditionally.
- *Enforces:* yes. Every file carrying `#nullable enable` is analyzed and its `CS86xx` diagnostics are
  promoted to errors by `/p:TreatWarningsAsErrors=true`. It additionally enforces all non-nullable
  compiler warnings, which the current command does not enforce either.
- *Agrees with CI:* by construction — it is character-for-character the command at `ci.yml` 113-115.
- *Green on clean `main`:* CI runs this command on every PR to `main`/`development` from a clean
  checkout. That it is green is strongly implied but **not directly verified by this agent** (no
  `gh` access); see Open Questions.
- *Does it weaken policy?* No, and this must be stated explicitly in the spec because a reviewer
  will challenge it. Removing `/p:Nullable=enable` removes a property that **no merge gate has ever
  enforced**. The enforcement delta is strictly positive: today the documented gate enforces nothing
  (it does not compile); afterwards it enforces exactly what CI enforces. Going from zero enforcement
  to CI-parity enforcement is a strengthening, not a relaxation.
- *Cost:* a genuine full solution compile per toolchain pass. See timings below.

**(b) `/t:Rebuild` while keeping `/p:Nullable=enable` — REJECTED, and inadmissible.**
The delegation prompt asks whether "do not weaken a policy to make a gate pass" cuts against
rejecting this. It does not, for three reasons. First, the gate is not merely red; it is
*unpassable within this feature's authorized scope*, because the epic declares the debt burn-down an
explicit Non-Goal (epic.md lines 77-80). A documented mandatory command that cannot pass is not a
gate; it is a permanent blocker that every session must override, which is what produced the #507 and
#508 human overrides. Second, per the destructive-failure evidence above, a routinely-failing
`/t:Rebuild` deletes every project's build outputs on every toolchain pass, so step 4 (vstest) would
have no assemblies to run. Third, it would *increase* divergence from CI rather than remove it,
directly contradicting the required outcome. Not admissible.

**(c) Keep `/t:Build` plus a non-vacuous-compile assertion from an `/fl` log — REJECTED.**
This is a sound *verification* technique and is already the standing recommendation in
`.claude/agent-memory/orchestrator/msbuild-analyzer-gate-vacuous-without-rebuild.md`. But as the
*documented command* it fails the simplicity principle in `.claude/rules/general-code-change.md`
(two commands plus a log-parsing step where one command suffices), it does not converge with CI, and
it turns a policy line into a procedure that every agent must implement identically. Recommend
retaining the `csc.exe`-count technique as an optional diagnostic in plan preflight, not as the
policy command.

**(d) Persist `<Nullable>` in `Directory.Build.props` or per-`.csproj` — REJECTED.**
Verified: no `Directory.Build.props` exists and no `.csproj` carries `<Nullable>`. Adding one would
make the property participate in the up-to-date check (solving the vacuity), but it would opt in
every file in the affected projects at once — which *is* the debt burn-down the epic explicitly
excludes. Out of scope by charter.

**(e) Scope `/p:Nullable=enable` to opted-in projects only — REJECTED.**
No project can opt in cleanly today. The 2026-08-08 forced-rebuild measurement attributes 195 errors
to `UtilitiesCS.csproj`, and `.claude/agent-memory/orchestrator/project_claudemd_nullable_command_diverges_from_ci.md`
line 23 records a further 219 in `TaskMaster.csproj`. `.claude/agent-memory/atomic-executor/project_repo_sdk_and_nullable_rebuild.md`

## Q4 — Corrected Format Command Design

### Evidence

- `dotnet-tools.json` pins `csharpier` at `1.2.6` with `"rollForward": false`.
- Measured by the orchestrator in this worktree on 2026-08-10: `dotnet tool run csharpier .`
  returns **EXIT 1** with `Required command was not provided.` / `Unrecognized command or argument '.'`.
- `.claude/agent-memory/atomic-executor/project_repo_sdk_and_nullable_rebuild.md` line 15 records
  independently: "CSharpier is a local tool pinned at 1.2.6 (`dotnet-tools.json`). v1 uses
  SUBCOMMANDS: `csharpier check .` and `csharpier format .` (the old `--check`/bare-path v0 syntax is
  gone). A separate global csharpier (1.3.0) exists at `~/.dotnet/tools` — prefer the manifest
  version via `dotnet tool run`."
- Two in-repo precedents already use the correct v1 form: `.vscode/tasks.json` lines 54-63
  (`dotnet tool run csharpier format .`) and `.codex/codex-web-setup.sh` line 339.

### The version-pinning trap

`#509` names the real hazard precisely: a globally installed CSharpier 1.3.0 accepts the bare-path
form, so a session that runs `csharpier .` may silently format with an unpinned version. This is not
hypothetical — `.claude/agent-memory/atomic-executor/project_csharpier_formats_xml_print_width.md`
records a 1.3.0-driven formatting outcome on `TaskMaster/Ribbon/RibbonExplorer.xml` during issue
#503 that a scoped gate could not reproduce. Divergence between a global 1.3.0 and the manifest
1.2.6 would produce diffs that fail CI's `dotnet csharpier check .`.

The mitigation is to remove the global-install alternative from the approved-commands list entirely
(rows 2, 3, 7 and 9 in the Q1 table) and to state the pinning requirement as a rule rather than a
preference.

Note that CI's `dotnet csharpier check .` (line 93, preceded by `dotnet tool restore` at line 89) is
**also** manifest-resolved: the `dotnet` CLI resolves `csharpier` through `dotnet-tools.json` when a
local manifest is present. `dotnet tool run csharpier ...` is the more explicit spelling and is
recommended for documentation because it cannot be mistaken for a global invocation. `ci.yml`
requires no change on this point.

### Documenting both roles without ambiguity

The toolchain's step 1 must be able to mutate; CI's gate must not. Recommend documenting them as one
step with a stated verification form, rather than as two competing "approved commands":

> **1. Format — CSharpier (pinned via `dotnet-tools.json`, currently 1.2.6)**
> - Apply formatting: `dotnet tool run csharpier format .`
> - Verify (CI parity, read-only): `dotnet tool run csharpier check .`
> - CI runs the read-only form (`.github/workflows/ci.yml`). A local pass must end with `check`
>   reporting no differences.
> - Always invoke through `dotnet tool run` so the `dotnet-tools.json` manifest version is used. Do
>   **not** invoke a globally installed `csharpier`; a different global version produces diffs that
>   disagree with CI.
> - Run `dotnet tool restore` once per clone or worktree before the first invocation.

### Q4 recommendation

Adopt the block above verbatim at every Tier 1 format site. Confidence: **High**. The syntax claim is
empirically confirmed by the orchestrator's measured EXIT 1, and two in-repo files already use the
recommended form.
