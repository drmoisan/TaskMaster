SecurityCodeScan.VS2019 5.6.7 cannot be loaded by the Roslyn 5.6.0 analyzer host in this repo's build toolchain (VS18 Community / csc 5.6.0-2.26230.15).

**Why:** Its analyzer types throw TypeInitializationException -> FileNotFoundException for `YamlDotNet, Version=11.0.0.0` (the analyzer's own dependency). Wiring the co-located YamlDotNet.dll as a sibling `<Analyzer Include>` does NOT resolve it — the Roslyn 5.6 load context will not satisfy SecurityCodeScan's `Assembly.Load(YamlDotNet, 11.0.0.0)` from a sibling analyzer entry. This surfaces as CS8032 (a COMPILER warning, not an analyzer rule), so it CANNOT be neutralized via `.editorconfig` `dotnet_diagnostic.<rule>.severity = suggestion`. Under `/p:TreatWarningsAsErrors=true` (the protected nullable CI gate) CS8032 is promoted to an error and breaks the build. Discovered during issue #181 analyzer-stack hardening (P4-T16): wiring all 6 analyzers added +16 CS8032 errors to first-party projects vs the 84-error vendored-only baseline.

**Resolution (#181 plan v2.0):** SecurityCodeScan.VS2019 was DROPPED entirely from the rollout — documented deferral in `.claude/rules/csharp.md`, NO CS8032 suppression, no substitute security analyzer. The adopted stack is the 5 analyzers below. Caveat for future debugging: during the v2.0 cleanup the CS8032 regression did NOT always reproduce (with the package's co-located YamlDotNet.dll physically present in `analyzers/dotnet/`, the nullable Rebuild returned the 84-error baseline with 0 CS8032 even while the `<Analyzer Include>` items were still wired). Treat the +16 CS8032 as environment/restore-state-dependent, not perfectly deterministic — but still remove SecurityCodeScan wiring entirely; do not rely on it not firing.

**How to apply:** The other 5 analyzers (Meziantou 3.0.101, SonarAnalyzer.CSharp 10.27, Roslynator.Analyzers 4.15 [roslyn4.7 subfolder], AsyncFixer 2.1.0, Microsoft.CodeAnalysis.BannedApiAnalyzers 3.3.4) load cleanly at suggestion severity and do not regress the gate. If asked to add SecurityCodeScan, either find a Roslyn-5.x-compatible variant, defer it, or get explicit authorization for a narrowly-scoped CS8032 suppression (which would mean SecurityCodeScan does not actually run). Also note: Meziantou and Roslynator ship roslyn-version subfolders (analyzers/dotnet/roslynX.Y/cs/) — for non-SDK packages.config projects you must hard-code the correct subfolder in `<Analyzer Include>` (Meziantou roslyn5.0, Roslynator roslyn4.7); NuGet does not auto-select it. CSharpier 1.2.6 ALSO formats XML project files (`.csproj`/`packages.config`), so editing those files dirties the `csharpier check .` gate until you run `csharpier format` on them. RS0030 (BannedApiAnalyzers) fires correctly against banned symbols but only surfaces in MSBuild output at warning+ severity (suggestion-level analyzer messages are not printed by the console logger at any verbosity) — to verify it fires, temporarily set `dotnet_diagnostic.RS0030.severity = warning`, build, then revert.
