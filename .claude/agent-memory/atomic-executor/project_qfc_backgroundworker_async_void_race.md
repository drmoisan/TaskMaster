`QfcDatamodel.Worker_DoWork(object sender, DoWorkEventArgs e)` (`QuickFiler/Controllers/QfcDatamodel.cs`) is declared `private async void`. `BackgroundWorker`'s internal `WorkerThreadStart` invokes the `DoWork` delegate synchronously and, the instant that call **returns control** (for an `async void` method, this is at its first genuinely-asynchronous `await`, not at logical method completion), treats the work as finished and raises `RunWorkerCompleted`, resetting `isRunning` (`BackgroundWorker.IsBusy`) back to `false`. `Worker_DoWork`'s body (`await LoadRemainingEmailsToQueueAsync(_token)` → `await Task.Run(...)`) hits a real await almost immediately, so `IsBusy` can flip back to `false` before a caller's very next line of code executes.

**Why:** Discovered while executing issue #244's plan-specified test `InitEmailQueue_ZeroBatchSize_StillStartsBackgroundWorker`, which asserts `worker.IsBusy.Should().BeTrue()` synchronously right after calling `model.InitEmailQueue(0, new BackgroundWorker())`, with the plan's own text asserting "no synchronization ... is required." Empirically this is false: the same exact test/assertion reliably **failed 7/7 times** when run via a narrow `vstest /TestCaseFilter` matching only 3 tests (this one preceded by another test that also creates+starts a `BackgroundWorker`, warming the ThreadPool so the race resolves against the assertion), but reliably **passed 2/2 times** in the full 472-test `QuickFiler.Test` suite run (different ThreadPool warm state/scheduling). It also passed 3/3 times when run as the *only* matching test (cold ThreadPool gives the calling thread's next line a head start over `Delegate.BeginInvoke`'s dispatch latency).

**How to apply:**
- This is a pre-existing behavior of `SetupWorker`/`Worker_DoWork`/`RunWorkerAsync()`, shared verbatim by every `InitEmailQueue` code path (both `batchSize <= 0` and `batchSize > 0`) — it is not introduced by any specific `InitEmailQueue` change and is not a production regression signal.
- Do not "fix" a failing `worker.IsBusy` assertion by adding a sleep/retry (masks flakiness, prohibited by `.claude/rules/csharp.md`). The synchronous, reliable half of the same assertion is `worker.WorkerSupportsCancellation.Should().BeTrue()` (set directly by `SetupWorker`, no race).
- If a future plan needs a deterministic proof that `RunWorkerAsync` was invoked, do not rely on `BackgroundWorker.IsBusy` read synchronously post-call. Prefer: (a) `WorkerSupportsCancellation` alone, (b) reflection-checking `worker.DoWork`'s invocation list is non-empty (proves `SetupWorker` wired the handler without needing `IsBusy` at all), or (c) an injected spy/counter instead of the real `BackgroundWorker.RunWorkerAsync()->IsBusy` path.
- When auditing/reviewing any test in this codebase that reads `BackgroundWorker.IsBusy` immediately after `RunWorkerAsync()` with an `async void` `DoWork` handler, treat it as a latent flaky-test risk regardless of whether it happens to pass in a given run — its pass/fail outcome is a function of which other tests run adjacently, not of the code under test.
