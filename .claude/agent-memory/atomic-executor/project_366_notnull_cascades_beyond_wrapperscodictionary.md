On epic child #366 (utilitiescs-nullable-reusabletypes), applying the ratified `where TKey : notnull` constraint to `ConcurrentObservableDictionary<TKey,TValue>` forces the same constraint onto every nullable-enabled #367 consumer that passes an UNCONSTRAINED `TKey`. The epic Option-A waiver predicted only `WrapperScoDictionary<TDerived,TKey,TValue>` (`UtilitiesCS/NewtonsoftHelpers/WrapperScoDictionary.cs`, 4 CS8714 sites) and authorized EXACTLY that one file + one clause.

Reality (measured 2026-07-19, VS18 isolated UtilitiesCS.csproj `/t:Rebuild /p:TreatWarningsAsErrors=true /p:BuildProjectReferences=false`): once `WrapperScoDictionary` itself gets the constraint, a SECOND #367 NewtonsoftHelpers file — `ScoDictionaryConverter<TDerived,TKey,TValue>` in `UtilitiesCS/NewtonsoftHelpers/ScoDictionaryConverter.cs` — emits 3 unique CS8714 (lines 27,28,40; double-counted to 6 under recompile) because it constructs `WrapperScoDictionary<TDerived,TKey,TValue>` / `serializer.Deserialize(..., typeof(WrapperScoDictionary<TDerived,TKey,TValue>))` with its own unconstrained `TKey`. Its `where TDerived : ScoDictionaryNew<TKey,TValue>` would independently force the same constraint once ScoDictionaryNew is constrained in Phase 8, so this file needs `where TKey : notnull` regardless.

**Why:** the cascade is inherent to constraining any of the four generic dictionary bases — it propagates to every generic #367 wrapper/converter with an unconstrained TKey, not just the direct WrapperScoDictionary consumer.

**How to apply:** the minimal fix that closes the ScoDictionaryNew/ConcurrentObservableDictionary chain is symmetric — add `where TKey : notnull` to `ScoDictionaryConverter<TDerived,TKey,TValue>` (one line, after its `where TDerived : ...`). Verified-safe non-cascade files: `PeopleScoConverter` references WrapperScoDictionary only in commented-out code and is otherwise concrete (`PeopleScoDictionaryNew`); `WrapperPeopleScoDictionaryNew` uses concrete `ScoDictionaryNew<string,string>` / `ConcurrentObservableDictionary<string,string>` — neither emits CS8714. So a widened waiver of exactly TWO files (WrapperScoDictionary.cs + ScoDictionaryConverter.cs), one `where TKey : notnull` line each, clears the ScoDictionaryNew chain. Under the original one-file bounded waiver this is a hard STOP — do not suppress with `#pragma warning disable`, do not widen unilaterally; report and get the waiver extended. See [[project_scodictionarynew_tryadd_not_add]].

**Batch 8 (#366) discovered a SEPARATE, THIRD chain (2026-07-19):** the ratified `where TKey : notnull` on `ScDictionary<TKey,TValue>` (a plain `ConcurrentDictionary`-based serializable dict, NOT the observable ScoDictionaryNew) cascades into its OWN wrapper `WrapperScDictionary<TDerived,TKey,TValue>` (`UtilitiesCS/NewtonsoftHelpers/WrapperScDictionary.cs`, line 18/19: `where TDerived : ScDictionary<TKey,TValue>`, unconstrained TKey, already `#nullable enable` via merged #367) — 1 unique CS8714 (double-counted to 2 under Rebuild). This file is NOT one of the two Batch-6-waived files, so it is a hard STOP requiring a fresh epic waiver-extension decision. Note: `ScoDictionaryStatic` is listed in the [P6-T2] ratification as one of the "four generic dictionary bases" but is actually a NON-generic `static class` of Type extension methods — the `where TKey : notnull` constraint is mechanically inapplicable there (no TKey). Batch-8 green state = ScoDictionaryNew constrained (required, cascade absorbed by the two waiver files), ScDictionary constraint REVERTED to keep the tree green pending the epic decision. `ScBag` is `ConcurrentBag<T>`-based, no constraint.
