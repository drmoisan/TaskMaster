Under `[assembly: Parallelize(Workers=0, Scope=ClassLevel)]`, a `[DoNotParallelize]` class is NOT run in a phase that is disjoint from the parallel bucket. Empirically (issue #292, CI run 29046195330, 10 real failures), `CurrentStoreContextTests`/`ThreadMonitorTests` are `[DoNotParallelize]` and assert `CurrentStoreContext.Current == null`, yet observed `"<Stores-enumeration>"` written by `StoresWrapper`/`StoreWrapper` test classes still executing in the parallel bucket. So `[DoNotParallelize]` on a reader alone does NOT stop concurrent writers in other classes of the same assembly.

**Why:** the process-global `static volatile string CurrentStoreContext._current` (UtilitiesCS/Threading/CurrentStoreContext.cs:32, deliberately not AsyncLocal because the #260 watchdog reads it cross-thread) is shared; the serial and parallel buckets overlap in wall-clock time.

**How to apply:** The correct mutual-exclusion guarantee is NOT "serial bucket doesn't overlap parallel bucket" (false here). It is: mark EVERY class that transitively opens a scope on the shared static `[DoNotParallelize]`, so (a) the serial bucket serializes all its members relative to each other, and (b) ZERO writers remain in the parallel bucket. Then no read can overlap any write. A census that only lists readers is insufficient; enumerate writers by grepping for the scope-opening production calls (e.g. `CurrentStoreContext.Begin`, `StoresWrapper.Init/CreateAsync/RewireOlObjectsAsync/AddOrRestoreStore`, `StoreWrapper.Init/Restore`), not merely constructor references (constructing `StoresWrapper` does not open a scope).

**Cross-assembly + coverage-runsettings gotcha (corrected 2026-07-09, #292 remediation):** `TaskMaster.Test` ALSO has this race intra-assembly: `StoresWrapperEnumerationScopeTests` (the AC3/AC4 `Init...ClearsContextAfterReturn` / `EnumerationThrowsMidStream...Null` regression tests) is an unmarked scope-opening null-baseline reader (`AppOlObjectsAttributionContextTests` is already `[DoNotParallelize]`). `TaskMaster.Test` has NO `[assembly: Parallelize]`, so it runs SEQUENTIALLY (race-free) under the plain CI `vstest ... /EnableCodeCoverage` invocation — which is why only UtilitiesCS.Test turned CI red. BUT the repo coverage path `dotnet-coverage collect -- vstest ... /Settings:scripts/vscode/TaskMaster.cli.runsettings` force-imposes `<Parallelize Workers=0 Scope=ClassLevel>` on EVERY assembly, activating TaskMaster.Test's latent race (2-3/250 flakes when TaskMaster.Test is run alone under that runsettings). So: the same defect can be dormant in an assembly with no parallelize attribute and surface only under a coverage-measurement runsettings; verify with a repo-wide (not per-assembly) grep for `CurrentStoreContext` readers, and run the coverage path AND the plain `/EnableCodeCoverage` path — they expose different failures. See [[project_utilitiescs_test_parallelism_flakiness]].
