description: A ratified generic constraint on a base type cascades CS8714 through EVERY nullable-enabled downstream consumer; in an epic those consumers span sibling children, so a one-file waiver estimate undercounts

  type: project
---

Adding `where TKey : notnull` (or any generic constraint) to a shared base type emits CS8714 in EVERY `#nullable enable` downstream consumer that passes an unconstrained type argument — not just the first one found.

**Why:** In epic utilitiescs-nullable-remediation, child #366 ratified `where TKey : notnull` on four dictionary bases. The epic layer authorized an Option-A waiver for EXACTLY ONE cross-child file (`WrapperScoDictionary.cs`, #367-owned), assuming that was the whole cascade. On execution, clearing WrapperScoDictionary surfaced 3 NEW CS8714 in a SECOND #367 file, `ScoDictionaryConverter.cs` (`ScoDictionaryConverter<TDerived,TKey,TValue> : JsonConverter<TDerived>` with unconstrained TKey and `where TDerived : ScoDictionaryNew<TKey,TValue>`). The "one-line propagation" estimate undercounted because the base type had two nullable-enabled consumers in the sibling child, and the pragma-gate rebuild reveals them one build at a time.

**How to apply:** (1) Before estimating a constraint-propagation waiver, statically enumerate ALL nullable-enabled consumers of the constrained type across the WHOLE assembly/epic (grep for the type name under `#nullable enable` files), not just the site that first errors. Concrete-type-argument consumers (e.g. `ScoDictionaryNew<string,string>`) are SAFE; unconstrained-generic consumers REQUIRE the constraint. (2) A child orchestrator granted a bounded one-file waiver MUST STOP and re-escalate when the cascade needs a second file — do NOT self-widen (contrast: the epic layer, not the child, owns the scope-boundary decision). (3) The isolated per-file pragma gate (`msbuild <proj>.csproj /t:Rebuild /p:TreatWarningsAsErrors=true`, no `/p:Nullable=enable`) is what surfaces each cascade site; expect to iterate. Related: [[parallel-epic-children-name-collisions]] (cross-child surfacing at rebase).

**2026-07-20 update (the two-file waiver ALSO undercounted).** The waiver was extended to two files (WrapperScoDictionary.cs + ScoDictionaryConverter.cs) and Batches 6/7 completed green. But in Batch 8, applying the ratified constraint to the FOURTH base `ScDictionary<TKey,TValue>` surfaced a THIRD #367-owned consumer, `WrapperScDictionary.cs(18)` — each `Sc*/Sco*` dictionary base has its OWN `Wrapper*`/`Converter*` consumer pair, so enumerate the derivation chain PER BASE, not once. Two further concrete lessons: (a) `ScoDictionaryStatic` is NOT generic — it is a non-generic `static class` of `Type` extension methods with no `TKey`, so the plan's "four generic bases" wording was factually wrong for it (constraint mechanically inapplicable, reaches 0/0 regardless); verify each named "base" is actually a generic type before planning a constraint for it. (b) The child correctly HALTED again at the third consumer per its explicit third-consumer re-escalation clause and committed the green partial batch (ScoDictionaryNew constrained, ScDictionary constraint reverted, cluster 0/0, 5702 tests) rather than self-widening. Ship-green-without-the-constraint (net481 no-op) remains the in-scope fallback (Option B) since CS8714 is never actually emitted on net481's un-annotated BCL.

**2026-07-20 second update (the THREE-file waiver ALSO undercounted — now proven symmetric).** Epic authorized A' (third file WrapperScDictionary.cs). On execution, constraining `ScDictionary` + `WrapperScDictionary` surfaced a FOURTH #367-owned consumer `ScDictionaryConverter.cs` (NO 'o'; distinct from the waived `ScoDictionaryConverter.cs` WITH 'o'), 4 CS8714 sites. The rule is now concrete and symmetric: **each constrainable dictionary family contributes exactly TWO cross-child consumer files — a `Wrapper*` AND a `*Converter*`.** The Sco family = {WrapperScoDictionary.cs, ScoDictionaryConverter.cs}; the Sc family = {WrapperScDictionary.cs, ScDictionaryConverter.cs}. Two constrainable families ⇒ FOUR consumer files, discoverable in ONE upfront grep (`grep -rl "where TDerived : Sc" UtilitiesCS/NewtonsoftHelpers` or grep the base type names across `#nullable enable` files) instead of four sequential pragma-gate escalations. The child again HALTED at the fourth file per its A' fourth-consumer re-escalation clause (tree green at the pre-constraint HEAD, ScDictionary deferred). Cost of NOT enumerating upfront: four separate epic-layer round-trips (one, two, three, four files) for what a single `grep` would have scoped as a four-file waiver at the outset.
