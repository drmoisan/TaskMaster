When a preparation-mode child dies on an infrastructure error (API failure, org monthly spend
limit) rather than a task failure, its worktree survives but **its entire feature folder is
typically uncommitted** — the preparation-mode kickoff line only tells it to commit *after*
`PREFLIGHT: ALL CLEAR`, so a child killed before that point has committed nothing.

`SendMessage` is **not** in the `epic-planner` tool set (only `Agent`, `Read`, `Grep`, `Glob`,
`Write`, `Edit`, `Bash`, and the MCP validator), so resuming a child in place is not possible even
when the caller asks for it. Relaunching naively is destructive, because a fresh `Agent` call gets
a **new** worktree and the old worktree's uncommitted work is never seen.

Recovery procedure:

1. `git -C <wt> status --porcelain` and `git -C <wt> log --oneline origin/<integration>..HEAD` for
   every surviving worktree. Uncommitted feature folder plus zero commits is the common shape.
2. Commit each worktree's work onto its own `bug/<slug>` branch yourself, with explicit pathspecs
   (`docs/features/active/<folder>` plus `.claude/agent-memory`), stating in the message that
   epic-planner preserved it after an infrastructure termination and that preflight was not
   reached.
3. `git push -u origin bug/<slug>` for each — durable backup, and it lets a fresh worktree check
   the branch out.
4. Force-remove the now-clean worktrees. Required, not optional: git refuses to check a branch out
   in two worktrees, so the old worktree must go before the relaunched child can use the branch.
   Some agent worktrees are locked and need `git worktree remove -f -f`.
5. Relaunch with a prompt whose first section is "THIS IS A RESUME, NOT A FRESH RUN": check out the
   preserved branch, merge the current integration tip, enumerate the artifacts that already exist,
   and state the specific remaining step.

Two things the relaunched child must be told explicitly:

- **Rebuild the child-scoped checkpoint.** `artifacts/` is gitignored, so the checkpoint does not
  travel with the branch and is absent in the new worktree.
- **Trust on-disk artifacts over the dead run's `next_step`.** Child checkpoints lag badly; one
  child's checkpoint said `next_step: S2_research` while its folder already held research, three
  feature documents, an atomic plan, and nine evidence artifacts.

Also re-verify each child's real state rather than the last reported line: a caller's summary of
"where it left off" is a report from the dead agent's context, not ground truth, and findings held
only in that context (for example a preflight's specific blocking-defect list) are gone and must
be regenerated by re-running the gate.

## Mass simultaneous failure and the worktree-lock reality (2026-08-21)

A single `API Error: 529 Overloaded` killed 3 of 4 preparation children at once, plus two grandchild
preflight validators, each of which had emitted only an opening line and verified nothing. Treat a
529 as an infrastructure event affecting the whole fan-out, not as N independent task failures, and
do NOT immediately relaunch — a retry into a degraded API usually dies the same way and burns another
full batch.

Two things measured that run which contradict the obvious assumption:

- **Not every agent worktree is locked, and the lock does not identify the agent.** Only 2 of 4 were
  locked. Both lock files read `claude agent agent-<id> (pid NNNN)` with the SAME pid — that is the
  parent Claude process, not a per-agent holder. So a lock proves nothing about whether the agent
  that created the worktree is alive. Determine liveness from the completion notification and from
  artifact mtimes, then release a dead agent's lock deliberately before relaunching into it.
- **Checkpoint `next_step` can lag by three whole steps.** One child's checkpoint read
  `next_step: S2_research` while its folder already held `issue.md`, `spec.md`, a research artifact,
  and a revised atomic plan, and its receipts showed researcher, prd-feature, planner, executor,
  prd-feature, planner. Read the artifacts and the `delegation_receipts` agent list; never size the
  remaining work from `next_step`.

Also verify preflight yourself before believing any of it: grep each child checkpoint for a
`PREFLIGHT` token. In that run **zero of four** items had `PREFLIGHT: ALL CLEAR` even though three
children had produced complete-looking plans. An `atomic-planner` may also report
`VALIDATOR NOT RUN` because the MCP validator is absent from ITS tool surface — epic-planner can run
`validate_orchestration_artifacts artifact_type=plan` against the child worktree root itself and
close that gap, but a passing plan validator is a structural/G1-G6 check and is NOT preflight
clearance.

## Relaunch scoped to PREFLIGHT ONLY, and fan in the feature-only commit

The 2026-08-21 recovery relaunched all four children with a prompt whose entire job was the
`atomic-executor` preflight. Research, spec, and a validator-passing plan already existed on each
preserved branch, so the prompt listed each artifact with its byte size and said plainly: do not
re-run research, do not rewrite the spec, do not regenerate the plan, "a plan that already passes
the validator must not be churned." All four cleared. Narrow scoping is what made a second full
fan-out affordable after the first was destroyed.

Two operational details that made it work:

- **Remove the old worktree before relaunching.** Git refuses to check a branch out in two
  worktrees, so a relaunched child cannot use the preserved branch until the dead child's worktree
  is gone. Verify first that `HEAD` equals the merged branch tip and that `git status --porcelain`
  shows nothing outside `.claude/agent-memory/`, then remove.
- **Resume from the CURRENT branch head, not the preservation commit.** If anything merged into the
  branch family between preservation and relaunch (here, a `main` merge restoring 61 records), the
  preservation commit is stale and resuming from it silently re-introduces whatever that merge
  fixed. State the correct SHA in the prompt and say why.

**Fan in the feature-only commit, not the branch tip.** Children commit their subagents'
`.claude/agent-memory/` writes as separate trailing commits, and they do it inconsistently — in that
run one child left them uncommitted while three committed them. Merging the last feature-only
commit (`git merge <sha>` rather than the branch) keeps the integration branch to deliverables,
keeps all children symmetric, and loses nothing: the memory commits stay on the pushed branch and
are recoverable. Check the shape first with
`git show --name-only --format="" <sha>` over `git rev-list <base>..<branch>`.

Also worth knowing: preflight is not ceremony. In that run it found a blocking defect in **every**
plan, all of the same class — an instruction that reads as authoritative but cannot be satisfied at
execution time (an undefined variable making `vstest` run against zero assemblies and report zero
failures; a workspace root pinned to a deleted worktree under a "verified, do not re-derive" header;
a line-range deletion invalidated by an earlier task in the same plan). None is catchable by the
plan validator, because each spans two tasks or depends on repository state.
