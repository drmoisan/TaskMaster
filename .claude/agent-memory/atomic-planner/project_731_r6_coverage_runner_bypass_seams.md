A plan that runs `pwsh -File scripts\vscode\Invoke-MSTestWithCoverage.ps1` from an agent worktree deterministically self-blocks. Its discovery filter at `scripts/vscode/Invoke-MSTestWithCoverage.ps1:296-303` ends with `$_.FullName -notmatch '\\\.claude\\'` (`:301`); an agent worktree lives under `...\TaskMaster\.claude\worktrees\<id>`, so every built assembly fails the predicate, `$testAssemblies` is empty, and the script throws at `:305-307` and writes no Cobertura document at all. Tracked as issue #752.

**Why:** #731's plan cleared preflight in five rounds with `[P0-T9]`/`[P5-T5]` invoking the script, and `[P0-T10]` said "if the document does not exist, report a blocked toolchain" — so the plan could never reach Phase 1.

**How to apply:** replace the script invocation with a dot-sourced procedure and verify each seam before citing it:
- The script is safe to dot-source: its entry point is guarded by `if ($MyInvocation.InvocationName -ne '.')` at `:348`. Dot-sourcing does execute `Set-StrictMode -Version Latest` and `$ErrorActionPreference='Stop'` (`:245-246`) in the caller's scope, so every later snippet must use `GetAttribute('...')`.
- Dot-source `Invoke-MSTestWithCoverage.Helpers.ps1` separately — the script only loads it inside `Invoke-MSTestWithCoverageMain` (`:261`). Helpers dot-sources ClosureFilter/PackageRate/Threshold at `:2-4`.
- Call `Invoke-DotnetCoverageCollection` (`:172`, five mandatory params at `:181-196`) with an explicit `-TestAssembly` list. Reuse this seam rather than a bare `vstest.console.exe`: `Get-DotnetCoverageArgumentList` appends `/InIsolation` and `/TestCaseFilter:TestCategory!=LiveOutlook` at `:76`, and a hand-rolled command would attempt live-Outlook tests.
- It throws at `:235-237` on a non-zero child exit, but only **after** `dotnet-coverage` has written the raw document — wrap in try/catch, record the code, continue.
- Create the output directory first: the function writes a derived settings file adjacent to `-OutputPath` (`Get-DerivedCoverageSettingsPath`, `:118`).
- Post-process by calling `ConvertTo-KoverageCoberturaXml` yourself into a **distinct** path. Doing so outside the try/catch makes both baseline and post-change documents always `processed`, which collapses any raw/processed degraded-run branching to nothing. Distinct paths also make baseline preservation trivial.
- Rebuild the assembly list with the script's own predicates minus the broken one, and apply the nested-worktree exclusion to `[IO.Path]::GetRelativePath($root, $_.FullName)` with `(^|\\)\.claude\\` — see [[project-752-relative-path-anchor-plan-seams]] for why the leading alternation is required.

**Round 7 — three self-blocking gate shapes the earlier rounds introduced.**

1. *A drive-letter scan is not a raw/processed discriminator.* `ConvertTo-KoverageRelativePath` (`Helpers.ps1:52`) builds a candidate prefix list at `:67-85` and at `:87-92` strips a prefix **only when one matches**, returning every other path unchanged; `:435-437` runs it over `//class[@filename]`. So a correctly processed document still carries drive-letter `filename` values for every source outside the repository root — measured at 410 of 1442 on this harness. A gate of the form "state is `raw` if ANY `class/@filename` carries a drive-letter prefix, and the recorded value must be `processed`" is therefore true on every run and halts the plan. Scope such a scan to the `class` elements the task's own anchored match already selected, and record any document-wide residual count as informational only.
2. *Porcelain and anchored name-status are disjoint views, and a scope gate must subtract both.* On a branch that has already committed its feature folder, `git status --porcelain` listed exactly one path while `git diff --name-status <merge-base>` listed sixteen — twelve `.claude/agent-memory/` paths plus `issue.md`, `spec.md`, the plan, and the research artifact — all clean in porcelain and thus invisible to a porcelain-derived baseline. A Phase 5 gate that subtracts a set recorded under a porcelain-built heading fails on arrival. Capture the anchored name-status list as its own Phase 0 heading and subtract that set; do not hard-code the expected paths, because the plan and spec gain further commits from the Phase 6 check-offs. Related: [[agent-memory-is-tracked-scope-git-gates]].
3. *`$x = <call> *>&1` loses everything when the call throws.* A terminating error aborts the assignment statement, so the target variable keeps its prior value — the output is lost in exactly the failing-run state a degraded-run row depends on. Require a streaming writer (`Tee-Object -FilePath`, or an enclosing `Start-Transcript`) whenever a plan captures console output from a call that is expected to throw.

**Round 8 — the backslash-authoring rule needed a location.** Round 7 added a rule requiring every doubled-backslash snippet to be authored into a `.ps1` file and run with `pwsh -File`, but named no path; both plausible choices broke something. Fixed by mandating one reusable helper at `coverage/plan731-helpers.ps1`. See [[powershell-batch-budget-caps-plan-authored-helpers]] for the general rule and the hook line numbers.

**Round 9 — edit a backslash-bearing line by replacing only its non-backslash prefix.** A caller-supplied premise that a target line "contains no backslash" is itself a citation and must be re-derived: #731's `- **Version:**` line carried two, inside a carried-forward `` `\.claude\` `` literal, and the round-9 directive asserted it carried none. Replacing the whole line would have pushed that literal through the Edit tool, which is precisely the silent-collapse hazard the plan's own Backslash-literal authoring rule exists to prevent.

**Why:** the plan's rule states that both the Bash command parameter and the Write tool collapse a doubled backslash to a single one with no error, and that the resulting degraded anchor still produces a number, so the corruption is invisible on a passing run. An edit to prose *adjacent* to such a literal is the highest-risk edit in the file.

**Round 10 — two acceptance conditions that only coverage execution could falsify.** Execution reached `[P0-T11]` and blocked: `QfcCollectionController.cs:21` and `QfcDatamodel.cs:25` each carry a class-level `[ExcludeFromCodeCoverage]`, so neither has any `class` element in the Cobertura document and neither `[P0-T11]`'s per-filename `hits=` row requirement nor `[P5-T7]`'s "expected under Pre-existing uncovered" claim could ever hold. Only 3 of the 5 changed production paths are instrumented (`QfcQueue.cs`, `QfcFormController.SetupDisposal.cs`, `QfcRemainingQueueAdmission.cs`), and only `SetupDisposal.cs` gains substantive executable lines — so the "five file" changed-line gate is really a one-file gate. See [[excludefromcodecoverage-voids-per-file-coverage-rows]] for the general rule and the required sub-heading shapes. `SetupDisposal.cs` being instrumented is what let the executor reproduce the issue-#683 figure (70.70 percent, 46 uncovered lines) exactly, which independently validated the extraction rule and left `[P5-T8]`/AC15 untouched.

**Round 12 — budget the formatter's blank line, not one line per comment.** A numstat bound of "at most N insertions" for an inserted single-line C# comment must budget **two** insertions, not one: CSharpier requires a blank line immediately above an inserted comment, and it inserts one during the Phase 5 format pass. #731 bounded `QfcCollectionController.cs` to 2/1 and `QfcQueue.cs` to 1/0 and observed 3/1 and 2/0; execution blocked at `[P5-T10]`. No placement costs one net insertion — a trailing comment on the declaration line, or deleting a nearby blank to compensate, is 1 insertion plus 1 deletion and breaches the zero-deletion bound instead. The spec AC's *content* bound ("one statement and one comment line") is unaffected; the extra insertion is whitespace, so widen the numeric bound and state the reason inside the acceptance so it does not read as a relaxed gate.

Two corollaries:
- A Phase 1 acceptance of the form "line count equals its `[P0-T3]` value plus 1" is true only **before** the Phase 5 format task and false after it. State both measurement points, and say explicitly that the already-checked task is not re-run or unchecked.
- The "+2 after format" rule does **not** generalise to a file that a later phase also edits. `QfcDatamodel.cs` ended at exactly its 480-line baseline: +1 comment, +1 formatter blank, and −2 from the `[P3-T4]` construction-site shrink. Re-derive each file's end-state count individually rather than applying a uniform delta.
- Re-derive a line count with a `Grep` `^` count against the file when Bash is unavailable; it equals `(Get-Content).Count` whether or not the file ends with a newline. Also sweep the plan for restatements of the corrected figure — #731 carried the stale 506/2328 in the Plan-deviations disclosure and in two split follow-ups.

**How to apply:** scope `old_string`/`new_string` to a leading fragment that stops before the first backslash — for a version bump, `- **Version:** 1.7 (revision round 7: ` becomes `- **Version:** 1.8 (revision round 8: <new summary>. Carried forward from round 7: `. The backslash-bearing remainder then appears in neither operand and is never re-serialised. Verify with an occurrence-counting `-o` grep for `\\` before and after: an unchanged per-line count is the proof. Use the same technique for any single-line edit to a line holding a regex or a Windows path literal. Related: [[zero-hit-grep-gates-need-carveouts]].
