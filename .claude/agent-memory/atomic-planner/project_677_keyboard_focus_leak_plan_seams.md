Plan `docs/features/active/2026-08-28-quickfiler-keyboard-hook-leaks-to-outlook-677/plan.2026-08-28T08-45.md` (v1.4 after preflight R4; spec.md bumped 0.2 → 0.3 in R1). Seams to keep stable:

- **R1 killed the optional-trailing ctor parameter.** Adding `Func<bool>? mayTakeFocus = null` to all six `BreadcrumbDropDownHost` ctors looked source-compatible but breaks FIVE existing tests that bind to the constructor set by reflection with arity/shape matching: `BreadcrumbDropDownHostTests.cs:426-443` + `Part2.cs` (`constructor.Invoke(new object[7])` → `TargetParameterCountException`), `BreadcrumbDropDownLifecycleTests.cs:169-188` (same), `BreadcrumbDropDownReadinessTests.cs:263-289` (exact `Type[7]` `GetConstructor` → null), `BreadcrumbDropDownLifecycleCoverageTests.cs:117-152` (`HaveCount(4)` over arity-matched ctors), and `:236-254` (`.Single(Length == 9)` throws when two ctors hit 9-arity; its null-check loop also rejects a nullable param). **Lesson: before claiming "optional parameter = zero test edits", grep the test tree for `GetConstructor`, `GetConstructors`, `ConstructorInfo`, and `new object[` against the target type.**
- **Adopted seam:** `internal Func<bool> MayTakeFocus { get; set; } = () => true;` on the concrete host; `ItemViewer.Breadcrumb.cs` assigns `host.MayTakeFocus = MayRestoreBreadcrumbFocus;` right after the :198-207 construction, before `ConfigureBreadcrumbDropDown` (concrete local — no `IBreadcrumbDropDownHost` change, mock hosts unaffected). `InternalsVisibleTo("QuickFiler.Test")` verified at `QuickFiler/Properties/AssemblyInfo.cs:5`.
- **Compile-red consequence of a property seam:** the Part3 `PredicateHarness` must construct the concrete host with the TYPED public 7-arg ctor and assign the property in typed code — a reflection-built harness would compile fine at baseline and destroy the `[expect-fail]` gate. Error family is CS1061/CS0117 only (no CS1729/CS1739, since no ctor changes). Base-file `Harness` model citation is `:383-460` for the whole class (`Create()` construction pattern `:404-445`; the earlier `:383-443` end-line cut inside the `new object[]` initializer).
- **Deferred-drain harness identity (R2, corrected in R3):** the ONLY real deferred-drain seam is `BreadcrumbSelectorToggleUiBoundaryTests.CapturingSynchronizationContext` (`:346`, `DrainUntil` `:376`, `DrainAll` `:399`, `PendingCount` `:358`), consumed as `new BreadcrumbPopupUiOperations(new BreadcrumbUiDispatcher(context, errors.Enqueue))` (`BreadcrumbDropDownCoverageThresholdTests.cs:314-316`). `BreadcrumbDropDownLifecycleConcurrencyTests.cs`'s `InlineSynchronizationContext` (`:401-404`) posts synchronously — citing it makes any execution-time-vs-scheduling-time test (the AC-5 pin) unfalsifiable, since no gap exists in which a predicate flip could be observed. General lesson: before citing a test-harness SynchronizationContext as a timing seam, read its `Post` override — inline `callback(state)` means zero deferral.
- **R3 killed the ambient-context install.** R2's mechanic (public 7-arg ctor + `SynchronizationContext.SetSynchronizationContext(capturingContext)` before construction, so `CaptureCurrent()` at `BreadcrumbDropDownHost.cs:98` picks it up) creates NO gap either: `BreadcrumbUiDispatcher.IsCurrentBoundary()` (`BreadcrumbUiDispatcher.cs:255-272`) returns true when `SynchronizationContext.Current` is reference-equal to the captured context, and `Dispatch` (`:71-95`) then runs the action INLINE — `CapturingSynchronizationContext.Post` is never reached, making the AC-5 test unsatisfiable once the fix exists. Correct mechanic: pass the operations object explicitly as the `operations` argument of the INTERNAL 9-arg ctor (`BreadcrumbDropDownHost.cs:143-153`, reachable via `InternalsVisibleTo`), adapt legacy factories with `BreadcrumbPopupUiOperations.NormalizeFactory` (`ThresholdHarness`, `BreadcrumbDropDownCoverageThresholdTests.cs:306-327`), and never install the context ambiently. Drive `ScheduleObserved`-routed calls (`BreadcrumbDropDownOpenLifetime.cs:421-433`; `DropDown.Closed` → `InvalidateAndSchedule` at `BreadcrumbDropDownHost.cs:401`) with `DrainUntil`/`DrainAll` on the creating thread. R4 falsified the R3 claim that direct `Close(...)` tests need no drains: `CompleteAll` (`BreadcrumbDropDownHost.cs:436-455`) is itself synchronous but is only ever reached from a posted callback — `Close(reason)` routes through `InvalidateAndSchedule` when open (`BreadcrumbDropDownHost.cs:232-235`) and `TryCancelPendingOpen` otherwise (`:237`, `BreadcrumbDropDownOpenLifetime.cs:74-95`), both reaching `ScheduleObserved` → `PostAsync` → `Dispatch` → `_context.Post`. Under the capturing boundary EVERY route to `FinishClose` is queued, so all eight tests drain; skipping the drain makes a `FocusAnchorCount == 0` assertion pass with or without the guard. The AC-5 test additionally pins `PendingCount > 0` between the `Closed` raise and the predicate flip, proving queued-not-inline, and requires an open-and-drain precondition (else `OnDropDownClosed` early-returns at `:399` on `!OpenState` and `PendingCount` is 0 for a setup reason). `DropDown.Closed` is raised reflectively per the base file (`BreadcrumbDropDownHostTests.cs:233-238`, `InvokePrivate` with `ToolStripDropDownClosedEventArgs(AppClicked)`); this does not weaken D2's compile-red because construction and the property assignment stay typed. General lesson: a dispatcher that captures a context often ALSO short-circuits when running on it; check the `IsCurrentBoundary`-style branch before relying on `Post` being called.
- **Timestamp-named TRX (R2, optional-fix class):** every "exactly one TRX exists" gate under a task-private `/ResultsDirectory:` must have an explicit clear-the-directory-first step, or any re-run/Phase-5 restart deposits a second timestamped TRX and fails an otherwise-passing gate.

General lesson: never null-guard the event source inside its own subscriber; in low-line-count coverage-gated files every unreachable branch is a coverage liability.
