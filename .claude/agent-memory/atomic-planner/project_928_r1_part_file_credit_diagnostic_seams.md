Written 2026-09-29 while authoring the #928 cycle-1 remediation plan (relocate the `if scoped {warn} else {two asserts}` block from the ParseFile-copied entry point into `Invoke-MSTestWithCoverage.Scope.ps1` behind one unconditional call, so Pester 5.6.1 breakpoint coverage credits it from any suite; mechanism in feature-review's [[pester-breakpoint-coverage-binds-to-first-parsefile-copy]]).

**The remediation inputs' step-0 diagnostic was unfalsifiable as written.** It asked for a two-file ordered run (AssemblyDiscovery then the new suite) with `CodeCoverage.Path` = the Scope part file and "every part-file line credited". Every entry-point suite reaches all five predicate lines through the unscoped arm, so the first suite alone credits them and the run passes whatever the crediting mechanism does. The premise that matters is "a path-loaded part-file line reached ONLY by the later-sorting suite is credited". I redirected the subject to `Invoke-MSTestWithCoverage.Threshold.ps1` lines 53-54 and 123-124 (the two floor throws): AssemblyDiscovery either mocks both assertions or drives them at 0.8 (Grep `line-rate="0\.[0-7]` = 0 in that file), so it never reaches them, while the new suite's It 12/13 do. Gate = control run (AssemblyDiscovery alone) leaves all four uncovered AND the ordered run credits all four; the inputs' Scope 5/5 check is recorded but not the verdict.
**Why:** a gate that passes for a reason unrelated to the premise would have let the plan proceed on an unmeasured assumption, and the orchestrator's stop condition (`BLOCKED: part-file-not-credited`) could never fire.
**How to apply:** for any "is X credited from a later suite" diagnostic, first ask which lines the FIRST suite already reaches; pick a subject line the first suite provably cannot reach, and pair it with a single-suite control that shows it uncovered.

**Pester 5 mocks win over the entry point's own re-dot-source.** `Invoke-MSTestWithCoverageMain` dot-sources the helpers chain by path inside its body on every invocation, which redefines `Assert-Cobertura*` in the function's local scope; the AssemblyDiscovery call-site suite and the ResultsDirectory discard test nevertheless mock those assertions and observe the calls (334/334 green). So a call moved one scope deeper (from inside a part-file function defined by the same kind of dot-source) resolves the mock the same way. Do not spend a preflight round re-deriving command-lookup theory; cite the passing sibling tests as the empirical fact.
