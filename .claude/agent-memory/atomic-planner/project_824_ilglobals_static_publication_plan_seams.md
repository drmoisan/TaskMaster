Fourteen defects returned by `atomic-executor` preflight against `docs/features/active/2026-09-08-ilglobals-loadopcodes-unsynchronised-static-race-824/plan.2026-09-08T23-51.md` (2026-09-09). The generalisable ones:

1. **`global.json` `rollForward: latestFeature` plus `$host$` in `paths` defeats `dotnet --version` equality.** TaskMaster's `global.json:4` is `"rollForward": "latestFeature"` and `:6-9` lists `.dotnet-sdk` *and* `$host$`, so a host SDK in a higher 8.0 feature band wins over the repo-local one. Never gate on the exact pinned string. **Round 2 correction:** the round 1 replacement — assert a `.dotnet-sdk` install path in `dotnet --list-sdks` — was itself unverifiable by reading. `Install-RepoDotNetSdk.ps1` modifies neither `PATH` nor `DOTNET_ROOT`, and `--list-sdks` enumerates the muxer root of the invoked `dotnet`, not `global.json`'s `paths`. Gate instead on the installer's own filesystem marker: `Test-Path .dotnet-sdk/sdk/8.0.205` (`:36` install dir, `:56` marker composition, `:102-104` throw-if-absent), keep the `--list-sdks` output as recorded context only, and let a successful `dotnet --version` carry the resolution claim (`global.json:10` is an `errorMessage`, so an unresolvable SDK is a hard error).

2. **A csharpier before/after observation must compare the full patch, not the name list.** The formatter can rewrite a file the plan had *already* changed, which leaves `git diff --name-only` byte-identical between the two sides. Capture `(git diff $b | Out-String)` before and after and emit a `FORMAT_CHANGED_TREE=` boolean.

3. **"Restore the path and restart the format loop" does not terminate for pre-existing drift.** A path that csharpier rewrites because it was already unformatted at baseline gets rewritten again on the next pass. Split the remedy on the P0-T8 baseline drift list: in-list means halt blocked (the repo owns that repair, not this plan); absent-from-list means restore and restart, which terminates. This is also the reason the Phase 0 baseline formatter step must be the read-only `check`.

4. **CS8618 is a warning, not an error, under a plain `/t:Build` with no `/p:TreatWarningsAsErrors=true`.** An acceptance clause asserting `: error CS86[0-9][0-9]:` count 0 against such a log reads 0 whatever the compiler decided. Assert the `: warning CS86xx:` form on the plain build and reserve the error form for the nullable gate that supplies the switch.

5. **A merge-base anchor needs its own inertness proof.** When five later gates assert "anchored diff is empty for path X", any change a *sibling* branch/commit already contributed between the base and HEAD is attributed to this plan and no acceptance condition can tell the two apart. Add a Phase 0 task that lists `git diff --name-only <base> HEAD` and requires every inherited path to fall inside the plan's own Owned Write Set classes, halting otherwise.

6. **A global tool installed by `dotnet tool install --global` is not on the installing session's PATH.** A single combined `if (-not Get-Command) { install }; tool --version` probe can pass in-session and still leave the tool unresolvable for a later task. Require a second, separate invocation reporting `RESOLVED=True`.

7. **The `Glob` tool returns file paths, so a directory-only pattern (`packages/*/`) can return nothing while the directories exist.** Count with `Get-ChildItem -Directory` instead.

8. **A plan-authored PowerShell helper is subject to two `Write|Edit` PreToolUse hooks** at `.claude/settings.json:140` (`check-powershell-test-purity.ps1`) and `:144` (`enforce-powershell-batch-budget.ps1`). Budget the refusal path explicitly: fall back to separate `pwsh -NoProfile -Command` invocations, never raise the budget or relocate to evade.

9. **`.gitignore:84` is `*.log`.** When a spec AC demands "logs written under `<FEATURE>/evidence/qa-gates/`", a raw log there is untracked and cannot be committed. Reconcile in a decision record (markdown per-step artifacts are the evidence of record) and cite that record at check-off; do not silently drop the clause and do not edit the criterion text.

Round 2 added three more, all generalisable:

10. **A task that relocates code must state the deletion, not only the addition.** "Add a static constructor that runs the loop" performed literally leaves the original loop in place, so the file then holds two loops, two throws and four assignments — and the same task's acceptance ("exactly one `Invalid OpCode.`", "exactly two assignments") is unsatisfiable at the moment it runs. Write the instruction as "move X out of A and into B", name the exact line range deleted, and say what A's body looks like until the next task fills it.

11. **`git commit --amend` amends whatever the IMMEDIATELY PRECEDING task committed, not the task you had in mind.** A conditional `.claude/agent-memory` chore commit sitting between the feature commit and the closure task silently becomes the amend target, folding feature evidence in under the wrong message and rewriting history the epic layer may depend on. Use a plain second commit whose pathspec covers the residual files; a closure task always has at least the closure artifact to commit, so `exits 0` stays satisfiable.

12. **An observation captured mid-loop cannot evidence the whole loop.** "No step modified a tracked file, per the P5-T1 observation" is false-by-construction when P5-T1 runs immediately after step 1 and steps 2-5 follow. Cite two observations: the mid-loop one for its own step, and the post-loop re-validation task for the remainder.

Round 3 added two, and overturned a judgment I had defended in my round-2 reply:

13. **Pin every local identifier name whose spelling can feed a later count gate, and pin it in EVERY task of the class.** I left a task saying "captures the two fields into locals" and argued the resulting collision would be a *failing* gate rather than an unsatisfiable one. The reviewer closed it against me on three grounds: the plan's own authoring rule is "fix the evidence in the plan; never leave the executor to select it"; the collision is invisible at the authoring task's own acceptance and surfaces three phases later, after two build cycles and a rework phase have run on the file that would need editing; and I had only considered the flagged task, while a *second* task had the same exposure — a static-ctor local named after the field it assigns shadows that field, forces the `Type.field = ...` spelling, and raises that task's own "exactly two matches" count to four. Executor judgment does not discharge a class that spans tasks. **How to apply:** when any acceptance anywhere counts occurrences of an identifier, pin the names of every local the plan instructs the executor to create in that file, and add a zero-match check for the field spelling in each authoring task so the collision fails locally. A research document's example naming does not bind the executor unless the plan tells the executor to copy it.

14. **A later task that adds a `using` directive shifts every frozen line bound below it by one.** A gate comparing assignment line numbers against a *static-constructor line range recorded two tasks earlier* fails by exactly one line once the intervening task adds the import the fix needs — and the last field assignment sits immediately above the constructor's closing brace, so the +1 lands it exactly on the frozen upper bound. A later format pass can shift it again before a QC-phase re-run of the same gate. **How to apply:** never carry a line number across a task that edits the same file above it. Have the gate re-derive its own bounds by reading the file when it runs, and record the earlier task's values *beside* the re-derived ones with any difference stated, so the earlier record stays auditable without being load-bearing. Name the bounds explicitly — "three bounding line numbers" with only two named is itself executor-selected evidence.

Round 4 added two blocking defects, both about output the tool does not produce:

15. **`vstest.console.exe` prints no `Failed:` line and no `Skipped:` line on an all-green run.** Measured across four green runs in TaskMaster, including under `dotnet-coverage collect`, a passing run prints only `Test Run Successful.`, `Total tests: N`, `Passed: N` and `Total time:`. The two aggregate lines are independent per counter, so a run with failures and no skips prints `Failed:` and still omits `Skipped:`. An acceptance clause demanding all four counts "read from the console log" is therefore unsatisfiable on the success path it is written for. **How to apply:** state a derivation rule — record the match count for each of `^\s*Total tests:`, `^\s*Passed:`, `^\s*Failed:`, `^\s*Skipped:` alongside the values, take a count from its line when present, and record 0 with the absence stated when the line is missing and the log carries `Test Run Successful.`. There is no TRX fallback for the coverage runner: its inner argument list (`scripts/vscode/Invoke-MSTestWithCoverage.ps1:76`) supplies only `/Settings:`, `/InIsolation` and `/TestCaseFilter:`, and `scripts/vscode/TaskMaster.cli.runsettings` configures no logger, so no TRX exists to read.

16. **An unsorted `Get-ChildItem *.trx | Select-Object -First 1` selects the OLDER file after a re-run.** The default TRX filename is `<account>_<machine>_<per-second timestamp>_net<tfm>.trx`, vstest never overwrites, and directory enumeration is filename-ordered. Per-task results directories bound collisions across tasks only, never across re-runs — and a QC loop that restarts on any formatter rewrite, or a build task that fails and is corrected, makes re-runs a normal path. **How to apply:** always insert `Sort-Object LastWriteTime -Descending` before the `Select-Object -First 1`, and have each consuming task record the selected TRX's `LastWriteTime` plus the count of TRX files found, so a stale selection is visible rather than silent.

Also round 4, adjudicated non-blocking but taken: **a `git checkout` example must not quote a path the plan itself modifies.** A restore example whose operand is one of the plan's own owned source files discards the plan's production fix if an executor runs it unsubstituted. Quote an illustrative path outside the Owned Write Set instead, and say in the delivery note that it is an operand in a command example only, not a scoped path.

Round 5 corrected the round-4 replacement itself, and the seam is narrower than "outside the Owned Write Set":

17. **An illustrative path in a code span must be owned by NOBODY, not merely outside this plan's write set.** The round-4 fix substituted a sibling epic child's file (`UtilitiesCS/Extensions/DfDeedle.cs`, owned by child 825 at `spec.md:120-121`). It satisfies "outside the Owned Write Set" and is still wrong, because a downstream tool derives a feature's change footprint by harvesting backticked path tokens: a backticked sibling-owned path widens this feature's apparent blast radius at epic fan-in and falsifies the plan's own stated convention that a repository path appears inside a code span only when this feature owns it. **How to apply:** in an epic child's plan, an illustrative command operand must satisfy three conditions simultaneously — the file exists, it is outside every scope-gate class, and it appears in no sibling's owned set in `spec.md`. State those three conditions in the plan prose beside the operand so the choice is auditable. Then sweep the WHOLE plan for backticked path tokens against every sibling's owned stems, not just the line you edited: this class surfaced twice in consecutive rounds, and the second occurrence was introduced by the fix for the first.
